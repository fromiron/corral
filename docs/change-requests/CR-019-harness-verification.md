# CR-019: broker 코딩 도구·자동 검증·제한된 개선 (R2)

- 상태: 채택·구현 중, 2026-10-18. Bell의 H2–H8 구현 계속 요청.
- 기준: 개인 하네스 구현 플랜 H4–H6, CR-018, CR-012·013.
- Pi `read/edit/write`의 공개 계약을 기존 파일 broker에 연결한다. 읽은 근거는 execution별로 보관하며 다른 실행의 읽기가 쓰기 권한을 대신하지 않는다. symlink·범위 밖 경로·변경된 hash는 거절한다.
- 검증은 기존 등록 argv만 실행한다. 모델은 argv/env를 바꾸지 못한다. Run·execution·attempt·effect에 묶고, 시작 tree와 명령 fingerprint를 고정한다. 별도 검증 복사본에서 수행하며 취소는 자식 프로세스까지 정리한다.
- 검증 실행 상태와 품질 판정을 분리한다. error/cancelled/stale를 pass로 취급하지 않는다. 시간·외부 호출·ID는 주입한다.
- 검토 recipe의 기준·평가 역할·검사·시도/수정/시간/토큰 상한은 불변 revision이다. 기존 Agent→Review→Decision→Loop를 재사용한다. 동일 결과·같은 실패·상한 도달은 명시한 이유로 멈춘다.
- LSP 조회는 사용자가 등록한 서버만 실행한다. Hashline은 고정 fixture의 비교 평가 후보이며 기본 편집 방식으로 추가하지 않는다.
- 인간 승인과 원본 반영은 별도 동작이다. 자동 commit/push/deploy는 추가하지 않는다.

## 반례·완료 조건

TC-HAR-010/011: Pi 편집 계약, 변경된 읽기 근거·실행 간 혼선·경로 탈출 거절.
TC-HAR-012/013: spawn 실패, 중복 종료, 취소 후 자식 잔존, 변경된 fingerprint, stale 보고서 거절.
TC-HAR-014: 첫 시도를 포함한 상한, 기준 변경 거절, 같은 출력/실패 반복 중지, 부모 취소 후 후속 호출 없음.
일반 CI는 로컬 fixture/fake provider를 사용한다. 실제 품질·비용 개선은 opt-in 평가 없이 주장하지 않는다.

### H4 편집 경계

- SDK 역할에는 역할의 기존 파일 권한과 하네스 allowlist를 함께 만족하는 Pi `read/edit/write` 별칭을 제공한다. 기존 기본 worker의 파일 도구 계약은 유지한다.
- Pi 1.3.0의 `edit` 입력은 `{path, edits:[{oldText,newText}]}`다. 각 블록은 원본 파일에서 찾고 겹침·모호한 일치·변경 없음은 공식 도구와 같은 의미로 처리한다. BOM·줄바꿈·diff/patch 형식도 공개 도구를 재사용한다.
- 파일 I/O는 계속 서버 broker가 수행한다. Pi 편집 변환은 리소스·확장·세션을 로드하지 않는 별도 임시 worker에서 공개 `createEditTool`의 메모리 operations로 계산한다. 실제 파일 경로나 자격 증명을 보내지 않는다. 변경된 결과만 broker의 쓰기 lease 및 execution별 읽기 hash 검사로 반영한다.
- 검증 대상: 원본 Pi와 같은 정상 결과/오류, 여러 블록의 전부 성공 또는 무변경 실패, BOM/CRLF, 중복 문자열·겹침, 취소 시 무반영, 계산 중 원본 변경 거절. 단일 파일 도구는 기존 원자적 교체·파일 작업 기록을 재사용한다.

### 프로젝트 실행 설정과 신뢰

- 등록 검사와 LSP 서버 정의는 `ProjectToolConfigRevision`에 저장한다. 프로젝트별 증가 revision과 내용 hash를 가지며 수정·삭제하지 않는다. 역할은 등록 ID를 선택하고 Run 시작 시 해당 설정 revision을 고정한다. 실제 argv·로컬 경로는 공개 Run 이벤트에 넣지 않는다.
- 실행 신뢰는 프로젝트·종류·ID·launch fingerprint별 별도 결정이다. 설정 revision만으로 실행을 허가하지 않는다. fingerprint에는 정의, 실행 파일, 관련 scripts/lockfiles와 Node 버전을 포함한다. 신뢰 철회는 이미 고정된 설정에도 적용한다.
- 기존 `workspace_bindings.verify_json`은 migration에서 첫 설정 revision으로 보존한다. 자동 실행 신뢰로 승격하지 않는다. 이후 기존 수동 검사 설정 API도 같은 revision 저장소를 사용한다.
- TC-HAR-012/013은 이전 revision 보존, 동시 저장 충돌, 잘못된 argv/중복 ID, 기존 설정 이관 및 신뢰 비승격도 확인한다. LSP·검증 실행기는 같은 설정을 읽되 별도 수명으로 관리한다.

### Pro 재검토 후 파일 변경 전제조건

- edit는 계산을 시작할 때 확인한 원본 hash를 최종 적용까지 유지한다. 계산 중 파일 삭제·교체 또는 같은 execution의 재조회가 이 전제조건을 바꾸지 않는다. 없는 파일 생성과 기존 파일 편집을 구별한다.
- broker와 사람용 파일 조회는 같은 제한 바이트 읽기·파일 핸들 검사를 사용하되, 사람의 열람은 agent 읽기 기록을 만들지 않는다. 편집용 문자열은 BOM을 보존한다.
- 최종 OS 변경 제출 직전에 취소·원본 hash·대상 존재 여부를 재검사한다. 새 파일 생성은 이미 존재하는 경로를 덮지 않는다. 이미 OS에 제출한 작업을 취소가 되돌린다고 보장하지 않는다.
- 파일 변경 성공 후 기록만 실패하면 작업은 `uncertain`으로 남긴다. `failed`로 바꿔 실제 변경을 없던 것으로 기록하지 않는다. 임시 파일은 정리한다. TC-HAR-010/011의 삭제·재조회·BOM·최종 쓰기 취소·기록 실패 반례로 확인한다.
- 검증 명령 자체가 후보 복사본의 파일을 바꾼 경우 `targetUnchanged=false`와 `inconclusive`로 기록한다. 종료 코드 0만으로 실행 시작 tree의 통과를 확정하지 않는다. Git에서 제외한 의존성 준비는 별도이며 원본 폴더와 공유하지 않는다.

### 등록 검사 승인

- `run_check`는 역할 snapshot의 검사 ID와 허용 도구에 모두 포함될 때만 제공한다. argv/env를 모델 입력으로 받지 않는다. 수동 검사와 같은 실행기를 호출하며 현재 execution·attempt·effect를 보고서에 남긴다.
- 신뢰하지 않은 실행 해시는 기존 `approval.requested`에 선택 `tool` 정보를 붙여 Inbox로 보낸다. 실행·시도·효과·호출 ID, 대상 tree, 실행 해시, 본문 참조, 5분 기한을 고정한다. 명령과 인자는 비공개 본문에서 확인한다.
- 승인은 해당 실행 한 번에만 유효하다. 사용자 설정의 지속 신뢰로 승격하지 않는다. 취소·만료·실행 종료는 runtime의 거절과 이유로 닫으며 늦은 승인을 거절한다. 다른 승인이나 사용자 일시 정지가 남으면 Run을 재개하지 않는다.
- 승인 화면은 고정된 본문을 읽지 못하거나 참조와 불일치하면 실행 승인을 막는다. 공개 export에는 명령 본문이 들어가지 않는다.

### LSP 조회 경계

- `lsp_query({serverId,path,operation,position?})`는 선택한 등록 서버만 사용한다. operation은 diagnostics/definition/references이며 위치는 0부터 시작하는 UTF-16 좌표다. 서버 설치나 임의 명령 실행은 제공하지 않는다.
- 첫 구현은 질의마다 별도 서버 프로세스를 사용한다. 시작·질의·종료를 하나의 Coordinator 도구 효과가 소유하고, 다른 execution/Run과 서버 상태를 공유하지 않는다. 반복 초기화 비용을 줄이는 서버 재사용은 실제 성능 측정 뒤 별도 변경한다.
- 파일 broker에서 제한된 문서 본문·hash를 읽고 version 1로 연다. 응답의 문서 version, URI·경로·범위와 완료 시점의 파일 상태를 확인한다. 다른 파일 위치를 반환받은 사실은 해당 파일의 읽기/수정 권한을 대신하지 않는다.
- push 진단이 아직 오지 않았으면 오류 0개로 취급하지 않는다. pull 진단을 지원하는 서버는 공식 요청을 사용한다. initialize/질의 시간 초과·취소·늦은 응답·서버 종료는 결과를 통과 근거로 만들지 않는다.
- 서버가 요청하는 workspace/applyEdit는 거절한다. H8의 명시적 변경 제안 경로가 별도로 적용을 관리한다. 응답 크기와 결과 개수를 제한하며 원래 컴퓨터의 절대 URI를 모델/공개 기록에 넣지 않는다.
- TC-HAR-010/018: 실제 로컬 JSON-RPC fixture로 정상 질의, UTF-16 위치, 초기화 실패·무응답, 진단 미도착·다른 version, 범위 밖 URI, 질의 중 파일 변경·취소, 자손 프로세스 정리를 확인한다.

### H6 검토 recipe의 구체 계약

- 기존 Loop의 선택 `reviewRecipe`에 불변 `ReviewRecipeRevision` 내용을 보관한다. 별도 설정 저장소를 만들지 않고 기존 Corral definition revision과 Run snapshot이 과거 내용을 보존한다. 기준 본문은 definition의 criteria이며 recipe에 그 내용 해시를 고정한다. 기준 파일을 함께 지정하면 상대경로·전체 파일 hash도 고정한다.
- recipe는 후보 생성 노드, 평가 역할, 등록 검사 ID 목록, 첫 생성을 포함한 최대 시도, 추가 수정 횟수, 시간·모델 호출·출력 토큰 상한을 가진다. 컴파일 시 같은 Loop 안의 후보→평가자→검토 Decision 구조와 기준 해시를 확인한다. 정책·도구·검사 선택은 역할의 하네스에서 추가로 제한한다.
- 후보의 `submit_result`에서 Coordinator가 등록 검사를 실행한다. 기존 `run_check` 승인·실행·취소 경로와 해당 execution/attempt/effect를 재사용하며 자동 호출 주체는 runtime으로 기록한다. 검사는 모델이 실행했다고 주장하는 본문을 근거로 삼지 않는다.
- 제출된 후보 ID·기준 버전·recipe 해시·검사 보고서·대상 tree를 연결한다. 평가자는 후보와 검사 요약을 입력으로 받는다. 검사 실패는 review의 pass를 revise로 낮추고, 검사 오류/취소/stale 또는 잘못된 review는 통과가 될 수 없다. 같은 기준으로 새 Run을 시작해야 재시도할 수 있는 중단 이유를 기록한다.
- 같은 산출물 반복, 동일한 tree에서 같은 검사 실패, 시도/수정 상한, 시간/호출/토큰 소진은 중단이다. 기존 Loop 추가 승인이나 Reins 한도 patch도 recipe 상한을 늘리지 못한다. 기준 변경은 새 Run을 요구한다. 기본 Loop의 기존 승인 동작은 유지한다.
- recipe 예산에는 그 Loop의 모든 시도와 위임 자식의 모델 요청·압축·재시도를 포함한다. 부모 Run 한도도 동시에 지킨다. 취소 후 검사/모델을 새로 시작하지 않는다.
- 기준 파일은 broker 변경에서 보호하고 검사·판정 전에 다시 hash를 확인한다. 신뢰한 네이티브 코드의 직접 파일 접근을 막는 OS 샌드박스를 의미하지 않는다. 이미 확인한 검사 tree가 달라졌으면 최종 결과 통과 근거로 쓰지 않는다.
- TC-HAR-014-H/N: 첫 시도 포함, 검사 fail/review pass 불일치, 오류·stale·잘못된 기준, 동일 결과/실패, 예산/시간, 중복 제출, 추가 승인·patch 우회, 취소 중 검사 정리, 이전 후보/기준 혼선을 검증한다.

### 품질 비교의 판정 의미

- `corral eval`의 brief에 선택한 고정 정답 조건(exact text, 모든 문자열 포함, JSON 값 일치)을 선언한다. 정답을 실행 중 모델이 생성하지 않는다. 조건이 없는 기존 suite는 품질 미측정으로 남긴다.
- 개인 하네스 비교 suite는 baseline/mandatory_skill/deterministic_check/review_repair/coding_tool 다섯 그룹을 명시한다. 그룹은 실험 구성의 이름이며 그 이름만으로 기능이 실제 호출됐거나 효과가 입증됐다고 하지 않는다. 실제 Run ID·정의 hash·적용 하네스 hash·호출 도구와 요청 목적을 보고서에 기록한다.
- 최종 정답률은 정답 조건이 있는 전체 과제 중 정확한 최종 결과를 전달한 비율이다. 잘못된 통과는 성공으로 끝났으나 정답 조건을 어긴 결과다. 불필요한 반려는 정답인 후보를 품질 판정 때문에 중단한 경우다. 사용자 승인 대기·평가 오류·취소·예산 부족을 품질 반려로 계산하지 않는다.
- calibration/holdout 과제를 별도 집계한다. SDK 요청 재시도, execution 재시작, Loop 수정 횟수, 사용량·시간, 사용자 개입 요청을 따로 센다. 결정적 fake/fixture 실행은 도구 정확성과 계측 경로만 검증하며 실제 모델 품질 개선 수치로 발표하지 않는다.
