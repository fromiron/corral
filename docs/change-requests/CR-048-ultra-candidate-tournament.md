# CR-048 — Ultra 후보 경쟁·자동 판정·고도화·자동 반영

- 상태: **승인, 구현(C-173)** — Bell, 2026-10-23: “Ultra 개편 CR을 작성하되, 최종 우승안의 세션 사본 반영도 확인 없이 자동으로 하도록 해 줘. 구현은 아직 하지 마.”
- 목적 근거: 같은 날 Bell이 Ultra를 “복수 LLM을 최대한 사용하여 복수 에이전트가 각각 기능을 만들고(워크트리) 리뷰 에이전트가 리뷰 후 좋은 안건을 알아서 판정하고 고도화해가는 기능”으로 정의했다.
- 예산 결정: Bell, 2026-10-23: “Ultra는 어떤 예산·폭주 방지 한도도 없이 사용자 취소만 유지. 판정 모델 문제는 익명화로 닫기.” 직전 발언: “이건 토큰맥싱을 하면서 최선의 결과를 찾기위한거임. 리미트없이.”
- 대체 관계: [CR-031](CR-031-ultra-quality.md) C-114의 “선택 옵션”과 “사람의 정확한 후보 선택 뒤 하나만 승격”, CR-031의 절대 예산·80% 중지·마무리 예약을 **새 선택 형식(version 2)에 한해** 대체한다. C-114의 격리 사본·필수 검사·취소 경계와 C-118의 복수 모델·최대 지원 추론·provider conformance는 유지한다. version 1 기록과 그 해석은 바꾸지 않는다.
- 추적: C-173 / CRL-ULTRA-004 / TC-ULTRA-004-H,N,F.
- 기준: `35aff4b`. 현재 구현은 [모델 안내](../Models.md#복수-모델-ultra), `packages/core/src/ultra-team.ts`, `candidate-team.ts`, `candidate-budget.ts`, Coordinator의 후보 경로를 확인한다.

## 현재 구현과의 차이

| 목표 | 현재(C-118·C-114) | 이 CR |
|---|---|---|
| 모델마다 각자 구현 | 기본 Ultra는 주 모델 하나가 작성, 나머지는 읽기 전용 보조·검토. 후보별 구현은 명시 opt-in | 조건을 갖춘 요청에서 후보 경쟁이 Ultra 기본 |
| 우승안 판정 | 후보별 리뷰어가 자기 후보만 통과/수정 판정. 후보 간 비교 없음 | 검사 통과 후보를 판정 모델이 비교해 우승안 선택 |
| 고도화 | 후보 안의 수정 최대 2회 | 우승안 사본에서 판정 지적과 다른 후보의 장점을 반영하는 고도화 라운드 |
| 세션 사본 반영 | 사람의 명시 선택 후 단일 승격 | 사용자 확인 없이 자동 반영. 재검증 실패 시에만 보류 |
| 예산 | Run 절대 상한(기본 호출 40·출력 64,000·1시간, 스키마 최대 100·256,000·1시간), 80%에서 신규 작업 중지 | 예산·폭주 방지 한도 없음. 사용자 취소만 정지 수단 |

모델 판정과 고도화가 결과 품질을 높인다는 주장은 이 CR의 계약이나 결정적 시험의 증거가 아니다. 품질·비용 비교는 별도 opt-in live 평가로 기록한다.

## 흐름

계획 → 후보 구현 → 자격 심사 → 판정 → 고도화 라운드 → 최종 검사 → 자동 반영. 모두 같은 Run·취소 경로 안에서 Coordinator가 진행한다. 별도 병렬 Run, 외부 workflow 엔진, 모델이 호출하는 새 오케스트레이션 도구는 만들지 않는다.

## 1. 기본 모드와 선택 형식

1. `UltraSelection` version 2를 추가한다. 후보 모델 목록(기본: pool의 모델마다 한 후보, 2–5개, 같은 모델 중복 허용), 판정 모델(기본: 기존 `verifierProfile`), 고도화 라운드 수(0–3, 기본 2), 자동 반영 여부(기본 켬)를 시작 snapshot에 고정한다.
2. 후보 경쟁은 작업 사본이 있고 검증된 Linux 격리와 등록 검사를 제공하는 요청에서 기본이다. 조건을 충족하지 못하면 기존 C-118 협업 Ultra로 시작한다는 사실과 사유를 **시작 전에** UI/API/CLI 응답으로 보여 준다. 시작 후 다른 방식으로 조용히 바꾸지 않는다. 저장소 없는 텍스트 요청은 C-118 그대로다.
3. version 1 기록·재시도·재생은 기존 의미(opt-in 비교, 사람 선택)로 해석한다. 새 기본값을 과거 snapshot/hash에 소급하지 않는다.
4. UI·HTTP·`corral exec auto --ultra`는 같은 선택 계약과 재시도 identity를 사용한다. 사용자 정의 팀에는 적용하지 않는다.

## 2. 자격 심사와 자동 판정

1. 후보는 기존 C-114 경로로 실행한다(동시 3, 후보 안의 수정 최대 2회). 고정 tree에서 필수 등록 검사를 통과한 후보만 자격이 있다. failed·unsupported·cancelled·unknown·stale은 제외한다. 자격 후보가 없으면 `no_acceptable_candidate`이며 반영하지 않는다.
2. 자격 후보가 하나면 판정 호출 없이 우승으로 한다. 둘 이상이면 판정 모델이 비교한다.
3. 판정 입력은 과제·criteria·후보별 diff·검사 결과·사용량 요약이다. 후보는 익명 라벨로 제시하고 모델/profile 이름을 노출하지 않는다. 다른 provider의 원시 대화·추론 서명·로그는 전달하지 않는다. 판정 에이전트는 후보 작성 에이전트와 컨텍스트를 공유하지 않는 별개 실행이다. 판정 모델이 어떤 후보의 작성 모델과 같아도 익명화 외의 별도 처리는 하지 않는다.
4. 판정 출력은 strict schema다. 순위, 기준별 근거(해당 diff·검사 증거 ref), 우승안의 개선점, 다른 후보에서 가져올 요소(후보 ID와 파일/hunk ref)를 담는다.
5. Host는 후보 ID가 이 Run의 자격 후보인지와 증거 ref의 존재를 검증한다. 형식 오류는 같은 판정에 1회 수정 요청한다. 그래도 유효하지 않으면 자동 반영 없이 `judgment_failed`로 두고 기존 수동 선택을 열어 둔다.
6. 판정은 검사 결과를 대체하지 않는다. 검사 실패 후보를 우승으로 만들 수 없다.

## 3. 고도화 라운드

1. 우승 후보의 격리 사본에서만 진행한다. 세션 사본과 다른 후보 사본은 바꾸지 않는다.
2. 작성자는 우승 후보의 모델이다. 입력은 판정의 개선점과 판정이 지목한 다른 후보 요소의 명시 binding이다. 다른 후보 사본 전체의 읽기 권한을 주지 않는다.
3. 각 라운드는 작성 → tree 고정 → 필수 검사 → 판정 모델의 직전 수용 버전 대비 비교(개선/동등/퇴보)다. 검사 실패·퇴보·판정 무효인 라운드는 폐기하고 사본을 직전 수용 tree로 되돌린다.
4. 라운드 상한, 판정의 “추가 개선 없음”, 취소 중 먼저 오는 조건에서 멈춘다. 결과는 검사 통과 증거가 있는 마지막 수용 tree다.

## 4. 자동 반영

1. `autoApply`가 켜져 있으면 사용자 확인 없이 기존 C-114 승격 경로로 최종 수용 tree를 세션 사본에 반영한다.
2. 반영 직전에 기존 조건을 다시 확인한다: 소유 실행 종료·정산, 출처 tree hash와 최종 수용 tree 일치, 검사 증거의 신선도, 세션 사본이 Run의 기준 tree에서 바뀌지 않았음. 반영 전 체크포인트([CR-030](CR-030-runtime-checkpoints.md))를 남겨 사용자가 기존 복원 경로로 되돌릴 수 있게 한다.
3. 재검증이 하나라도 실패하면 반영하지 않고 `auto_apply_held`와 사유를 표시한다. Run 중 사용자가 세션 사본을 바꾼 경우도 여기에 해당한다. 세션 사본을 덮어쓰거나 자동 merge하지 않으며 기존 수동 선택을 열어 둔다.
4. Host가 Run에서 결정적으로 정한 command ID로 반영하고 receipt를 남긴다. 같은 반영이 두 번 일어나지 않는다.
5. 반영은 작업 사본의 파일 변경까지다. Git commit·push·merge·배포는 하지 않는다.
6. 서버 재시작·crash 뒤에는 자동 반영을 재개하지 않는다(CR-031 유지). 반영 전 중단은 수동 선택 대기, 반영 중 중단은 기존 승격 복구 의미로 상태를 확인한다.
7. 반영 결과로 우승 후보·수용 라운드·검사 결과·체크포인트를 Run과 알림에 연결한다.
8. `autoApply`를 끄면 우승안과 판정 근거를 보여 주고 기존 수동 선택으로 반영한다.

## 5. 예산 없음

1. version 2 Ultra Run에는 Corral이 거는 사용량 한도가 없다. Run 전체의 모델 호출 수·출력 토큰·실행 시간 상한, 80% 신규 작업 중지와 마무리 예약, 에이전트별 반복·호출 횟수 한도를 적용하지 않는다. 호출당 출력은 각 모델·transport가 지원하는 최대값을 쓰며 Corral이 더 낮추지 않는다.
2. 실행 길이는 흐름의 구조로만 정해진다: 후보 2–5개, 후보 안의 수정 최대 2회, 고도화 라운드 상한과 판정의 “추가 개선 없음”. 동시 실행 3과 host 전체의 모델·worker·process 동시성 상한([CR-042](CR-042-desktop-capabilities.md) ABS-06)은 사용량 한도가 아니라 자원 admission이므로 유지한다.
3. 에이전트가 같은 도구 호출을 반복하는 등 끝나지 않는 실행은 사용자가 취소할 때까지 계속되며 그 비용은 사용자가 부담한다. 이는 Bell이 승인한 위험이다. 공급자 쪽 사용량 제한·429·구독 한도는 Corral이 해제하지 않으며 기존 오류 경로로 처리한다.
4. 시작 화면·API·CLI는 Ultra에 사용량 한도가 없다는 사실을 시작 전에 표시한다. 실행 중에는 후보·판정·고도화별 실제 사용량을 계속 보여 주고, 측정하지 못한 사용량을 0이나 무료로 표시하지 않는다.
5. 일반 모드와 version 1 Ultra의 기존 Run 예산 계약은 바꾸지 않는다. 기존 `RunLimits` 스키마 상한을 전역으로 넓히지 않고 version 2 Ultra 경로에서만 적용하지 않는다.

## 6. 취소와 늦은 결과

1. 사용자 취소가 유일한 정지 수단이므로 Run 취소는 실행 중인 모델 호출·도구 실행·검사·후보 실행을 모두 확정적으로 멈춰야 한다. 반복 중인 에이전트나 응답이 없는 provider 호출도 취소 후 새 호출을 시작하지 않는다.
2. 후보 취소는 해당 후보만 멈춘다. 고도화 중인 우승 후보를 사용자가 취소하면 고도화를 멈추고 자동 반영하지 않으며 수동 선택을 열어 둔다.
3. Run 취소는 모든 소유 실행을 정리하고 반영하지 않는다. 반영 중 일시 정지·취소 거절은 기존과 같다.
4. 늦은 판정·라운드 결과는 발생한 라운드 번호와 tree에만 귀속하며 이후 라운드나 반영 결과를 덮지 않는다.

## 유지 경계

D&D·Reins, 사용자 정의 팀 불변, 후보 안의 native 확장·MCP·시작 명령·LSP·임의 host 명령 금지, 작업 사본별 단일 writer, 미연결·미검증 모델의 시작 전 거절과 provider fallback 금지, 과거 recipe/hash 보존을 유지한다.

## 검증

구현 전에 대표 반례가 실패하는 것을 확인한다. 결정적 worker, 임시 Git worktree, 실제 Linux 격리를 사용하며 일반 CI에 유료 호출을 넣지 않는다.

- TC-ULTRA-004-H: 자격 후보 판정 → 고도화 라운드 수용/폐기 → 자동 반영과 체크포인트 복원.
- TC-ULTRA-004-N: 판정 형식 오류·검사 실패 후보의 우승 시도·Run 중 세션 사본 변경·전원 실패·자동 반영 끔에서 반영 없음 또는 보류. 기존 기본 상한을 넘는 호출·출력·시간에서도 version 2 Ultra가 중지되지 않고, 일반 모드·version 1 Ultra의 예산은 그대로 적용된다.
- TC-ULTRA-004-F: 반복 중인 에이전트·응답 없는 호출을 포함한 후보/Run 취소, 늦은 판정·라운드 결과, 재시작, 같은 반영 command 중복.

## 구현 메모 (2026-10-23, C-173)

Bell의 같은 날 지시 “로컬 머지하고 그대로 계속 진행해”로 구현했다. 위 계약을 바꾸지 않고 구현에서 정한 세부만 적는다. 실행 결과는 [구현 기록](../evaluation/Ultra-Tournament-2026-10-23.md)에 있다.

- 협업 전환 사유는 `no_working_copy`(작업 사본 없음)와 `no_isolation`(후보 사본·복원·diff·Linux 격리 미제공) 두 가지다. 저장소가 있는데 등록 검사가 없거나 harness가 strict가 아니면 C-114/C-118처럼 모델 호출 전에 거절한다. 협업으로 바꿔도 C-118이 같은 조건에서 거절하기 때문이다.
- 실행 방식은 auto 시작 응답과 Run snapshot의 `ultra.mode`·`fallbackReason`으로 계획 호출 전에 확정·표시된다. Studio 선택 화면은 조건을 설명하며, 시작 전 예측 표시는 host 격리 상태 조회가 없어 구현하지 않았다.
- 판정은 후보 그래프의 `judge` 노드(검토 모델, 산출물 작성·제출만)로 실행한다. 이를 위해 Corral 정의의 노드 상한을 27에서 28로 올렸다. 라벨은 검사를 통과한 후보에만 A부터 붙인다.
- 고도화 라운드는 우승 후보 Loop의 다음 회차로 `write_n`→`synthesize_n`(등록 검사 포함)만 실행하고 후보별 리뷰어 판정은 생략한다. 라운드 안의 recipe 중지는 우승 후보를 실패로 만들지 않고 해당 라운드만 폐기한다.
- 자동 반영 명령 ID는 `auto_apply_<runId>`로 고정한다. 승격 claim 전 거절(세션 사본 변경, 미정산 등)은 보류로 남아 직접 선택할 수 있다. claim 뒤 실패는 기존처럼 복구 근거 확인이 필요하다는 거절이 직접 선택에도 적용된다.
- 사용량 한도 없음은 Run snapshot의 version 2에서만 켜진다. 호출당 허용량은 1,000,000 토큰으로 내보내고 worker가 모델 카탈로그 최대값으로 낮춘다. Corral 정의의 `limits`는 스키마상 그대로 기록되지만 적용하지 않는다.
- CLI `exec auto --ultra`는 version 2를 보내지만 작업 사본 없이 실행하므로 협업 방식이다. 후보 수·고도화·자동 반영 옵션은 CLI에 추가하지 않았다.
