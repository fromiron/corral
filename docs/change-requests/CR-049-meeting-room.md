# CR-049 — 회의실: 여러 모델과의 그룹 채팅과 작업 인계

- 상태: **승인, 그룹 채팅 후속 수정 구현** — Bell, 2026-10-23: 최초 C-174–176의 구현·검증 이후 실제 화면을 보고 기본 개발 역할·라운드·반론 절차가 의도와 다르다고 정정했다. 같은 날 후속 지시가 이전 발언 규칙 1–17의 충돌 부분을 대체한다. C-174·175는 순차·무작위 발언, 사용자 연속 전송, 에이전트 멘션 응답까지 구현했고 [그룹 채팅 검증](../evaluation/Meeting-Chat-2026-10-23.md)을 확인했으며 C-176의 사람 채택·같은 프로젝트 인계 경계는 유지한다. 이전 Linux 시험은 [실행 기록](../evaluation/Meeting-Room-2026-10-23.md)의 당시 계약에 대한 증거이며 새 대화 경험의 검증이 아니다. 실행 Corral 추천·복제/신규 생성은 후속 범위다.
- 목적 근거: 같은 날 Bell이 회의실을 “역할별 ai에이전트(지정 가능)들과 의논하는 기능이고 카카오톡, 라인 같은 채팅방과 같음. 협업 채팅창으로 브레인스토밍, 의견 도출 등을 하고 비서가 회의록을 작성하여 플래닝 하는 기능”으로 정의했다. 회의 결과를 프로젝트 세션에 지시하거나 플랜을 실행하는 흐름은 Bell이 제공한 초안 「Corral 회의실 → 일반 프로젝트 세션 인계 구현 플랜」(2026-10-23, P0–P6)을 따른다.
- 추적: C-174–C-176 / CRL-MEET-001–003 / TC-MEET-001–003-H,N,F.
- 관계: [CR-048](CR-048-ultra-candidate-tournament.md)의 Ultra와 별개다. Ultra는 같은 과제를 여러 모델이 구현해 겨루는 실행 방식이고, 회의실은 사람이 주도하는 대화와 결정이다. 회의는 프로젝트를 바꾸지 않으며 실행은 인계받은 일반 세션의 기존 Coordinator·권한·취소 경로에서만 일어난다.

## 1. 대화와 정리의 현재 계약

Bell의 2026-10-23 후속 지시가 기준이다. 회의실은 사람이 여러 AI와 대화하는 그룹 채팅방이며, 대화를 시작하기 위해 개발 역할이나 라운드·반론 단계를 선택하지 않는다.

### 1.1 일반 대화

1. 사람이 보낸 메시지에 참가자가 답하고, 사람은 이유를 묻거나 조건을 보태며 같은 대화를 이어 간다. “오늘 저녁 뭐 먹을까?” → 각 모델의 메뉴 제안 → “왜 그 메뉴야?” → “가볍게 먹고 싶어”는 각각 자연스러운 메시지다. 후속 질문은 저장된 앞 대화와 참가자 답을 문맥으로 사용한다.
2. 멘션이 없으면 비서를 뺀 참가자가 답한다. `@참가자 이름` 또는 입력창의 참가자 선택으로 응답 대상을 좁힐 수 있다. 명시적으로 역할 이름을 정한 참가자는 그 이름으로도 대화한다.
3. 대화에는 제품 수준의 라운드 번호·반론 버튼·반론 횟수 상한이 없다. 반대 의견이나 질문도 일반 메시지로 보낸다. `/반론`을 포함한 입력을 별도 진행 단계로 자동 변환하지 않는다.
4. 참가자는 동시에 답을 만들지 않고 메시지마다 참가자 목록을 한 번 무작위로 섞은 뒤 한 명씩 순차적으로 발언한다. 다음 참가자는 시작 직전까지 실제로 게시된 앞 참가자 발언을 읽는다. 각 참가자에게는 자신의 역할 지시만 전달하며 다른 참가자의 역할/캐릭터 지시는 공유하지 않는다. 아직 하지 않은 말이나 반응을 대신 꾸며 대화가 진행된 것처럼 표시하지 않는다. 에이전트가 다른 참가자에게 답을 요청할 때는 `@이름`을 쓰고, 지목된 참가자는 그 발언을 읽고 다음에 응답한다. 이미 답한 참가자도 다시 부를 수 있다. 단순한 이름 언급, 자기 멘션, 알 수 없는 이름은 호출하지 않으며 비서의 정리는 여전히 사람이 요청한다.
   모델이 답하는 동안에도 사람은 여러 메시지를 연속해서 보낼 수 있고 각 메시지는 즉시 게시된다. 현재 발언은 보존하고, 다음 발언은 새 사용자 메시지들을 읽고 최신 요청에 답한다. 아직 시작하지 않은 이전 요청의 답변과 이전 요청에서 늦게 도착한 자동 멘션은 새 사용자 요청보다 먼저 실행하지 않는다. 사람이 중지하면 현재 발언과 아직 시작하지 않은 발언·멘션 응답을 함께 중지한다. 재열기나 동일 명령 재전송으로 멘션 호출이 반복되지 않는다.

### 1.2 선택 역할과 비서

5. 기본 참가자는 모델 이름으로 구분하며 역할을 강제하지 않는다. 일상 질문에는 자연스럽게 답하고, 요청하지 않은 개발 계획·구현·검증 보고서를 만들지 않는다.
6. 개발을 의논할 때에는 사람이 각 참가자에게 필요한 역할과 역할 설명을 명시적으로 지정한다. 개발 역할은 선택 사항이며 대화 주제와 요청에 맞게 적용한다. 기존에 저장된 이름·역할을 조용히 삭제하거나 바꾸지 않는다.
7. 비서는 자동으로 의견을 내거나 매 메시지마다 정리하지 않는다. 사람이 결론을 정리하고자 `@비서`로 요청하거나 **비서에게 플랜 정리 요청**을 누르면 회의록과 플랜을 만든다.
8. 회의록은 쟁점, 참가자별 주장, 합의, **남은 이견**, 미확인 사실을 담는다. 플랜은 그 논의에 근거한 목표·범위·제외 범위·완료 기준·다음 행동을 담은 결정 후보다. 이견을 합의로 뭉개거나 답하지 않았거나 실패한 참가자를 찬성으로 세지 않는다. 결론이 부족하면 남은 질문과 확인할 사항을 남긴다.
9. 비서의 플랜은 실행 승인이 아니다. 사람이 검토·수정·채택한 뒤에만 구현 작업 세션으로 넘긴다(3–4절).

### 1.3 실패와 중지

10. 참가자 하나가 실패하면 해당 답의 실패와 이유를 보여 주고 다른 참가자의 답은 보존한다. 자동 재시도는 하지 않으며, 사람은 그 참가자를 멘션해 다시 물을 수 있다.
11. 사람은 현재 답변 생성을 중지할 수 있다. 이미 도착한 답과 사용자 메시지는 남기고 중지 사실을 표시한다. 늦은 답은 원래 메시지에만 귀속하며 새 메시지에 끼어들지 않는다. 이전 버전의 미전송 대기 메시지 편집은 원래 command ID와 현재 상태를 확인한다.
12. 회의를 닫았다 다시 열어도 저장된 기록만 보여 주며 새 호출을 하지 않는다.

### 1.4 참가자와 사용량

13. 참가자는 비서를 빼고 2–6명이다. **회의의 Corral 사용량 한도(토큰·호출·시간)는 없다.** 사람은 현재 답변을 중지할 수 있고 공급자 쪽 제한·과금은 그대로다. 사용량은 참가자별로 보여 주며 미확인 사용량을 0으로 세지 않는다.
14. 내부 저장/API의 `rounds`·`roundId`는 기존 기록과 실행 소유권을 잇는 호환성 단위다. 이를 UI 절차나 사용자에게 요구하는 대화 개념으로 노출하지 않는다. 기존 반론 기록·동일 명령 재전송은 읽을 수 있어야 하지만 새 대화의 반론 횟수를 제한하는 근거가 되지 않는다.

## 2. 회의실과 참가자

1. 회의는 프로젝트 안의 세션 종류 `meeting`이다. 일반 작업 세션과 다른 session ID를 가지며 기존 세션 저장·목록을 공유한다. 기존 세션은 모두 `work`로 해석하고, 기록이 있는 세션의 종류 변환은 하지 않는다.
2. 참가자는 이름, 모델 프로필, 선택적 역할 설명(프롬프트)으로 정한다. 서로 다른 회사의 모델을 섞을 수 있고, 같은 모델을 여러 역할에 써도 된다(역할은 별개 에이전트다). 미연결 모델은 회의 시작 전에 표시하고 그 참가자를 뺄지 묻는다.
3. 새 회의의 기본값은 연결된 모델의 이름과 역할 없는 참가자다. 아키텍처·구현·검증 같은 개발 역할을 기본으로 부여하지 않는다. 개발 목적에 맞는 역할은 사람이 설정하며 참가자 수를 품질 보장으로 표시하지 않는다.
4. 회의 참가자는 프로젝트 파일을 바꾸거나 명령·검사를 실행하지 않는다. 사람이 고른 근거(파일, 결과, 링크한 산출물)만 읽기 입력으로 받는다. 같은 프로젝트라는 이유로 모든 자료를 읽지 않는다.
5. 회의 중 모델 출력의 “승인됨”, “실행하자” 같은 문장은 권한이나 실행 지시가 아니다.

## 3. 결정 채택

1. 사람은 회의록의 결정 후보를 고치거나 일부 행동만 골라 **결정 버전**으로 채택한다. 결정 버전은 목표·범위·제외 범위·완료 기준·남은 이견·근거를 담은 불변 기록이며, 바꾸면 새 버전이다.
2. 회의 종료와 결정 채택은 별개다. 회의를 닫은 뒤에도 채택할 수 있고 철회·대체도 사람의 기록으로 남긴다.

## 4. 작업 인계

Bell 초안의 방향을 따른다. 정확한 데이터 계약과 명령은 착수 시 이 CR에 기록한다.

1. **작업으로 넘기기**는 채택한 결정 버전에서만 연다. 대상은 같은 프로젝트의 기존 일반 세션 또는 새 일반 세션이다. 회의 세션·다른 프로젝트·보관된 세션은 서버도 거절한다.
2. 전달물은 전체 대화가 아니라 작업 요청서(목표·범위·제외·완료 기준·남은 이견·위험·선택한 근거)다. 기각된 대안은 “기각된 배경”으로 구분한다.
3. 실행 구성은 기존 Corral 또는 자동 방식(Ultra 포함)을 사람이 고른다. 세션의 기본 Corral은 바꾸지 않고 이번 요청에만 고정한다.
4. **초안으로 넘기기**는 대상 세션에 인계 항목만 남기고 실행하지 않는다. **넘기고 시작하기**는 기존 시작 경로로 새 Run을 연다. 대상 세션이 실행 중이거나 입력창에 보내지 않은 내용이 있으면 끼어들거나 덮지 않고 초안으로만 남긴다.
5. 같은 인계 명령의 재전송은 같은 세션·항목·Run을 돌려준다. 다른 결정·범위·대상은 새 명령이다. 응답이 불확실하면 기존 receipt를 먼저 조회한다.
6. 회의에는 대상 세션, 출처 결정 버전, 사용한 실행 구성, Run 상태와 결과 링크만 남긴다. 결과를 다시 논의하려면 사람이 **이 결과로 다시 논의**를 눌러 새 대화 메시지의 입력으로 고정한다.

## 검증

구현 전에 대표 반례가 실패하는 것을 확인한다. 결정적 에이전트를 쓰고 일반 CI에 유료 호출을 넣지 않는다.

- TC-MEET-001-H/N/F: 기본 모델 이름·역할 없음, 일상 질문→이유→조건 변경의 대화 문맥, 명시 역할·멘션, 라운드/반론 절차 없는 메시지, 생성 중 연속 메시지 즉시 게시·최신 요청 우선, 에이전트 멘션 응답·중복/자기/인용 멘션 무호출, 참가자 실패·사람 중지·늦은 답·재열기에서 새 호출 없음. 이전 반론 기록/명령의 호환성은 새 대화의 횟수 제한과 구분한다.
- TC-MEET-002-H/N/F: 요청 전 비서가 개입하지 않음, 요청 시 대화에 근거한 회의록·플랜과 남은 이견, 미응답을 찬성으로 세지 않음, 사람 채택 전 플랜의 실행 불가, 결정 버전 변경·철회.
- TC-MEET-003-H/N/F: 기존/새 세션 인계, 회의 세션·다른 프로젝트 거절, 실행 중 대상과 미전송 입력 보존, 같은 명령 재전송의 중복 없음, 응답 유실 후 receipt 조회, 취소와 시작 경합.

## C-174 구현 설계 (2026-10-23)

최초 구현의 저장·실행 경계를 유지하되 위 후속 계약에 맞춰 대화 기본값과 프롬프트·표시를 수정한다. 아래 내부 `round` 이름은 호환성을 위한 데이터 식별자이며 대화 절차가 아니다.

1. **저장**: 회의는 `WorkSession.meeting`(참가자 설정·메시지별 응답 묶음·대기 메시지)을 가진 세션이다. 없으면 `work`다. 회의 상태는 세션 revision CAS로만 바꾸며, 일반 세션 수정 경로(PATCH)로는 바꿀 수 없다. SQLite는 `meeting_json` 열을 추가한다.
2. **답 하나 = Run 하나**: 참가자 답은 그 참가자의 이름·역할·모델로 만든 단일 에이전트 Run이다. 산출물 작성·제출만 허용하고 파일·명령·검사 도구는 없다. 사용자 메시지에 대한 Run은 저장된 앞 대화와 이번 메시지를 읽는다. 한 번에 한 참가자의 Run만 시작하고, 다음 참가자 입력은 앞 Run이 끝난 뒤 확정된 발언까지 다시 구성한다. 참가자 목록에는 이름만 공유하고 역할 지시는 본인에게만 전달한다. 아직 차례가 오지 않은 참가자는 대기로 표시하며, 중지하면 남은 참가자를 호출하지 않는다. 재시작 후 남은 발언은 자동으로 재개하지 않는다. 시작 명령 ID는 `meeting_<roundId>_<participantId>`로 고정해 같은 메시지 재전송이 Run을 늘리지 않는다.
   실제 공급자가 도구 호출 없이 정상 종료한 텍스트 답변도 회의 답이다. worker가 정상 stop·비어 있지 않은 본문·도구 시도 없음을 확인하고, Coordinator가 현재 회의·시도·마지막 완료 호출·취소 여부를 대조한 뒤 기존 산출물 작성/제출 경로로 확정한다. 추가 모델 호출은 없으며 잘림·오류·빈 답·미완료 도구 작업이나 일반 작업 Run에는 적용하지 않는다.
3. **사용량 한도 없음**: Run 시작 요청의 `meeting` 출처(세션·라운드·참가자)가 있으면 Coordinator는 CR-048 version 2와 같은 방식으로 Corral 사용량 한도를 적용하지 않는다. 이 출처는 회의 서비스만 붙이며 HTTP Run 시작 요청에서는 거절한다.
4. **메시지 응답 서비스**: core의 회의 서비스가 멘션 해석, 참가자/비서 응답 대상, 진행 중 답변과 즉시 게시된 사용자 메시지, 명시 에이전트 멘션 응답, 중지(현재 진행·대기 발언 취소)를 처리한다. 새 UI와 프롬프트는 라운드/반론 진행을 요구하지 않으며 legacy 반론 명령은 호환성 경로로만 남긴다. 서버와 브라우저 데모가 같은 서비스를 쓴다. 답의 상태와 본문은 각 Run의 상태와 확정 산출물에서 읽는다.
5. **재시작**: 이전 버전의 미전송 대기 초안과 아직 시작하지 않은 답변은 서버 재시작 뒤 자동으로 보내지 않는다. 사람이 보내기를 눌러야 한다. 시작 기록만 있고 Run이 없는 답은 “시작되지 않음”으로 보이며 다시 호출하지 않는다.
6. **선택한 근거**: 사람이 첨부한 텍스트 파일과 명시적으로 고른 결과만 원문·해시·크기를 고정해 메시지 입력에 넣는다. 프로젝트 자료를 자동으로 읽거나 링크를 따라가지는 않는다. 이전 버전의 대기 초안 편집도 같은 command ID와 대기 상태를 확인한다.

## C-175·C-176 구현 설계 (2026-10-23)

1. 사람이 요청할 때만 비서가 대화 기록에서 회의록과 플랜을 작성한다. 확정 산출물은 구조화된 회의록으로 검증하며 플랜은 기존 결정 후보의 목표·범위·제외·완료 기준·행동 필드를 사용한다. 주장·이견·합의의 지지자는 앞 대화의 실제 성공한 답을 참조해야 한다. 형식이나 참조가 틀리면 회의록 오류를 저장하고 자동으로 재호출하지 않는다.
2. 결정 후보는 회의록 안에만 둔다. 채택 명령은 사람이 편집한 목표·범위·제외·완료 기준·남은 이견·근거·위험·행동·기각된 배경을 불변 결정 버전에 저장한다. 대체는 새 버전, 철회는 별도 기록이며 명령 재전송은 같은 결과를 돌려준다.
3. 인계 명령은 결정 버전과 요청별 실행 구성을 고정한다. 기존 Corral은 선택 당시 정의·revision을 보존하고, 자동 방식은 모델·추론·품질·Ultra 선택을 보존한다. 대상 세션 기본값은 수정하지 않는다.
4. 서버는 receipt와 대상 항목을 실행 전에 저장한다. 동일 명령의 다른 본문은 거절하며, 응답이 불확실하면 저장된 receipt와 기존 시작 명령을 조회한다. 조회나 재열기는 실행을 재개하지 않는다.
5. 대상은 같은 프로젝트의 보관되지 않은 일반 세션이다. 진행 중 Run·대기 항목 또는 요청한 브라우저에 저장된 미전송 초안이 있으면 초안으로 남긴다. 다른 브라우저의 로컬 초안은 서버가 관찰할 수 없으므로 전역 초안 부재를 보장하지 않는다.
6. 인계 이력에는 출처 결정·대상 세션·실행 구성·Run 상태·결과 링크를 표시한다. 결과 재논의는 사람이 명령을 보낼 때만 확정 결과를 새 회의 입력으로 고정한다.
7. `meeting_` 접두사의 내부 시작 ID는 회의 서비스만 사용한다. 일반 시작·자동 시작/취소·결과 질문·분기·runtime 재개 API로 선점하지 못한다. 회의 답 Run의 분기·runtime 재개도 회의 발언 규칙을 우회하므로 거절한다.
