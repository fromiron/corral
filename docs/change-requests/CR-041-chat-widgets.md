# CR-041: 채팅 위젯과 실시간 작업 계획

현재 상세 기준: [채팅 위젯 상세 계약](../current/chat-widgets-contract.md). 아래 원래 계획의 Git 참조는 승인 경위이며 현재 작업 목록은 [활성 계획](../plans/README.md)이다.

- 상태: 구현 및 로컬 통합 검증 — 사용자 지정 v2 플랜 (Git `373764467a52:docs/plans/Corral-Chat-Widgets-Implementation-Plan-v2.md`). 유료 provider·native IME 검증은 아래 경계에 남긴다.
- 기준: `fix/studio-chat-display`의 `1329703` 이후. CR-007 `startFromVersion`과 testkit `defaultReply`는 유지한다.
- 추적: C-121, CRL-WIDGET-001, TC-WIDGET-001-H/N, TC-WIDGET-002-H/N.
- 디자인: 내장 leeskills review-visuals, check-accessibility. 기존 토큰·Button·Popover 재사용. 새 폰트 없음.

## 계약

1. 채팅 타임라인 밖, 오른쪽 위에 상황별 요약 카드를 둔다. 컨텍스트는 메시지 추정과 전체 요청 추정을 타입으로 구분한다. 전체 비율은 요청 측정이 완전하고 그 호출의 창을 알 때만 표시한다.
2. 입력창 바로 위 Todo는 기존 `update_plan` → `work_plan.updated` → private body를 읽는다. UI는 완료를 저장하지 않는다. 현재 작업을 수행하는 execution 계획을 보여주고, 끝난 팀 계획을 진행 중으로 올리지 않는다.
3. 승인·질문·실패·불명확 효과는 접힘 밖에 둔다. 오른쪽 패널이 다른 Run을 열어도 현재 실행 store의 `open`을 갈아끼우지 않는다.
4. `model.request_recorded.contextEstimate`는 메시지 합으로 남긴다. `contextUsage`는 선택 필드다. 과거 이벤트는 재작성하지 않는다.

## 반례

- 정상: 다단계 계획의 완료 수와 현재 항목이 갱신된다. 단순 요청은 계획을 만들지 않는다.
- 실패: 계획 본문·측정 실패는 로딩/오류/부분 측정으로 남고 비율을 만들지 않는다.
- 취소: 수동으로 접거나 펼친 선택은 revision이 바뀌어도 유지된다. 성공 종료만 auto를 접는다.
- 중복: 같은 toolCallId는 한 행이다. 공급자 usage는 추정에 더하지 않는다.
- 늦은 응답: 이전 revision, 다른 execution, 다른 세션의 결과가 현재 대상을 덮지 않는다.

## 범위 밖

예산 증가, 권한 확대, 자동 compact 정책, Todo 클릭 완료, 폰트 임베딩, testkit `defaultReply` 변경.

## 검증

단위 시험은 결정적 fixture다. 유료 모델 호출은 넣지 않았다.

### 이전 기록 (2026-10-19, 충분한 완료 증거가 아님)

로컬 Studio `http://localhost:5173`, 데모 세션 `session_d3a906e8`, 미커밋 작업 트리.

- 패널을 닫아도 타임라인 위 컨텍스트 칩과 입력창 위 활동 줄이 남았다. 컨텍스트 팝오버는 측정이 없을 때 비율을 만들지 않고 범주를 “이번 요청에 없음”으로 보였다.
- `짧게 안녕이라고만 답해줘`를 보낸 뒤 타임라인에 요청과 결과가 남았다. 이 데모 역할은 기존 echo 경로라 계획 도구를 호출하지 않았고, 화면은 가짜 Todo를 만들지 않았다.
- 채팅 폭 420px에서 위젯 바가 가로로 넘치지 않았다. 승인 대기, 다단계 `update_plan` 전환, IME, 스크롤 앵커의 브라우저 기록은 하지 못했다.

### 2026-10-20 재조사와 수정

기준 HEAD `ec5e244` / `fix/studio-chat-display`의 기존 미커밋 구현을 보존하고 수정했다.
사용자가 제공한 Codex 화면은 정보 계층·여백·얕은 보조 UI의 참고이며, 기능 계약은 v2 플랜이다.

**배치에 대한 사용자 정정:** 실제 화면을 본 사용자가 “위젯이 상단바 위치에 있는데
내가 준 이미지랑 다르지 않음?”이라고 지적했다. 현재의 직접 지시는 v2의 상단 바
제안보다 우선한다. 데스크톱에서는 상단 바를 제거하고 기존 보조 영역에 약 300px의
독립된 오른쪽 위 카드를 둔다. 상세 패널은 그 자리를 대체하며 제3열을 만들지 않는다.
작업 계획은 입력창 위에 남긴다. 가용 Workbench 폭 900px 이하 또는 상세 패널을
보는 동안에는 입력창 근처의 “작업 현황” 버튼으로 같은 카드를 연다.
기존 상단 바/좁은 열 칩 위치 테스트는 이 사용자 정정에 맞는 기하·접근 경로로 갱신한다.
추가 사용자 정정에 따라 세션 화면의 상단 “프로젝트 / 세션” 경로 표시를 제거하고,
세션 탭과 패널·메뉴·검색 버튼을 같은 52px 행에 통합했다. 별도의 탭 행은 없으며,
이전 약 85px에서 약 33px를 줄였다. 세션 탭과 사이드바가 탐색을 담당하고,
접근 가능한 세션 제목은 시각적으로 숨겨 보존한다. 좁은 화면이나 접힌 사이드바에서는
사이드바 열기 버튼을 유지한다. 탭이 넘치면 탭 영역만 가로 스크롤하고,
사이드바 등에서 세션을 열어도 활성 탭을 보이는 위치로 옮긴다.
프로젝트·설정 화면의 위치 표시는 유지한다.

- 기존 `ChatView.header`가 타임라인 안에 있었고 좁은 열에서 칩이 없어졌다. 첫 수정의 상단 바도 사용자가 이미지와 다르다고 확인했다. 최종 수정은 스크롤과 독립된 오른쪽 위 카드 및 좁은 폭의 동일 카드 팝오버다.
- Todo 본문은 공유 hook에서 hash·scope·실행·attempt·revision·criteria를 검증한다. 로딩 오류, 잘못된 immutable 본문, 늦은 응답, 수동 역할/접힘, 끝난 planner를 현재 진행으로 보여주는 경우를 수정했다.
- 요청을 조립한 추정과 최종 provider payload의 측정을 분리했다. 두 runtime에서 실제 도구 schema·tool-call arguments·system sources를 집계하고 이미지·불투명/미지원 입력은 부분 측정으로 남긴다. 이후 모델 패치도 요청 시점의 창과 모델에 고정된다.
- 실제 질문·승인 UI는 오른쪽의 같은 Run 대응 영역 하나만 사용한다. 전역 DOM 검색을 제거하고 대상 URL·포커스·receipt를 보존했다. 활성 활동·Pause/Resume은 컴포저 근처로 모았다.
- 기본 패널에서 결과 목록이 보이지 않던 경우, 명시한 과거 결과/원문과 저장된 탐색 상태가 섞이던 경우를 고쳤다.
- 종료 뒤 늦은 usage/effect 정산을 읽기 위해 과거 조회는 진행 중 요청만 공유한다. 종료 상태를 immutable 캐시로 취급하지 않는다.
- 데모 계획은 실제 `host.invokeTool(update_plan)` 경로로 0/7에서 7/7까지 갱신한다. 짧은 요청에는 계획을 만들지 않으며, 진단·역할 prompt·이전 결과 전체를 답변에 재귀 인용하지 않는다.

`TEST DRIFT`: 기존 승인 E2E는 타임라인과 패널에 같은 제출 컨트롤이 두 번 있다는 것을
기대했다. v2의 단일 대응 호스트 계약에 맞춰 현재 실행의 대응 바 → 정확한 패널 →
기존 답변/승인 receipt를 검증하도록 바꿨다. 데모 역할 prompt echo 기대도 공개 답변에
진단을 섞지 않는 계약으로 교체했으며 testkit `defaultReply`는 그대로다.

검증 환경은 Windows Node 24.19.0, 실제 Studio/로컬 서버/Pi adapter/Coordinator/SQLite와
로컬 결정적 provider다. 화면과 입력 흐름은 인앱 브라우저에서도 별도로 조작했다.
회귀 E2E는 합성 composition event를 포함하며 실제 한국어·일본어 OS 입력기 검증은 아니다.
유료 실제 LLM의 자율적인 계획 발행, Electron 배포, 전체 WCAG 적합성은 주장하지 않는다.

실제 화면 확인에서 `createFauxCore` 기반 검증은 최종 provider payload hook을 호출하지
않는다는 한계가 드러났다. 이 경우 UI의 “부분 측정·최종 입력 대기”가 정확하며
전체 비율로 승격하지 않았다. 컨텍스트 게이지의 통합 검증은 실제 Pi serializer →
로컬 HTTP 호환 endpoint → `model.payload_recorded` → UI 경로로 별도 수행한다.

최종 화면 비교와 검사 결과는 [화면 검증 기록](../evaluation/Chat-Widgets-Design-QA.md)에 있다. 현재 배치 계약은 문서 상단의 상세 계약 링크를 따른다.
