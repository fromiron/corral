# 초기 개발의 테스트 운영

기본 E2E의 범위는 [데모·출시 명세](../specs/features/demo-release.md)를 따른다. 매 UI 변경마다 상세 브라우저 시나리오 전체를 통과시키는 것을 개발의 전제로 삼지 않는다.

기본 Vitest 테스트 한 건의 제한 시간은 15초다. 저장소 전체와 개별 패키지에서 같으며, 별도 시간이 필요한 테스트는 자체 제한을 명시한다.

| 명령 | 용도 |
|---|---|
| `pnpm test:e2e` | PR CI와 일반 개발의 Chromium 스모크 2개. 대화 전송·답변·재로드, 캔버스 포인터 연결 |
| `pnpm test:e2e:extended` | 변경한 영역의 상세 시나리오를 필요할 때 선택 실행 |
| `pnpm release:gate` | 전체 확장 E2E와 다중 브라우저·접근성·IME를 포함한 출시 검증 |

서버 스모크는 먼저 `pnpm --filter @corral/studio build`가 필요하다. 공급자 응답은 기존 로컬 fake를 쓰며 유료 API는 호출하지 않는다. 기본 검사는 Chromium만 설치하면 된다. 확장 검사의 Firefox 프로젝트는 `pnpm --filter @corral/studio exec playwright install firefox`로 따로 준비한다.

특정 회귀만 확인할 때는 파일과 프로젝트를 지정한다.

```sh
pnpm test:e2e:extended e2e/server/server.spec.ts --project=server --workers=1
```

세션 테스트는 대화 옆 패널의 탭(파일 · 문서 · 변경 · 실행 #n · 결과 등)을 `workbench.ts`의 도우미(`openPanelTab`, `openPane`, `selectPanelTab`, `closePanel`)로 열고 고르고 닫는다. `openPane`은 명령 팔레트의 "{탭 이름} 열기"(Open {tab})를 고른다. 문서 탭은 그 접근 이름으로 찾는다(이름이 같으면 " — 폴더", 원본 폴더면 ", 프로젝트 원본 폴더"가 붙는다. [세션 패널 › 문서 탭](../specs/features/session-panel.md#문서-탭)). 다른 탭으로 이동한 뒤 보존된 입력을 검사할 때와 실제 입력할 때를 구분한다. 실행 완료는 개별 실행 행의 부분 일치 텍스트가 아니라 Run의 정확한 상태나 확정 결과로 기다린다. 디자인킷 전환 뒤에도 키보드 조작·전체 식별자 펼치기·초안 보존 같은 원래 검증 목적은 유지한다.

## 마지막 검증 절차

한 작업을 마치고 합치기 직전에, 합칠 커밋에서 한 번 돌린다. 각 명령은 종료 코드 0이어야 통과다. 실패하면 거기서 멈추고 [흔들리는 테스트 분류 절차](#흔들리는-테스트-분류-절차)로 가른다.

1. 변경을 모두 커밋하고 `git status`가 깨끗한지 확인한다. `pnpm lint`는 git이 무시하지 않는 추적 안 된 파일도 읽으므로, 작업 트리를 깨끗하게 만들 수 없으면 합칠 커밋을 [분류 절차](#흔들리는-테스트-분류-절차) 5단계와 같은 형식(`git worktree add`)으로 별도 작업 트리에 꺼내 거기서 이 절차를 돌린다. 이 절차 도중 소스를 바꾸면 1단계부터 다시 돌린다.
2. `node --version`이 [`.node-version`](../../.node-version)의 값과 같은지 확인한다([출시 증거와 게이트 › 라이선스와 SBOM](release.md#라이선스와-sbom)).
3. 이 기계에서 다른 테스트 실행이나 빌드가 돌고 있지 않은지 확인한다. 아래 명령도 한 번에 하나씩 돌린다. 함께 돌면 짧은 구간을 보는 테스트가 거짓으로 실패한다.
4. 5179 포트에 떠 있는 서버가 없는지 확인한다. 로컬의 확장 검사는 그 포트에 이미 떠 있는 서버를 그대로 쓰므로, 다른 작업 트리의 서버가 떠 있으면 그 코드를 검사하게 된다.
5. `pnpm install --frozen-lockfile`을 돌린다.
6. PR 게이트(`.github/workflows/pr.yml`)의 명령을 같은 순서로 돌린다. Vitest에는 CI와 같은 워커 수를 준다.

   ```sh
   pnpm contracts:check
   pnpm lint
   pnpm typecheck
   pnpm test --maxWorkers=2
   pnpm test:dev
   pnpm build
   pnpm test:e2e
   ```

7. 바꾼 것에 따라 다음을 더 돌린다.
   - 의존성을 바꿨으면 `pnpm deps:check`([AGENTS.md › Validation and Documentation](../../AGENTS.md#validation-and-documentation)). PR 게이트에는 없고 출시 게이트에만 있다.
   - `tools/release/`나 `tools/deps/`를 바꿨으면 `pnpm test:release`. 이 `node --test` 테스트는 `pnpm test`에도 PR 게이트에도 들지 않는다.
   - `apps/server/resources/builtin/`을 바꿨으면 더 돌릴 것이 없다. `pnpm test`가 `pnpm builtin:check`와 같은 검사를 한다([기본 제공 스킬과 에이전트 › 생성과 검사](../specs/features/builtin-crew.md#생성과-검사)).
8. 확장 검사를 돌린다. `apps/`나 `packages/` 아래(Studio·서버·패키지)에 바뀐 것이 없으면 8·9단계를 건너뛴다. 동작을 바꾸지 않고 파일 이동·이름 바꾸기·import 경로 고치기만 한 작업도 8·9단계를 건너뛰고 6단계의 스모크로 갈음한다. 그런 작업인지는 작업의 커밋마다 `git show -M --stat <커밋>`에 이름이 바뀐 파일과 import 경로만 고친 파일만 나오는지로 확인한다.
   - 언제나: 바꾼 영역의 확장 스펙 파일만, 위 "특정 회귀만 확인할 때"의 형식(스펙 경로, `--project`, `--workers`)으로 돌린다.
   - [docs/plans](../plans/)에 계획을 두는 긴 작업([AGENTS.md › Getting Started](../../AGENTS.md#getting-started) 4번)을 끝낼 때만: 확장 검사 전체를 돌린다.

     ```sh
     pnpm test:e2e:extended --workers=2
     ```

   전체 실행은 `--project`를 주지 않아야 chromium·firefox·server 세 프로젝트를 모두 돈다. `--workers=2`는 CI의 값이다. 워커가 많으면 실행이 끝나기 전의 짧은 구간을 보는 스펙이 흔들린다. server 프로젝트는 6단계의 빌드 결과(`apps/studio/dist`)를 쓰고, 하네스는 빌드가 있는지만 볼 뿐 최신인지는 보지 않는다. Firefox는 위 준비 문단대로 따로 설치한다.
9. [흐름 장면](#흐름-장면)에 적힌 영역을 바꿨으면 그 절의 명령으로 흐름 장면을 돌린다. 6단계에서 빌드했으므로 빌드 명령은 건너뛴다.
10. 돌린 명령과 결과를 작업 보고에 적는다. 조건 때문에 건너뛴 단계(7·8·9)와 돌리지 않은 전체 실행은 건너뛰었다고 그 조건과 함께 적는다. 실패는 분류 절차의 결과 이름으로, 결과 표의 "할 일" 칸이 정한 내용과 함께 적는다.

화면이나 서버 동작을 바꾼 변경이 실제 Studio에서 동작하는 것을 보이고 기록을 남기는 방법은 개발 스킬 [verify-corral](../../.claude/skills/verify-corral/SKILL.md)이다. 모델을 부를 수 없는 서버에 브라우저 Studio를 붙여 여정마다 실행 기록 하나를 남기며, 데스크톱 앱은 다루지 않는다. 위 단계의 하나가 아니며 테스트를 대신하지 않는다.

## 흔들리는 테스트 분류 절차

어느 실행에서든 테스트가 실패하면 아래 순서로 가른다. 각 단계는 다음 단계로 넘어가거나 결과 하나로 끝난다. 어느 결과에서도 재시도, 제한 시간 늘리기, 테스트 약화·삭제로 통과시키지 않는다(아래 추가·수정 기준).

1. Playwright 테스트가 실패했으면 다시 돌리기 전에 결과물을 옮긴다. Playwright는 시작할 때 `test-results`를 지운다. 저장소 루트의 `test-results/`는 git이 무시하므로 그 아래의 아직 없는 이름으로 옮긴다.

   ```sh
   mkdir -p test-results && mv apps/studio/test-results test-results/failed-run
   ```

2. 실패 메시지와 trace에서 대상 부재·입력 가림·서버 실패를 먼저 구분한다. 실패가 테스트 밖에서 왔으면(브라우저 미설치, `Studio is not built` 오류, 5179 포트를 다른 서버가 씀, 고정값과 다른 Node, 마지막 빌드 뒤의 소스 변경) 결과는 **환경 문제**다. 아니면 3단계로 간다.
3. 실패한 파일을 이 브랜치가 새로 만들었거나 바꿨는지 본다.

   ```sh
   git diff --name-only "$(git merge-base HEAD <합칠 브랜치>)" -- <실패한 파일>
   ```

   경로가 찍히면 결과는 **회귀**다. 아무것도 찍히지 않으면 4단계로 간다.
4. 실패한 파일만 워커 하나로, 다른 무거운 프로세스 없이 다시 돌린다. Vitest 파일은 경로를 준다. Playwright 스펙은 위 "특정 회귀만 확인할 때"의 명령 형식으로 스펙 경로를 `--project`보다 앞에 두고, 프로젝트는 실패 보고에 찍힌 이름을 쓴다.

   ```sh
   pnpm test apps/server/test/builtin-crew.test.ts --maxWorkers=1
   ```

   통과하면 결과는 **흔들림**이다. 같은 테스트가 다시 실패하면 5단계로 간다.
5. 브랜치를 딴 커밋을 별도 작업 트리에 꺼내 4단계의 같은 명령을 돌린다. E2E 파일이면 그 트리에서 먼저 `pnpm build`를 돌린다.

   ```sh
   git worktree add ../corral-base "$(git merge-base HEAD <합칠 브랜치>)"
   cd ../corral-base && pnpm install --frozen-lockfile
   ```

   거기서도 실패하면 결과는 **이미 있던 실패**, 통과하면 **회귀**다. 끝나면 `git worktree remove ../corral-base`로 지운다.

| 결과 | 할 일 |
|---|---|
| 환경 문제 | 원인을 고치고 마지막 검증을 실패한 단계부터 다시 돌린다. 테스트 실패로 세지 않는다 |
| 흔들림 | 마지막 검증을 이어 간다. 보고에는 통과가 아니라 "전체 실행에서 실패, 단독 실행에서 통과"로 스펙 이름, 옮긴 trace 위치와 함께 적는다. 흔들리는 테스트는 결함이며 고치는 일은 따로 한다 |
| 이미 있던 실패 | 보고에 한 번 적고 마지막 검증을 이어 간다. 요청이 없으면 고치지 않는다 |
| 회귀 | 합치기 전에 고친다. 고친 뒤 마지막 검증을 1단계부터 다시 돌린다 |

## 흐름 장면

대화 화면의 전이가 화면을 흔들지 않는지를 재는 장면 검사다. 동작의 기준은 [대화 입력 흐름](../specs/features/composer-flow.md)과 [표시 상태](../specs/features/presence.md)가 정하고, 여기에는 재는 방법과 합격선을 적는다.

```sh
pnpm --filter @corral/studio build
pnpm --filter @corral/studio exec playwright test --config playwright.flow.config.ts
```

- Chromium에서 워커 하나로만 돈다. 워커를 늘리면 여러 워커가 `test-results/flow/report.json`을 함께 써서 깨진다. 전체는 30분쯤 걸린다.
- 서버는 `e2e/server/harness.ts`의 하네스가 테스트마다 띄운다. 스크립트 어댑터와 가짜 응답만 쓰고 외부 호스트는 하네스가 막는다.
- 기본 게이트와 확장 구성에 들어 있지 않다. 대화 타임라인, 실행 행, 컴포저, 활동 바, 사이드바의 대화 행, 회의 화면을 바꿨을 때 해당 장면을 돌린다.

`e2e/flow/probe.ts`가 구간마다 재고 `e2e/flow/scene.ts`가 합격선을 단언한다. 결과는 `test-results/flow/report.json`에, 전이 전후 화면은 `test-results/flow/<장면>/<단계>.png`에 남는다.

| 재는 것 | 합격선 |
|---|---|
| 구간 시작 때 있던 `[data-chat-item]`과 `[data-session-row]`의 컨테이너 기준 위치 변화 | 1px 이하. 한 프레임만 움직여도 실패다 |
| 끝을 따라가는 중: 타임라인 마지막 항목의 아래 가장자리와 컴포저 위 가장자리의 간격 변화 | 1px 이하 |
| 위로 올려 읽는 중: 항목의 화면 기준 위치 변화 | 1px 이하 |
| 입력 상자 아래 가장자리의 화면 위치 변화 | 0px (빈 대화의 첫 전송은 제외) |
| 화면에 보이는 `[data-presence-label]` 가운데 같은 대상(`run:<id>`, `execution:<id>`)의 수 | 하나. 사이드바의 대화 행에는 이 속성이 없다 |
| 1280×800에서 상단 줄과 쉬는 컴포저 높이의 합 | 200px 이하 |
| 본문 열 너비 | 720–760px |

| 장면 | 재는 전이 | 추가 확인 |
|---|---|---|
| ① 대기 | 빈 대화 → 요청 전송 → 실행 시작 → 완료 | 활동 바가 실행 전후 같은 높이, 밝은·어두운 테마 |
| ② 여러 역할 | 세 역할이 함께 작업 중인 상태에서 하나씩 완료 | 닫힌 활동 바가 화면에 보이는 역할을 다시 말하지 않음, 펼쳐서 합류까지 조작 두 번, reduced motion |
| ③ 합류·끼어들기 | 합류 전송 → 읽힘, 끼어들기 → 응답이 끊기고 전달됨, 읽히지 못한 합류가 새 요청으로 시작 | 키보드만으로, 끊긴 응답이 제자리에 남음. 출력과 성공이 따로 닿는 변형, 답 본문이 먼저 해제되는 변형 |
| ④ 승인·입력 대기 | 작업 중 → 응답 대기 → 답함 → 작업 중. 카드를 화면 밖으로 올린 뒤 활동 바에서 승인 | 같은 요청이 화면에 한 번, 입력해 둔 초안 보존, Enter로 승인되지 않음 |
| ⑤ 인용 | 구절 선택 → 칩 → 전송 → 보낸 칩에서 원문으로 | 키보드만으로, 칩이 늘어도 입력 아래 가장자리 고정 |
| 사이드바 | 실행 종료 → 2초 안에 다음 실행 시작 | 행이 묶음을 옮기지 않음, 응답 대기는 즉시 이동 |
| 회의 | 사람 메시지 → 자동 선택 → 답변, 수신자 없음, 연쇄 8회에서 계속 카드 | 대화와 같은 컴포저 |

합격선을 낮추거나 구간·장면을 지워서 통과시키지 않는다. 재시도로 가리지 않는다. 실패한 실행의 trace와 `report.json`은 다시 돌리기 전에 [분류 절차](#흔들리는-테스트-분류-절차)의 1단계대로 옮겨 둔다.

## 추가·수정 기준

- 데이터·권한·취소·명령·상태 전이는 단위·통합 테스트로 검증한다. DOM 순서, 장식 클래스, 고정 픽셀, 번역 문구를 이유로 E2E를 늘리지 않는다.
- 실제 브라우저가 필요한 경계만 E2E로 남긴다. 포인터 hit testing, 실제 포커스·키보드, 페이지 재로드와 서버 연결이 해당한다.
- 기본 스모크는 두 흐름으로 유지한다. 새 상세 기능은 기존 단위·통합 테스트에 추가하고, 브라우저 검증이 필요하면 해당 파일만 선택 실행한다.
- 포인터 입력은 실제 핸들로 보내고 결과를 확인한다. `force`, DOM 이벤트 직접 호출, 임의 sleep, timeout 증가로 가려진 핸들이나 잘못된 대상을 통과시키지 않는다.
- 캔버스와 무관한 서버 테스트는 그래프를 UI로 매번 재조립하지 않고 기존 fixture/API를 우선한다. 현재 확장 검사에 남은 중복 UI 준비는 해당 시나리오를 수정할 때 함께 줄인다.
- 한 테스트는 한 사용자 결과를 확인한다. 화면의 모든 중간 상태를 고정하지 않는다. 재시도는 0이며, 실패 trace에서 대상 부재·입력 가림·서버 실패를 먼저 구분한다.

기존 상세 파일은 선택 검증용으로 유지한다. 기본 게이트에서 제외됐다는 사실은 그 시나리오의 통과나 출시 준비 완료를 뜻하지 않는다.
