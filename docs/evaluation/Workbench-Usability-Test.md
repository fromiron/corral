# Workbench 사용성 평가 진행 안내 (02-UX-Spec §11)

- 근거: 02-UX-Spec (Git `373764467a52:docs/proposals/workbench-v0.1/02-UX-Spec.md`) §11 "사용자 평가: 최소 5명의 과제 기반 탐색 테스트".
- 관찰할 과제: "어제 작업 찾기", "변경/미반영 구분", "diff 의견 전달 대상 확인".
- 상태: **진행 준비 완료, 실시 전.** 사람 참가자가 필요하므로 Claude가 대신 할 수 없다. 진행자(Bell)가 이 안내대로 실시하고 결과를 [결과 기록지](Workbench-Usability-Results.md)에 남긴다.
- 해석 범위: 5명은 큰 문제를 찾는 표본이다. 성공률을 시장 전체의 효과로 일반화하지 않는다(§11).

## 1. 참가자

- 5명 이상. 섞어서 모은다:
  - 코드 저장소를 다뤄 본 사람 3명.
  - 문서·조사 작업만 하는 사람 2명.
- Corral을 처음 보는 사람을 우선한다. 개발에 참여한 사람은 넣지 않는다.
- 기록에는 이름 대신 P1–P5를 쓴다. 화면이나 음성을 녹화할 때만 따로 동의를 받는다. 녹화가 없어도 진행할 수 있다.

## 2. 환경 준비(참가자마다 새로)

두 가지 중 하나를 쓴다. 기본은 **A**다.

**A. 로컬 서버(실제 파일).** 진행자 컴퓨터에서 준비한다.

1. 빈 작업 공간으로 서버를 연다: `pnpm corral dev`(모의 에이전트로 충분하다).
2. 연습용 Git 저장소를 만든다. 예: README.md·notes/1.3.md·src/version.ts를 커밋한다.
3. 프로젝트 "릴리스 노트"를 만들고 2의 폴더를 연결한 뒤 "이 저장소를 신뢰"를 켠다.
4. 팀: 템플릿 "Single agent"로 만든다. 팀 설계에서 "파일을 바꿀 수 있음"을 켜고 저장한다.
5. **어제 작업**을 만든다(과제 1용). 평가 전날 다음을 해 둔다:
   - 세션 "1.4 버전 노트 쓰기"를 만들고 작업 복사본을 만든다.
   - 요청 "1.4 노트를 써 줘"로 Run 1회를 끝낸다.
   - 고정하지 않는다.
   - 같은 프로젝트에 세션 2개("지원팀용 변경 요약", "공지 메일 준비")를 더 만든다.
   - 전날 준비가 어렵다면 당일 준비하고, 과제 지시문에서 "어제"를 "전에"로 바꾼다. 바꿨다는 사실을 기록지에 적는다.
6. 과제 2용: 5의 세션에서 승인과 반영을 하지 않은 상태로 둔다. 원본 폴더에는 커밋하지 않은 변경 1개를 따로 만들어 둔다(예: src/version.ts를 1.3.1로 고침).

**B. 브라우저 데모(설치 없음).** `/projects`의 "예시 프로젝트 만들기"를 쓴다.

- 두 번째 프로젝트("릴리스 노트")에 연결된 예시 폴더·파일 팀·작업 복사본이 생긴다.
- 데모는 새로고침하면 Run과 폴더가 사라진다. 그래서 "어제" 과제는 당일 준비한 세션으로 대신한다.

공통: 화면 1280×800 이상, 한국어 UI, 사이드바와 패널은 기본 너비. 시작 화면은 프로젝트 화면이다.

## 3. 진행(참가자당 약 30분)

1. 소개(2분): "제품을 시험하는 것이지 당신을 시험하는 것이 아닙니다. 생각을 소리 내어 말해 주세요."
2. 과제 1–3을 차례로 진행한다(과제당 최대 5분). 진행자는 답을 알려 주지 않는다. 막혀서 3분이 지나면 "어디를 보고 싶으세요?" 한 번만 묻는다.
3. 과제마다 끝나면 어렵기 점수(SEQ, 1 아주 어려움 – 7 아주 쉬움)를 받는다.
4. 사후 질문(5분)을 한다.

### 과제 1. 어제 작업 찾기

> "어제 '1.4 버전 노트'를 쓰는 일을 하다가 멈췄습니다. 그 일을 다시 찾아서, 마지막에 무엇을 결과로 받았는지 확인해 주세요."

- 성공: 3분 안에 해당 세션을 연다. 마지막 Run의 결과(작업 탭 Run 카드, 산출물 패널, 또는 실행 상세의 결과 보기)를 읽고 내용을 말한다.
- 부분 성공: 세션은 찾았지만 결과를 찾지 못했다. 또는 도움 질문 뒤에 성공했다.
- 볼 것:
  - 사이드바 세션 목록·검색과 프로젝트 전환 중 무엇을 썼는가.
  - 다른 세션이나 Run 화면을 잘못 연 횟수.

### 과제 2. 변경과 미반영 구분

> "이 세션에서 에이전트가 바꾼 파일은 무엇이고, 그중 아직 원본 폴더에 들어가지 않은 것은 무엇인가요? 원본 폴더에 원래 있던, 에이전트가 하지 않은 변경도 있다면 구분해 주세요."

- 성공: 다음 셋을 모두 말한다.
  - 세션이 바꾼 파일(변경 패널 또는 검토 화면).
  - 반영되지 않았다는 것(판단·반영 기록 없음, "원본 폴더에 반영" 전).
  - 원본 폴더의 별도 변경(검토 화면의 "원본 폴더(Git 작업 트리)" 범위, 또는 출처 "Corral 밖에서 바뀜").
- 부분 성공: 셋 중 둘만 말했다.
- 볼 것:
  - 검토함 표시나 승인을 반영으로 오해하는가.
  - "Corral / Corral 밖에서 바뀜" 출처 표시를 읽는가.

### 과제 3. diff 의견의 전달 대상 확인

> "notes 파일의 첫 줄에 '제목을 먼저 써 주세요'라는 의견을 남기고 수정해 달라고 보내 주세요. 보내기 전에, 이 의견이 누구에게 어떤 방식으로 전달되는지 말해 주세요."

- 성공: 다음을 모두 한다.
  - 줄 번호로 의견을 단다.
  - 보내기 전에 "보낼 곳"을 보고 전달 대상을 말한다. 실행 중이 아니면 "이 세션의 새 Run", 실행 중이면 "실행 중인 ○○"이다.
  - 보낸 뒤 세션 기록에서 그 요청을 찾는다.
- 부분 성공: 보내기는 했지만 대상을 말하지 못했다. 또는 보낸 뒤 결과를 찾지 못했다.
- 볼 것:
  - 의견 하나마다 바로 보내진다고 생각하는가(실제로는 묶어서 보냄).
  - 원본이 바로 바뀐다고 생각하는가.

### 사후 질문

1. 가장 헷갈렸던 화면이나 말은 무엇이었나요?
2. "세션", "작업 복사본", "반영"을 각각 자기 말로 설명해 주세요.
3. 비슷한 일을 하는 다른 도구와 비교해 이 흐름에서 빠진 것이 있나요?

## 4. 기록과 분석

- 기록: 참가자·과제마다 [결과 기록지](Workbench-Usability-Results.md)에 다음을 남긴다.
  - 결과(성공·부분·실패), 걸린 시간, 도움 질문 여부, SEQ.
  - 관찰한 문제를 화면 이름·행동·말로 적는다. 해석은 적지 않는다.
- 문제 심각도:
  - **치명**: 과제를 못 끝냄, 또는 잘못된 반영이나 전달로 이어짐.
  - **큼**: 도움이 필요했음.
  - **작음**: 망설였지만 스스로 해결함.
  - 같은 문제를 겪은 참가자 수를 함께 적는다.
- 다음 개선: 치명·큼 문제는 Workbench 플랜의 새 항목(CR 필요 여부 포함)으로 옮긴다. 화면 문구 문제는 메시지 파일에서 바로 고친다.
- 공개: 결과 문서에는 참가자의 개인정보·녹화·화면 속 개인 파일 이름을 넣지 않는다.
