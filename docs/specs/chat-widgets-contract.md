# 채팅 위젯 상세 계약

대화의 진행 정보와 필요할 때 여는 현황은 아래 배치 계약을 따른다. 실행 화면의 중앙·상세 역할은 [실행 기록 관찰](features/execution-monitor.md)을 따른다.

기본 대화 입구·입력창 배치는 [Workbench](workbench.md)를 따른다. 요청 옵션 팝오버는 없다. 아래 단계명은 계약 식별자이며 구현 순서나 새 작업 지시가 아니다.

## 1. 필수 화면 계약

### 1.1 배치

일반 대화 입구·요청 옵션은 [Workbench](workbench.md)를 따른다. 대화에는 상시 오른쪽 현황 열을 두지 않는다.

```text
프로젝트 ▾ / 세션 ▾ (/ 실행 ▾)   대화|파일|변경|실행 기록 · 실행 조작 알약·도구   한 줄 세션 헤더
대화 타임라인
  사용자 요청·답변
  결과·기록 진입점

컴포저 영역
  한 줄 상태: 끝난 실행 상태 · 계획 n/m · 변경 요약 · 현재 활동 · 현황 열기 · 새 요청에만 적용
    └ 펼치면 작업 계획(Todo)            입력창 바로 위
  대응 필요 알림(질문 제목) → 정확한 Run의 기존 질문/승인 영역으로 이동
  저장된 대기 요청(QueuedStack)
  기존 입력 DOM·팀·모델·권한·전송
```

Composer에는 끝난 실행의 상태·계획 n/m·변경 요약·현재 활동을 한 줄 상태로 두고(진행 중 상태와 조작은 상단 바의 실행 조작이 맡는다), 변경 요약은 카드에서 이동해 중복하지 않는다. 한 줄 상태를 펼친 Todo가 작업 계획을 읽는 유일한 곳이다. 대응 필요 알림은 기다리는 질문의 제목(둘 이상이면 첫 제목과 개수)을 보이고, 질문만 기다리면 정보 톤으로, 승인·실패·결과 미확인이 섞이면 경고 톤으로 그리며, 그 자리에서 답하지 않고 정확한 Run의 응답 영역으로 이동한다. 각 링크는 명시한 Run을 사용하며 같은 대상의 기존 결과/실행 선택은 보존한다. 다른 Run으로 이동할 때는 이전 Run의 하위 선택을 가져가지 않는다. 기존 Todo 본문·대응 필요 영역·Reins는 유지한다. 모델 선택에는 다음 요청임을 표시하며 실행 중 Instruction 모드 등 기존 노출 조건과 Ultra 제약을 바꾸지 않는다. 짧은 읽기 전용 상세는 기존 ContextInspector와 요약 팝오버를 재사용한다.

**현황**은 사용자가 입력창 근처의 버튼으로 여는 팝오버다. 현황의 항목이 여는 상세(컨텍스트·사용량·에이전트)는 같은 팝오버 안에서 목록 자리를 대신하며, 한 번에 한 면만 보인다. 돌아가기나 Escape는 그 상세를 연 항목으로, 다음 Escape는 현황을 닫고 현황 버튼으로 포커스를 돌린다. 대화와 입력창의 가운데 정렬·폭을 유지하고 빈 오른쪽 영역이나 자동으로 펼쳐진 요약 카드를 만들지 않는다. 진행 중에는 확인 필요 → 에이전트 진행 → 현재 결과·변경 → 컨텍스트·사용량 순으로 필요한 항목만 보인다. 종료된 실행은 현재 결과·변경을 먼저 보인다. 전체 작업 계획은 입력창 위 한 곳에서만 읽으며 현황에 같은 계획 항목을 반복하지 않는다. 실행 환경(시뮬레이션 등)은 모델 칩과 실행 화면에서 확인하고, 실제 모델이 없는 서버에서는 입력창 아래에 시뮬레이션 배지를 보인다. 확인 필요 요약은 미해결 질문·승인이 있을 때만 보이며, 정확한 Run의 기존 확인 영역으로 이동한다. 요약에서 승인·거절 명령을 보내거나 해결됨 상태를 별도로 저장하지 않는다. 현황의 각 항목은 기존 상세(ContextInspector, 요청별 사용량, 에이전트 상태·계획 선택)를 열고, 현재 열 수 있는 결과물은 실행 화면의 결과 읽기, 변경사항은 해당 실행의 diff로 연결한다. 해시·크기·설정 버전·런타임 기본값·연결 설명 같은 감사 정보는 실행 상세의 접힌 영역에 남는다.

표시할 실행이 있으면 **현황** 버튼은 대화의 모든 폭에서 접근 가능하다. 팝오버를 여는 것만으로 현재 실행·계획 선택·입력 대상이나 초안을 바꾸지 않는다. 닫기와 Escape는 열었던 버튼으로 포커스를 돌려준다.

사용량 상세는 끝난 호출의 보고된 입력 토큰과 캐시 입력, 그리고 두 값을 모두 보고한 호출 기준의 캐시 비율을 함께 보인다. 입력 토큰을 보고하지 않은 완료 호출 수를 따로 적어 알려진 합계의 범위를 드러내며, 모두 미보고면 입력 합계를 0으로 만들지 않는다. 캐시 입력을 보고하지 않은 호출은 0으로 세지 않고 보고 없음으로 따로 적는다.

현황 위젯은 가장 최근 실행이 아닌 실행을 골랐을 때만 그 실행 번호를 표시한다. 실행 번호는 세션의 생성 순서대로 1부터 부여하며 실행 선택기·상태 줄·결과 목록·`@` 메뉴가 같은 번호를 쓴다. 사용량의 대표 값은 해당 실행에서 보고된 출력 토큰이고, 상세는 보고된 입력과 캐시 입력을 구분한다. 캐시 입력은 입력의 일부이므로 총량에 다시 더하지 않는다. 결과 수는 결과 버전 수, 변경 수는 해당 실행 비교의 변경 파일 수이며 파일 쓰기 호출 횟수와 구별한다. 과거 실행 선택은 세션 누계의 범위를 바꾸지 않는다.

세션 하단 통계는 세션 누계임을 표시한다. 항목은 실행 수, 도구·에이전트 단계 수(각 실행의 주 에이전트 도구 작업과 하위 실행 수이며 모델 호출 수와 다르다), 보고된 입출력 토큰(종료한 모델 호출이 보고한 입력과 출력의 합이고 보고하지 않은 수치는 포함하지 않는다)이다. 항목 이름이 정의를 말하므로 따로 정의 문장을 두지 않는다. 시뮬레이션 표시를 유지하며 서로 다른 범위의 값을 일치시키려고 사용량 기록을 바꾸지 않는다.

세션 화면의 상단 한 줄(52px)은 왼쪽에 경로를, 오른쪽에 보기 전환·실행 조작·도구를 둔다. 경로의 각 항목은 메뉴를 여는 버튼이다. 프로젝트 항목은 프로젝트를 바꾸고, 세션 항목은 현재 프로젝트의 세션을 사이드바와 같은 순서(고정 먼저, 그다음 최근 갱신순)와 같은 상태 표시로 보여 고른 세션을 연다. 실행 기록을 보는 동안에만 세 번째 실행 항목이 붙어 세션의 실행을 번호·상태로 고르며, 이것이 실행 기록의 유일한 실행 선택기다. 열었던 세션을 별도 탭으로 남기지 않는다. 세션 이동은 경로의 세션 메뉴, 사이드바, 명령 팔레트, 그리고 데스크톱의 Mod+1–9로 한다. Mod+숫자는 같은 순서로 센 N번째 세션을 연다. 세션 제목은 경로의 세션 항목이자 접근 가능한 페이지 제목이며, 접힌 사이드바 진입점은 보존한다.

현재 작업의 문구가 Todo 헤더에 이미 보이면 RunActivityWidget은 동일 문구를 다시 반복하지 않고 실행 경과·기록 진입점만 제공한다. Todo가 접혀 있거나 없으면 활동 위젯에 현재 단계 요약을 표시한다. 승인 대기 같은 우선 상태는 ActionRequiredBar가 담당한다.

### 1.2 공간과 상호작용

- 실행 요약은 명시적으로 연 현황 팝오버에서 확인한다. 알 수 없음 카드 여러 개를 기본 화면에 쌓지 않는다.
- Todo와 입력창은 같은 콘텐츠 폭과 좌우 기준선을 사용한다. 단일 외곽선과 얕은 배경 단계로 묶으며 중첩 테두리·그림자를 반복하지 않는다.
- Todo의 행·높이는 실제 콘텐츠·확대·키보드 조건에서 조정한다. 초기 계획의 시작값을 검증된 제품 상수로 고정하지 않는다.
- 기본 Todo는 최대 5개 행을 읽을 수 있게 보여준다. 더 긴 계획은 완료 수와 전체 목록 진입점을 유지하고 전체 보기에서 제한된 높이의 스크롤을 제공한다.
- Todo 항목의 텍스트 줄바꿈을 허용한다. 사용자가 보고 있는 항목을 이벤트마다 정렬·삭제·자동 스크롤하지 않는다.
- 넓거나 좁은 폭 모두 같은 현황 진입점을 유지한다. 폭이 좁다는 이유로 정보를 제거하지 않는다.
- 낮은 화면·200% 확대·가상 키보드에서는 Todo를 요약형으로 시작할 수 있지만, 키보드로 모든 계획에 접근할 수 있어야 한다. 미해결 승인·오류와 전송 컨트롤을 가리지 않는다.
- viewport 위에 임의 fixed overlay를 얹지 않는다. 기존 flex/grid 안에서 공간을 확보하고 타임라인의 실제 가용 높이를 측정한다.

### 1.3 상황별 위젯은 허용된 종류에서 결정적으로 선택

위젯 종류·표시 여부는 Corral의 검증된 이벤트와 selector가 정한다. 모델이 HTML/JSX를 생성해 실행하거나 임의 UI 명령으로 권한을 변경하는 구조가 아니다. 사용자에게 적절한 위젯이 보인다는 것은 현재 데이터와 작업 상태에 맞는 미리 정의된 표현이 활성화된다는 뜻이다.

## 2. 표현 경계

이 절은 표현 동작의 계약이다. 컴포넌트 이름·위치는 현재 Studio 소스를 확인하며 과거 계획의 이름으로 새 컴포넌트를 중복 생성하지 않는다.

- 게이지와 분절 막대는 표시 전용이다. 고정 모델 목록, 고정 창 크기, 샘플 토큰, input/output/cache 합산으로 비율을 만들지 않는다. 기존 모델 선택 컨트롤을 대체하지 않는다. 같은 요청의 추정값으로 링·범례가 갱신되고 트리거로 상세가 열린다.
- 진행 중에도 사용자가 접을 수 있다. auto/open/closed 선호와 실행 상태를 분리하고, 완료 후 auto만 축약한다. 헤더는 공용 Button과 disclosure다. 접힌 본문은 키보드·접근성 트리에 남지 않는다. 비공개 추론 원문을 요구하지 않는다.
- 활동 표시는 Corral 토큰을 쓴다. 실행 상태에 따라 정지·진행이 바뀌고 reduced motion에서는 정적이다.
- Todo는 입력창 위의 형제 영역이다. 입력 DOM과 다음 요청 컨트롤은 유지한다. 샘플 retry, localStorage queue, 별도 전송 shortcut은 넣지 않는다.
- 좁은 폭은 채팅 컨테이너 기준이다. 스크롤 소유자는 기존 ChatView다. Todo나 헤더 높이가 바뀌어도 과거 anchor와 최신 추적을 각각 유지한다.
- 기존 Button, Popover, Dialog와 Corral의 색·타이포그래피·reduced motion을 쓴다. 새 폰트, 음원, Electron 코드, 패키지는 추가하지 않는다.

## 3. 현재 실행·오른쪽 탐색·다음 요청 분리

### 3.1 대상

| 대상 | 소유 정보 | 변경 계기 |
|---|---|---|
| presentationRunId | 실행 요약 위젯·현재 Todo·활동 표시 | 현재 세션의 확정된 활성 Run. 없으면 마지막 실행 |
| inspectedRunId / selectedResultId | 실행 화면의 조회 대상 | URL과 사용자 탐색 |
| composerDraft | 다음 본문·모드·모델·추론·첨부·시작 기준 | 사용자 입력·명시 설정 변경 |

과거 결과를 열어도 presentationRunId나 composerDraft를 바꾸지 않는다. 마지막 실행을 보여줄 때는 마지막 실행 기준임을 표시한다. 빈 세션에 과거 컨텍스트를 가져오지 않는다. 다른 세션에만 활성 실행이 있는 경우 현재 세션의 진행 위젯으로 표시하지 않는다. 결과물 위젯의 링크와 개수는 [API의 산출물 수명 계약](api-contract.md)에 따라 현재 본문을 열 수 있는 결과만 포함한다. 해제된 자료의 관계 정보는 실행 흐름에 남는다.

현재 세션이 실행 중이면 새 입력의 기본 목적은 대기열이다. 에이전트를 열어보거나 활성 실행 목록이 바뀌는 것만으로 지시 모드나 지시 대상을 선택하지 않는다. 사용자가 명시적으로 지시를 선택하면 대상과 전달 시점을 표시한다. 입력 중 고정한 대상이 종료되면 다른 대상으로 대체하지 않고 전송을 막으며 초안을 보존한다.

지시 모드도 같은 입력 DOM과 한 곳의 작업 계획을 사용한다. 입력창을 에이전트 상세·도구 기록·지시 이력 패널로 다시 감싸지 않는다. 빈 지시 이력과 전달 의미의 장문 설명을 기본 화면에 반복하지 않으며, 실제 지시 상태와 근거는 해당 실행의 Reins 상세에서 접근한다. 대상, 적용 시점, 전송 거절·오류·복구 행동은 입력창 가까이에 유지한다.

새 요청 전송 클릭만으로 현재 Todo를 지우지 않는다. 새 Run 생성이 확정되면 전환하고, 생성 실패 시 초안과 마지막 계획을 보존한다. 원래 실행의 결과 카드 또는 기록에서 해당 과거 계획으로 접근할 수 있어야 한다.

### 3.2 store와 구독

현재 useCorralRun은 호출별로 createRunSession을 만든다. 위젯마다 이 훅을 부르면 구독과 읽기 상태가 늘어날 수 있다. 현재 실행은 하나의 소유 store를 공유하고, 실행 요약 위젯·Todo·활성 RunMessage는 목적별 selector로 읽는다. SessionPage의 기존 store 소유권을 먼저 확인해 재사용한다.

과거 실행을 보는 store는 현재 실행의 open(runId)를 갈아끼우지 않는 별도 읽기 대상으로 둔다. 같은 runId를 두 영역에서 읽을 때의 재사용과 transport/프로젝트/세션 경계를 명시하고, 구독 해제는 실제 소유자가 담당한다. 전역 상태 관리 전체 교체로 확대하지 않는다.

위젯별 새 SSE·interval polling을 추가하지 않는다. 요청 기록과 WorkPlan bodyRef 변경 시에만 필요한 참조를 로딩한다. 스트리밍 토큰마다 전체 이벤트를 스캔하거나 private 본문을 다시 파싱하지 않는다.

## 4. 실행 요약 위젯 명세

### 4.1 표시 조건

| 위젯 | 표시 조건 | 기본 내용 | 클릭 |
|---|---|---|---|
| 컨텍스트 사용량 표시(현황 위젯) | 현재/마지막 실행에 기록 또는 측정 상태가 있음 | 전체 요청 추정이 가능하면 약 N%; 메시지만 있으면 메시지 약 Nk | ContextInspector |
| 에이전트 활동 표시(현황 위젯) | 진행 중인 에이전트, 다중 에이전트, 위임, 또는 사용자가 추적해야 하는 에이전트 대기 | 현재 시도 기준 전체 수와 작업/대기/실패 수를 구분 | 역할별 실행 상태·계획 선택 |
| RunChangesChip | 작업 사본·변경 기준이 적용됨 | 이번 실행 변경 수와 알려진 줄 수 | 같은 실행·tree 범위의 diff |

일상적인 단일 에이전트에서 Assistant 1개·프로필 1개·모델 호출 0개·진행 없음은 별도 카드로 표시하지 않는다. 모델 연결 등록 수를 연결 정상 상태 또는 활성 에이전트 수로 표시하지 않는다.

측정이 없는 컨텍스트 사용량 표시는 숫자 대신 컨텍스트 정보/측정 전 등 작은 중립 트리거로 제공한다. 전체 요청의 동일 기준 사용량과 유효 창이 있을 때만 디자인킷 Meter를 보인다. 부분 측정이나 분모가 없는 상태에 0% 막대를 만들지 않는다. 사용량은 실제 보고된 완료 호출별 출력 토큰이 둘 이상일 때만 디자인킷 Sparkline으로 보조 표시하고, 상세의 입력·캐시·출력과 미보고 구분은 유지한다. 실제 runtime에서 측정 가능한데 구현하지 않은 상태를 영구적인 미지원으로 분류해서는 안 된다. 로딩·미지원·오류·부분 측정은 상세에서 이유를 구별한다.

현황의 확인 필요는 원본 Banner·BannerTitle·BannerActions, 에이전트 진행은 AgentCard·AgentIdentity·AgentStatusLabel, 결과·변경은 CardGroup의 inline 행으로 구성한다. 에이전트 수와 상태는 task별 현재 시도를 기준으로 하며 이전 실패 시도를 현재 실패로 중복 계산하지 않는다. 컨텍스트·사용량은 원본 Card·Meter·Sparkline의 작은 요약으로 구성한다. 입력창 위 계획은 AgentSteering의 계획 행(완료·진행·대기 글리프와 제목)을 사용한다. AgentMonitor의 실행 제어나 DecisionInbox의 낙관적 응답 상태를 복제하지 않는다. 원본에 없는 범용 Popover는 기존 Corral 어댑터를 재사용한다. 과거 본문이 해제된 산출물은 결과 링크에서 제외하되 실행 화면의 관계 정보는 유지한다.

### 4.2 ContextInspector의 정보 계층

상단: 대상 실행·에이전트·모델, 전체/부분 측정 구분, 마지막 요청 시점.

본문: 사용량 / 유효 창, 분절 막대, 같은 기준으로 계산한 구성별 행.

하단: 정책에서 확인된 출력 예약·압축 임계치와 현재 compact 상태, 기존 명시적 compact 조작 또는 해당 상세로 가기.

구성별 후보 행은 아래와 같다. 실제 포함된 항목과 측정 근거가 있을 때만 수치를 제공한다.

| 범주 | 산정 대상 |
|---|---|
| Messages | 사용자·assistant·tool 결과 등 실제 포함된 대화. system 영역은 제외 |
| System prompt | 시스템 본문 중 별도 집계한 스킬·파일·서버 지시문 등을 제외한 부분 |
| System tools | 이번 요청에 포함된 내장 도구 정의 |
| MCP tools | 이번 요청에 실제 포함된 MCP 도구 정의 |
| Skills | 실제 로드되어 요청에 포함된 스킬 본문 |
| Memory / instruction files | 실제 요청에 포함된 지침·메모 파일. 파일 존재만으로 집계하지 않음 |
| MCP server instructions / agent instructions | 실제 포함된 해당 지시문. 다른 범주와 중복되지 않음 |
| Other / unclassified | 동일 산정 방식으로 측정되지만 출처가 분류되지 않은 부분 |

활성 도구 개수와 도구 호출 횟수는 다른 값으로 표시한다. deferred 목록은 현재 runtime이 실제로 지연 로딩 상태를 제공하는 경우에만 별도 행에 두며 활성 점유량에 더하지 않는다. disabled/unloaded를 임의로 deferred라고 부르지 않는다. Since last update는 전체의 일부인지 추가 추정인지 명확한 데이터가 없으면 제공하지 않는다.

### 4.3 컨텍스트 데이터 공급도 필수 구현 범위

기존 `contextEstimate`는 메시지 추정(`pi-1.3.0-messages`)이며 전체 요청 측정이 아니다. `contextUsage`는 별도 선택 필드다. 조립 추정·최종 provider payload·legacy 메시지·부분/오류를 구분하고, 최종 hook 증거 없이 전체 비율로 승격하지 않는다. 타입·기록은 현재 contracts와 두 runtime의 request-record 경로를 따른다.

데이터 공급은 다음 계약을 유지한다.

1. 요청 조립 지점에서 실제 messages/system sections/tool schema의 출처를 구조적으로 수집한다. 최종 payload hook 이후 포함 범위를 대조한다. 본문 키워드로 출처를 추측하지 않는다.
2. 같은 기준의 추정기를 사용해 범주별 추정량을 만든다. provider가 확인한 입력 usage는 별도 측정 기준으로 보존하고 추정 breakdown과 섞어 맞추지 않는다. 한국어·일본어·도구 JSON·첨부가 포함된 fixture에서 한계를 기록한다.
3. context usage snapshot에 최소한 runId, executionId, attemptNo, modelCallId, 기록 시점, 적용 컨텍스트 창, method, coverage, completeness, 구성별 수치/누락 이유를 결합한다. 전체인지 메시지 전용인지 타입으로 구분한다.
4. 계측 본문은 기존 private record/참조 경로를 우선 확장한다. 공개 이벤트에는 필요한 참조·집계만 둔다. 키·원문 프롬프트·메모 본문·로컬 경로를 새 public 로그로 내보내지 않는다.
5. 기존 model.request_recorded 등의 계약에 optional/versioned 필드를 추가할 필요가 있으면 명세·schema·생성 계약·replay 테스트를 함께 갱신한다. 과거 이벤트·snapshot·hash를 재작성하지 않는다.
6. 현재 두 runtime(pi-core/pi-sdk)을 연결한다. 지원하지 않는 provider payload 표현이나 미측정 이미지·도구 확장이 있으면 부분 측정으로 명시하고 전체 비율/정확한 free space를 표시하지 않는다.
7. 계측 실패는 미측정/오류로 전달한다. 위젯 때문에 추가 LLM 호출을 만들거나 permit·기존 검증을 건너뛰지 않는다. 기존 보호·권한 검증 실패와 계측 실패를 혼동하지 않는다.

### 4.4 수치 불변식

- usedTokens는 동일 요청·같은 측정 기준에서 서로 겹치지 않는 범주를 합한 값이어야 한다.
- 대화 안에 이미 들어 있는 스킬·지침을 system prompt 전체와 다시 합산하지 않는다.
- 누적 usage나 여러 모델 호출의 토큰 합을 단일 컨텍스트 점유량으로 쓰지 않는다.
- input/output/cache 토큰을 무조건 합산하지 않는다.
- 출력 예약은 점유한 입력과 분리해 표시한다. 예약의 정의·적용 범위가 확인되지 않으면 free space 계산에서 빼지 않는다.
- 전체 범위가 추정 가능하고 유효 창이 알려졌을 때만 약 N%와 추정 잔여 공간을 표시한다. 막대 렌더는 범위를 제한하되 수치 초과 자체를 숨기지 않는다.
- context window는 해당 Run/호출의 고정 snapshot에 따른다. 다음 요청의 모델 선택을 바꿔 과거 요청 분모를 바꾸지 않는다.
- compact 성공 receipt만으로 사용량 감소를 그리지 않는다. 새 snapshot 전까지 이전 요청 기준·갱신 대기임을 표시한다.
- 역할별 모델이 다른 Run은 execution별 분모가 다르므로 가상 합산 창을 만들지 않는다. 표시하는 비율의 대상 에이전트와 미측정 수를 함께 밝힌다.

### 4.5 변경사항

RunChanges와 기존 비교 범위를 재사용한다. 실행 중에는 잠정 값, 종료 후에는 해당 Run의 고정 tree 기준임을 구별한다. 기준 없음·조회 실패·미집계·바이너리를 0개 변경으로 처리하지 않는다. 위젯 조회 자체가 snapshot 생성이나 파일 수정을 일으키면 안 된다. diff를 열 때 run/scope/from/to를 보존한다.

## 5. ComposerWorkPlan: 실제 진행되는 Todo

### 5.1 새 Todo 저장 엔진은 만들지 않음

기존 update_plan → Coordinator → projection.workPlans → private bodyRef → WorkPlan 파싱 경로를 재사용한다. 현재 WorkPlan 상태는 pending/in_progress/completed이며 항목 수는 1–20개, 계획 하나의 in_progress는 최대 하나다.

WorkPlanPanel의 본문 로딩·검증을 공용 useWorkPlanSnapshot/selector로 추출하고 새 Dock과 전체 상세가 동일 결과를 사용하게 한다. UI가 임의로 완료 상태를 저장하지 않는다.

### 5.2 시각 상태

| 데이터 상태 | 표현 |
|---|---|
| pending | 점선 원 또는 비활성 원 + 예정이라는 접근 가능한 상태 이름 |
| in_progress | 진행 원/작은 활동 표시 + 강조된 현재 항목 |
| completed | 체크가 있는 원 + 낮은 대비의 완료 항목 |
| 실행 실패/취소/승인 대기 | 계획 항목 enum을 바꾸지 않고 실행 상태를 별도 배너로 표시 |

체크 표시는 읽기 전용이다. 클릭 가능한 checkbox로 완료시킬 수 있게 하지 않는다. 리스트는 안정적인 item.id로 갱신하고 항목의 완료만 바뀌면 해당 행과 카운트만 바뀐다.

2/7은 계획 항목 완료 수이며 전체 실행 시간의 28.6%라는 뜻이 아니다. 남은 시간을 추정하지 않는다. 새 계획에서 항목 수가 늘어 완료 비율이 내려가는 것은 정상이며 가짜 단조 증가를 만들지 않는다.

### 5.3 상태 전환 계약

| 상태/사건 | 동작 |
|---|---|
| 간단한 요청, 계획 없음 | Todo를 표시하지 않음. 일반 실행 상태는 활동 위젯에서 확인 |
| 계획 참조 도착, 본문 로딩 | Todo 슬롯에 로딩 상태 표시 |
| 유효한 계획 최초 수신 | 기본은 접힘. 한 줄 상태에 완료 수/전체 수와 지금 단계를 보인다. 펼침은 사용자가 고른다 |
| revision 갱신 | 현재 항목·완료 수 갱신. 수동 펼침 선택 유지 |
| 유효 본문이 늦게 도착 | 최신 참조와 맞는 본문만 적용. 이전 본문은 명시적으로 이전 revision 표시 |
| 모든 계획 완료, Run 진행 중 | 계획 N/N · 실행 중 |
| Run 성공, 계획 일부 예정 | 실제 완료 수를 보존하고 실행 종료와 미완료 항목을 구분 |
| 성공 종료 | 요약형 한 줄. 수동 open은 유지 |
| 실패/취소/입력 대기 | 실행 상태 노출, 마지막 실제 계획과 부분 결과 접근 보존 |
| 오래된 criteria/attempt | 이전 기준임을 표시하고 현재 유효한 검증으로 취급하지 않음 |
| 새 Run 생성 확정 | 새 대상 계획으로 전환. 입력 DOM은 유지, 이전 계획은 기록에 보존 |

선호 키는 session/run/scope/owner/attempt 단위로 구성하고 auto/open/closed를 분리한다. 같은 계획의 revision이 바뀌었다고 초기화하지 않는다. 탭을 다시 열었을 때도 사용자 선택을 같은 정책으로 복원한다.

### 5.4 계획 발행 경로: 위젯만 만들고 끝내지 않음

현재 autoDefinition은 각 역할의 allowedCollaborationTools에 update_plan을 이미 추가한다. 이 권한을 활용하되 기존 사용자 저장 역할을 자동 수정하지 않는다.

- 여러 단계의 구현·조사·검증 작업에서는 해당 실행의 첫 실질 작업 전과 의미 있는 단계 전환 시 기존 update_plan을 사용하도록 공개 작업 규약을 보완한다.
- 필요할 때만 계획을 만든다. 모든 인사·짧은 질문에 같은 3단계 계획을 강제하지 않는다.
- UI에서 자연어 체크박스를 파싱하거나 도구 호출 횟수·시간 지연으로 항목을 체크하지 않는다.
- 테스트용 script는 실제 host.invokeTool(update_plan) 경로로 revision을 만들고 Coordinator 이벤트를 UI가 받아야 한다. setState로 가짜 진행을 주입한 Storybook만으로 완료하지 않는다.
- 실제 LLM의 계획 발행 여부는 별도 opt-in·기존 한도 내 smoke로 확인한다. 일반 CI는 결정적 fixture를 사용한다. 실제 LLM이 계획을 발행하지 않은 경우 UI에 가짜 계획을 생성하지 않는다.
- 검증 필수 항목은 기존 Coordinator의 run_check immutable evidence 검증을 따른다. artifact 존재·model 완료·submit_result 성공으로 대체하지 않는다.

### 5.5 팀 계획의 정적 소유자 문제

이번 수정에서는 **팀 계획이 존재한다는 이유만으로 항상 팀 계획을 우선하지 않는다.** 현재 팀 계획은 planOwnerRoleId와 첫 소유 execution에 묶인다. 그 planner가 종료한 뒤 worker가 수행하는 단계가 팀 체크리스트에 자동 반영된다고 가정하면 화면이 정적으로 남을 수 있다.

- 기본은 현재 작업을 수행하는 execution의 유효 계획을 보여준다. 단일 실행에서는 선택기 없이 표시한다.
- 복수 실행에서는 역할별 선택기를 제공한다. auto-follow는 정해진 기준으로 선택하고, 이벤트가 가장 최근에 왔다는 이유로 역할을 계속 바꾸지 않는다.
- 사용자가 역할을 선택하면 종료·재시도에도 대상과 상태를 분명히 보여주며 수동 선택을 조용히 바꾸지 않는다. auto-follow 복귀는 별도 조작이다.
- 팀 범위 계획은 선택 가능한 상위 계획으로 제공한다. 소유자가 종료했다면 마지막 팀 계획임을 표시한다. 실행별 완료 수와 더하지 않는다.
- 라이브 팀 계획을 기본으로 승격하려면 해당 소유자의 실제 갱신 수명주기가 검증되어야 한다. writer가 planner 대신 팀 계획을 갱신하도록 권한을 우회하거나 UI에서 task 완료를 끼워 넣지 않는다.
- 팀 생성용 TeamPlan과 작업 checklist WorkPlan, 도메인 TaskBoard는 구별한다.

## 6. 실행 활동과 대응 영역

### 6.1 RunActivityWidget

현재 실행의 진행 상태는 입력창 근처의 단일 활동 위젯이 담당한다. 계획이 없을 때도 작동한다. 표시 우선순위는 사용자 응답 필요 → 실패/불명확 효과 → 현재 도구/계획 단계 → 실행 중 일반 상태다. 정확한 단계가 없으면 작업 중이라고 표시하며 검증 중 등 구체적 단계를 추측하지 않는다.

실행 경과는 기록된 시작·종료 시각에 근거한다. 단계 시작 시각을 알 수 없으면 전체 경과를 단계 경과로 표시하지 않는다. 종료 후에는 경과가 계속 증가하지 않는다.

입력창 근처의 활동 영역은 실행 대상과 대응·지시 제어를 담당하고, 전송 후 RunMessage는 관측된 작업 과정을 보여준다. 도구 원문은 작업 단계의 명시적인 상세 펼침에서 기존 도구 호출 컴포넌트로 읽는다. 실행이 끝나면 해당 차례 아래에 접힌 작업 기록이 남는다.

### 6.1a 대화 차례의 작업 과정

세션 대화의 한 차례는 사람의 메시지, 디자인킷 ThinkingSteps 작업 과정 묶음 하나, 답으로 보인다. 답은 항상 대화에 그대로 보이며 결과 버전 머리글·차례별 상태 배지·Run → 에이전트 → 대화 → 모델 호출로 이어지던 중첩 접힘은 대화 흐름에서 빠진다. 측면 창과 실행 화면은 현재 결과와 생성·전달·판단 관계를 보여준다. 본문 보관은 [본문 수명 계약](api-contract.md#산출물-본문-수명)을 따른다.

작업 과정은 원본 ThinkingStep의 아이콘·연결선·설명과 ThinkingStepDetails·ThinkingStepSources를 조합한다. 첫 model.request_prepared부터 모델 요청 행을 표시하고, 실제 dispatch·완료 기록으로 준비·응답 생성·완료를 구분한다. Manual [추론 판정](features/effort-routing.md)을 거친 요청은 그 판정 한 줄을 행에 바로 보이고 상세는 그 줄에서 연다. 판정을 거치지 않은 요청(Off·고정 수준·공급자 기본값·요약 정책)의 추론 기록은 요청 상세에 둔다. 일반 응답 첫 줄이나 추론 노력 설정을 모델의 생각 본문으로 재분류하지 않는다. 도구는 호출 ID별 이름·상태와 관측된 대상을 표시하고 상세에서 기존 ExecutionToolGroup으로 인자·결과를 읽는다. 결과 읽기는 해당 실행 기록에서 정확히 식별한 결과 버전의 이름과 버전을 표시한다. 알 수 없는 대상 식별자를 다른 결과나 최신 버전으로 대체하지 않으며 원래 식별자는 감사 기록에 보존한다. 자료 칩은 실제 입력·결과 참조만 표시하며, 이미지도 기록된 현재 자료가 있는 경우에만 제공한다. 다른 에이전트는 이름·상태와 해당 실행의 도구 상세를 보인다. 답을 게시하는 write_artifact/submit_result와 Coordinator가 대신 부른 호출은 작업 행이 아니다. 단계 수는 기존 도구·다른 에이전트 수를 유지한다.

실제 작업 중인 요청·도구·에이전트만 활성 모션을 사용한다. 일시정지·승인 대기·실패·취소는 상태 문구로 구분하고 작업 중인 것처럼 흐르지 않는다. 처음부터 관측되지 않은 미래 단계를 만들어 채우지 않는다. 끝나면 관측 시간·단계 수 아래에 접히며 한 번 눌러 펼친다. 모델 요청만 있는 차례도 기록된 요청 상태는 확인할 수 있다. 사건을 불러오지 않은 지난 차례의 머리글은 projection에서 같은 단계 수와 시간을 계산한다. 실행 중 흐르는 글은 리드의 일반 응답만 보이며 작업 과정과 별도로 이어진다. 해제된 응답·산출물 본문을 작업 상세에서 복원하지 않는다.

입력창 아래에는 세션의 실행 수 · 도구·에이전트 단계 수 · 보고된 입출력 토큰 · 캐시 적중률을 한 줄로 보인다. 입력창이 좁으면 항목 사이에서만 줄을 바꾸고 항목을 자르거나 빼지 않는다. 그 줄에 안내 문장을 덧붙이지 않으며 펼치는 조작이 없다. 캐시 입력을 보고한 호출이 없으면 0%가 아니라 "캐시 보고 없음"이라고 적는다. 입력창의 후속 작업/질문 선택기는 없어지고 질문은 보통 메시지로 보낸다. 팀 선택기는 모델 선택기와 같은 칩이며 "팀 없음"(기본) 아래에 "Corral" 묶음으로 auto, 저장된 Corral들, "Corral 만들기·관리"(프로젝트의 Corral 목록으로 이동)를 나열한다. 팀 없음/auto 선택은 세션별로 이 브라우저에 기억되고, Corral 선택은 세션의 Corral 설정이다. 다음 차례부터 적용된다. 요청 옵션 팝오버는 없다. Ultra·검토만·검증 범위·작업 방식·역할별 모델/방식·설계 템플릿을 입력창에서 고르지 않는다. 텍스트·이미지 첨부는 `+` 메뉴, 프로젝트 파일은 `@` 참조로 넣으며, 지침·메모리 첨부는 [Workbench의 명시 선택·버전 고정 계약](workbench.md#기본-입구)을 따른다. 보낸 텍스트 첨부는 이름과 크기를 먼저 표시하고 전체 내용 해시·출처·원문은 같은 첨부의 접힌 상세에서 확인한다.

실행이 성공했어도 실패한 도구 단계가 있으면 두 사실을 함께 설명한다. 대응 배너는 실패한 도구의 실행을 열고, 해당 실행 상세에는 실패한 단계와 안전한 사유를 표시한다. 도구 효과가 취소로 확정된 단계는 사유 문자열이 있어도 취소로 안내하고 실패 목록·실패 이동 대상에 포함하지 않는다. 전체 실행의 취소는 그 전에 실제로 실패한 도구 단계의 표시를 바꾸지 않는다. 실패·취소를 성공으로 바꾸거나 기록된 사용량을 바꾸지 않는다. 종료된 대상에 대한 명령 거절은 사람이 읽는 안내를 먼저 보이고 코드·명령 식별자는 접힌 진단에 남긴다. 요청별 사용량은 작성 역할과 요청 순번 또는 이미지 생성 동작을 먼저 표시하고 내부 호출 식별자는 접힌 진단으로 제공한다.

### 6.2 도구와 모델 원문

도구 라이프사이클은 toolCallId 기준 한 행을 갱신한다. 동일 도구 이름이라도 별개 실행·재시도·별도 호출은 병합하지 않는다. blocked/failed/cancelled/unknown은 정상 완료와 구분한다.

ExecutionTranscript의 원문은 모델 호출 N · 응답 원문으로(N은 사건 순번이 아니라 그 실행의 요청 순서) 기본 접힘 처리하는 compact 표시 모드를 제공한다. 전체 실행 페이지의 상세 접근은 유지한다. 문자열 같음을 근거로 감사 기록을 삭제하지 않는다.

### 6.3 ActionRequiredBar

승인·질문·실패·복구 필요·불명확한 결과는 일상적인 실행 정보 disclosure와 분리한다. 불명확한 결과는 결과를 모르는 효과, 기록에 남은 미확인 사용량, 확인되지 않은 종료를 구분해 각각의 원인으로 표시한다. 모델 요청의 미확인 결과와 파일·도구 등 다른 작업의 미확인 결과도 구분한다. 모델 요청만 미확인인 경우 파일 변경이 불명확하다고 표시하지 않는다. 화면의 표시는 기록된 사용량이나 효과의 실제 상태를 바꾸지 않는다. 대기 수와 의미 있는 질문/오류 요약 및 기존 대응 UI를 여는 동작을 제공한다. 미해결 항목은 사용자가 다른 결과를 보고 있어도 발견 가능해야 한다. 대화의 접근성 알림은 현재 보고 있던 실행의 시작·대기·종료 상태 전환을 알리며, 과거 실행을 처음 여는 것과 반복된 같은 상태·경과 시간 갱신은 새 완료 알림으로 취급하지 않는다.

한 질문 요청에 질문이 둘 이상이면 InteractionPanel은 질문을 단계로 보인다. 진행 n/m과 이전·다음으로 오가고, 마지막에 모든 답을 한눈에 보는 검토 단계에서 보낸다. 단계 이동과 검토는 답을 보내지 않으며, 보내기 한 번이 기존 명령·receipt 경로로 모든 답을 함께 보낸다. 질문마다 native fieldset을 유지하고 응답 중에는 비활성으로 둔다. 숫자키로 답을 확정하지 않는다. 질문이 하나면 지금처럼 한 화면이다. 기존 ApprovalPanel/InteractionPanel의 명령·receipt 경로를 재사용한다. 동일 승인에 두 독립 제출 컨트롤을 만들지 않는다. 활성 실행의 대응과 오른쪽에서 살펴보는 다른 실행의 대응은 scope를 명시한다. 성공 receipt 이전에 대기가 사라지면 안 된다. 닫기/Escape는 거절·취소·재개가 아니다.

단순히 run.status가 failed/cancelled라는 이유로 모든 진단을 강제 펼치지 않는다. 미해결·대응 필요 정보를 노출하고, 전체 기록은 선택적으로 확인하게 한다.

## 7. 오른쪽 패널·결과·설정·데모 정리

### 7.1 결과 읽기와 실행 상세

선택 결과의 중앙 읽기와 오른쪽 단일 대상 상세는 [실행 기록 관찰](features/execution-monitor.md)을 따른다. 결과 본문 아래에 전체 실행 상세를 다시 쌓지 않는다. 선택 대상·버전·실행 식별자는 유지한다.

결과 보기에서 선택 결과가 없으면 사용 가능한 결과 목록 또는 실제 pending/partial/none 상태를 보여준다. 존재하지 않는 explicit result ID를 최신 결과로 조용히 대체하지 않는다. URL 직접 진입·뒤로 가기·전체 실행 상세 이동 시 대상 파라미터를 보존한다.

RunStatusCards의 데이터 로딩은 위젯 selector와 공유하고, 상세 내용은 재사용한다. 이름만 바꾼 기존 네 개 details를 상단에 통째로 옮기지 않는다.

### 7.2 결과와 상태

현재 Output 기반 final/partial 결과 판정을 유지한다. 마지막 모델 응답을 자동 최종 답변으로 승격하지 않는다. 결과 본문이 늦게 로딩되면 실행 종료와 로딩 상태를 함께 보여주며 실패 시 같은 대상 재시도를 제공한다.

같은 실행의 같은 결과 버전은 목록과 `@` 메뉴에 한 번만 보인다. 이름이 같은 별도 결과나 버전은 합치지 않으며 실행 번호·작성 에이전트·에이전트 실행 순번으로 구별한다. 내부 실행 식별자는 상세 정보로 남긴다.

같은 화면의 헤더가 실행 상태를 이미 설명할 때 embedded ResultReader의 실행: 성공 반복을 제거한다. standalone 결과는 필요한 실행 맥락을 유지한다. 검토·제출·파일 반영 상태는 별개의 의미로 남기되 기본 화면에 무조건 상태 목록을 늘어놓지 않는다.

채팅과 사용자가 명시적으로 연 결과 화면이 같은 본문을 보여주는 것은 허용한다. 결과를 열었다고 보존된 채팅 본문을 자동 접거나 위치를 바꾸지 않는다.

### 7.3 과거 설정과 다음 설정

EntryCard의 당시 설정은 실행 snapshot 기반 접힌 실행 설정으로 제공한다. 입력창의 선택은 다음 요청을 뜻한다. 실행 요약 위젯에서 실제 실행 모델을 확인할 수 있지만 그곳에서 다음 요청 모델을 편집하지 않는다. 시뮬레이션·시작 버전·파일 작업 범위 같은 중요한 차이는 다음 요청 근처에 남긴다.

### 7.4 데모

새 demo reply는 진단과 입력 전체를 결과에 이어 붙이지 않는다. 이전 버전 본문은 필요한 입력으로 보존하되 결과에 통째로 재귀 인용하지 않는다. 기존 testkit defaultReply의 전달 관찰 시험은 보존하고 데모 reply/appendNotes/script 옵션으로 분리한다.

데모에서 계획 생성·진행·완료를 보여주는 전용 결정적 시나리오를 제공한다. 컨텍스트 수치 fixture를 사용할 때는 시뮬레이션임을 표시하며 실제 모델의 측정값으로 주장하지 않는다. 실제 요청을 수행하지 않은 데모가 파일을 검증·배포했다고 답하지 않게 한다.

SafeMarkdown에 role prompt 등 문자열 삭제 정규식을 넣지 않는다. 과거 산출물·private 원문·snapshot·hash를 조용히 다시 쓰지 않는다.

## 8. 비동기·입력·접근성·성능

- WorkPlan은 run 문맥, scope, executionId, attemptNo, revision, criteriaVersionId, bodyRef/hash의 현재 참조와 일치해야 표시한다. 이전 revision의 늦은 응답·다른 Run 오류가 현재 화면을 덮지 않는다.
- 컨텍스트 snapshot도 modelCallId/attempt와 측정 기준을 고정한다. 같은 모델을 썼다는 이유로 다른 execution 수치를 가져오지 않는다.
- 화면 전환 시 이전 로딩의 성공·실패 모두 stale 결과로 배제한다. 재시도는 선택 대상에 묶는다.
- 기존 ChatView의 session anchor/offset과 40개 초과 가상화를 유지한다. 새 scroll hook을 나란히 설치하지 않는다.
- 타임라인 콘텐츠뿐 아니라 위젯·Todo·입력창의 높이와 실제 viewport 변화를 감지한다. 과거를 읽는 중에는 entryId+offset을 유지하고, 최신 추적 중에는 끝 위치를 유지한다.
- Todo 갱신·팝오버 열기·세션 상태 갱신으로 입력 DOM을 재마운트하지 않는다. 초안·커서·선택·한국어/일본어 IME와 기존 Enter/Shift+Enter 규칙을 보존한다.
- 원형 상태는 색 외에도 아이콘 형태·상태 이름을 가진다. 읽기 전용 Todo는 조작 가능한 체크박스로 위장하지 않는다.
- disclosure와 Popover는 버튼, aria-expanded, 제어 영역 연결, Escape, 포커스 복귀를 제공한다. 접힌 본문은 포커스 경로에서 제외한다.
- 세션의 전체 실행 취소 확인은 현재 보기의 실행 제어 한 곳에서만 연다. 보존된 Composer가 같은 확인 상태를 읽어 별도 Dialog를 동시에 열지 않는다. 명령·단축키 진입과 새로고침 후 미전송 확인 상태는 같은 실행에 유지한다.
- 한 개의 조용한 live region에서 완료 수·사용자 대응 필요 같은 의미 있는 변화만 알린다. 토큰·경과 시간 tick마다 읽지 않는다.
- 경고/실패를 색만으로 구별하지 않는다. reduced motion에서는 점·링·접힘 모션을 제거하거나 최소화한다.
- 요청별 측정은 한 번 캐시하고 여러 위젯에서 전체 payload를 반복 순회하지 않는다. 대규모 토큰화로 UI thread를 막지 않는다. 필요한 작업이 커질 경우 기존 worker 구조를 우선 사용한다.
- 위젯 열기/닫기는 네트워크 탐색·조회 외에 도메인 command를 발행하지 않는다. compact/Reins/승인/취소는 기존 정확한 대상·attempt·revision 검사를 거친 Coordinator 경로에 남긴다.

### 11.1 시각 증거

각 캡처/전환 기록에는 빌드 SHA, fixture 또는 live 구분, 컨테이너 크기, 상태, 확인한 인수 ID를 기록한다.

필수 상태는 (1) 단일 다단계 실행의 Todo 펼침, (2) 항목 전환 직전/직후, (3) 컨텍스트 상세와 구성별 범례, (4) 성공 후 요약형, (5) 승인 대기 또는 실패, (6) 다중 에이전트 선택, (7) 좁은 채팅 열이다. M2의 짧은 전환 기록으로 새로고침 없이 목록이 바뀌는 것을 확인한다.

실제 사용자 프롬프트·경로·키 대신 결정적 fixture를 사용한다. 실행하지 않은 브라우저·OS·유료 provider 검사를 통과로 표시하지 않는다. 스크린샷은 보이는 배치의 증거이고 프로토콜 안전성 검증은 자동 시험으로 별도 확보한다.

## 12. 비목표와 변경 경계

이번 플랜은 UI 표시와 필요한 읽기용 컨텍스트 계측, 기존 권한 안에서의 계획 발행 규약을 포함한다. 키 자동 수집, 연결 권한 확대, 자동 compact 정책 변경, 자동 병합·배포·원본 반영, Todo 클릭 완료, 새 에이전트 실행 엔진은 포함하지 않는다.

공용 컴포넌트의 재사용을 우선하고 패키지 전체 교체·추가 스크롤 엔진·새 Todo DB를 만들지 않는다. 원본 프롬프트/산출물 필터링으로 중복을 숨기지 않는다. 도메인 결과·검토·제출·실제 파일 반영을 한 성공 상태로 합치지 않는다.

대화 내 실행 카드의 시작·검증·진행 상태는 위젯의 현재 실행 상태로 전달한다. 목록 조회의 이전 시작 상태를 대화 턴에 중복 표시하지 않으며, 최초 상태는 시작 중으로 설명한다.
