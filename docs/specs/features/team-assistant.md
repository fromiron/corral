# 기능 명세: AI로 팀 만들기와 편집

- 상태: accepted
- 기준: [팀 구성](team-composition.md), [라이브러리](library.md), [공통 Outrider](shared-outrider.md), [팀 편집기](canvas.md), [HTTP 계약](../api-contract.md), [관리형 LLM 요청](../llm-runtime.md)
- 비목표: 대화로 팀의 작업을 실행하기(실행은 시험과 세션이 맡는다), 임의의 그래프 편집을 자연어로 하기, 에이전트 원본·스킬·다른 팀을 대화로 고치기, 권한·MCP 인증·사람 승인을 대화로 주기, 대화 기록의 저장

## 사용자 관측 동작

팀 편집기의 두 보기 아래에 **AI로 팀 편집**이 있다. 팀이 일하는 대화나 Outrider와 다른 것이므로 이름에 늘 팀을 **만들기** 또는 **편집**한다는 말을 쓴다. 대화의 결과는 사람이 확인하는 **초안의 제안**이다. 저장과 시험은 사람이 따로 누른다.

### 자리

1. 접혀 있을 때는 편집 영역 아래 한 줄(**AI로 팀 편집**)이다. 누르면 그 자리에서 위로 펼쳐지고 입력에 포커스가 간다. 펼친 높이는 편집기의 절반을 넘지 않으며, 질문이나 제안이 있을 때만 60%까지 커진다. 머리말과 입력 사이의 대화 기록이 스크롤되며 새 질문이나 제안이 도착하면 그 동작을 볼 수 있다. 닫기와, 입력이 비었을 때의 Esc가 접고 진입점으로 포커스를 돌린다. 접었다 펴면 같은 팀의 입력과 대화로 돌아온다.
2. 편집기 폭이 좁으면 같은 한 줄이 대화 시트를 연다. 키보드가 열려도 입력과 주 동작까지 스크롤된다.
3. 입력은 디자인킷 `InputMessage`다. 접근성 이름은 빈 팀에서는 **팀 만들기 요청**, 작업 역할이 있는 팀에서는 **팀 편집 요청**이다. 한국어 IME 조합 중 Enter는 보내지 않는다. 보내는 동안 다시 보낼 수 없고 **취소**가 있다. 대화가 열려 있어도 목록·캔버스·저장·시험은 그대로 쓸 수 있다.
4. 모델을 부르는 전송은 입력 옆에 쓰는 모델의 이름을 보인다. 예시와 선택지를 누르는 것은 모델을 부르지 않는다. 모델이 연결돼 있지 않으면 그 사실과 할 수 있는 동작(선택지, 로컬 예시)을 보인다. 서버에 연결한 편집기에서만 모델 연결로 갈 수 있다. 입력과 초안은 그대로다.

### 새 팀

5. 라이브러리의 **새 Corral**은 저장하지 않은 새 팀을 팀 구성으로 연다. 대화가 펼쳐져 있고 "이 팀이 어떤 일을 하면 좋을까요?"와 눌러서 입력을 채우는 예시가 있다. 같은 화면에서 **에이전트 추가**로 직접 구성하거나 템플릿으로 시작할 수 있다. 둘러보고 떠나면 팀이 생기지 않는다. 템플릿의 **사본 편집**과 **목표에서 초안 만들기**도 같은 화면으로 들어온다.
6. 목적을 보내면 다음 응답은 둘 중 하나다.
   - 답에 따라 역할이나 결과가 달라지는 정보가 비었으면 **질문 하나**와 선택지(2–3개, **추천해 줘**, 직접 답하기).
   - 정보가 충분하면 바로 **제안**. "작성자 한 명으로 이 안내문을 써 줘"처럼 이미 정한 것은 다시 묻지 않는다.
   질문은 한 번에 하나, 한 제안에 두 번까지다. 역할 수·실행 방식·스킬을 되묻지 않는다.
7. 제안은 들어갈 역할(이름과 맡을 일 한 줄), 일의 흐름, 끝에 받을 결과와 제출자, 그리고 그렇게 권하는 이유 한 문장을 보인다. 이유는 지금 말한 목적과 고른 선택에서 온다. 일이 늘어나는 대안(조사 추가, 검토 통과 후 제출)이 있으면 한 줄 차이와 함께 고를 수 있다.
8. **초안에 적용**하면 두 보기의 같은 초안에 역할·흐름·결과가 생기고 포커스가 목록의 첫 역할로 간다. 되돌리기 한 번으로 제안 전체가 돌아간다. 라이브러리의 저장된 팀 수는 적용 전후에 같고, 첫 **저장**에서만 하나 늘어난다.
9. 모델이 없을 때의 제안은 **로컬 예시**라고 표시하고 모델 요청은 0회다.
   모델의 답을 쓸 수 없으면 같은 목적의 로컬 예시를 보인다. 모델의 제안이 아니라는 사실을 알리고 다시 시도할 수 있게 한다.

### 기존 팀

10. 기존 팀에서는 "이 팀에서 무엇을 바꿀까요?"와 선택지가 있다: **지금 누가 제출합니까 · 필요할 때 자문 추가 · 검토 통과 후 제출 · 목표 변경**. 선택지는 구조화된 요청이며 모델을 부르지 않는다.
11. 할 수 있는 요청은 네 가지다.
    - **구성 묻기.** 누가 무엇을 내고 누구의 결과를 받는지, 검토와 자문이 있는지를 현재 초안에서 읽어 답한다. 제출자를 물으면 실제로 받는 결과마다 제출자와 결과 이름을 한 문장으로 답한다. 출력이 여럿일 때만 문장 앞에 출력 이름을 붙이고, 받는 결과가 없으면 아직 없다고 답한다. 적용 버튼이 없다. 되돌리기·저장·실행이 늘지 않는다.
    - **목표 변경.** 요청을 **이전**과 **이후** 두 단락으로 나누어 보인다. 각 단락은 네 줄까지 표시하고 요청 전문도 확인할 수 있다.
    - **필요할 때 자문.** 공통 Outrider를 팀 전체 대상으로 더한다. 이미 있으면 있다고 답한다. 실행 단계와 권한을 더하지 않는다.
    - **검토 통과 후 제출.** 어느 결과를 누가 검토하고, 수정 요청이 누구에게 돌아가며, 누가 제출하는지를 보인다. 공통 Outrider가 없어서 함께 더해지면 그것도 보인다. 받는 결과가 여럿이면 어느 결과인지 먼저 고른다.
12. "발행 전에 검토받게 해 줘"처럼 의견만인지 통과 조건인지 모호하면 **필요할 때 의견 / 통과 후 제출** 중 고르게 한다. 통과 조건을 명시했으면 바로 제안한다.
13. 그 밖의 요청은 임의로 해석해 적용하지 않는다. 지금 할 수 있는 네 가지와 직접 고칠 자리(팀 구성, 흐름 그래프)를 안내한다.
14. 변경 제안은 **실제로 달라지는 항목**만 보인다. **초안에 적용**은 그 제안 전체를 한 번에 반영하고 포커스를 바뀐 행으로 옮긴다. 되돌리기 한 번으로 돌아가며, 앞서 손으로 고친 지시·스킬·다른 결과는 그대로다.

### 낡은 제안과 실패

15. 제안이 나온 뒤 초안이 달라지면(손편집, 되돌리기, 다른 적용) 그 제안은 적용할 수 없다. "초안이 바뀌었습니다"와 **다시 제안**을 보이고, 적었던 요청은 남는다. 다시 제안은 지금 초안을 기준으로 다시 계산한다. 모델이 필요한 제안은 사람이 **다시 제안**을 눌렀을 때만 새 요청을 보낸다.
16. 요청을 취소했거나 다른 팀으로 옮긴 뒤 도착한 응답은 나타나지 않고 적용되지 않는다.
17. 모델 요청이 실패하면 원인과 다시 시도를 보인다. 보낸 요청의 결과를 확인하지 못했으면 다시 보내지 않았다고 알리고, 사람이 고를 때만 새 요청을 보낸다.
18. 제안만으로는 아무것도 저장·실행되지 않는다. 권한, MCP 인증, 사람의 승인, 자동 관찰은 사람이 명시적으로 고르지 않는 한 제안에 들어가지 않는다.

## 계약

- **한 작업 사본.** 대화는 편집기의 작업 사본을 읽고, 적용은 공유 편집기 저장소의 `applyDraft` 한 번이다. 질문·선택·취소·같은 상태 적용은 되돌리기 0건이다.
- **임시 초안.** 새 팀은 저장본 없는 작업 사본으로 시작한다. [팀 편집기의 첫 저장](canvas.md#계약)이 팀을 만들면 주소는 저장된 팀의 편집 주소가 된다. 저장 전에 떠나면 내용이 있을 때만 묻고, 떠나면 아무것도 남지 않는다.
- **보이는 것이 적용되는 것.** 제안의 미리보기는 실제 편집 명령(`commands.ts`, `draftFromPlan`, `setSharedOutrider`, `setRequiredOutputReview`, `patchTeam`)을 현재 초안의 사본에 순서대로 실행하고 같은 컴파일러로 검사한 결과에서 만든다. 적용은 그 결과 객체를 그대로 쓴다. 명령 하나라도 거절되면 제안 전체를 만들지 않고 이유를 보인다.
- **낡음 판정.** 제안은 만들 때의 팀 키, 요청 id, 초안 객체를 기억한다. 적용은 현재 초안이 그 객체와 같을 때만 된다.
- **허용된 구조만.** 모델의 답은 신뢰하지 않는 글이다. JSON 객체 하나를 감싼 코드 블록과 객체 앞뒤의 설명은 무시한다. 객체 자체의 필드·대상·형식이 틀리거나 현재 모드에서 허용하지 않는 응답이면 답 전체를 버린다. 모델이 준 문자열을 명령으로 실행하지 않는다. `reason`은 비어 있지 않은 문자열이어야 하며, 여러 문장이면 첫 문장만 취하고 400자까지만 보인다.
  - `question`: 정해진 질문 id(`material`, `review_policy`, `review_target`) 하나와 그 id의 선택지.
  - `plan`: [목표 초안](library.md)의 `TeamPlan`과 이유 한 문장.
  - `edits`: `set_brief`, `add_shared_advice`, `require_review { outputId, index }`의 목록과 이유. 대상은 요청에 실린 현재 팀의 출력과 입력이어야 한다.
  - `describe`: 무엇을 묻는지(`submitter`, `members`, `review`)만. 사실은 클라이언트가 초안에서 읽어 쓴다.
  - `unsupported`.
  응답의 구별 필드는 `kind`다. 새 팀에서는 `question`·`plan`만, 기존 팀에서는 `question`·`edits`·`describe`·`unsupported`만 허용한다. 질문은 `id`와 `choices`를 담는다. `material`의 선택지는 `person`·`team`, `review_policy`의 선택지는 `opinion_only`·`required`다. `review_target`의 선택지는 서로 다른 `{ outputId, index }`다. 추천과 직접 답하기는 화면 동작이며 모델이 만든 선택지가 아니다. 계획은 `plan`, 편집은 `edits`, 각각의 이유는 `reason`에 담는다. 편집도 `kind`로 구별하며 `set_brief`는 `brief`를 담는다. 기존 팀 설명은 `topic`만 담는다.
- **사람의 선택이 이긴다.** 사람이 누른 선택(자료를 누가 주는지, 의견만/통과 조건, 자동 관찰, 검토 대상)은 구조화된 값으로 대화에 남고 요청에 함께 보낸다. 낱말 매칭이나 모델의 다음 답이 그 값을 덮지 못한다. 모델의 답이 선택과 어긋나면 선택에 맞게 고치거나 버린다.
- **부정문.** "검토 통과나 자동 관찰은 필요 없다"처럼 부정된 검토·관찰은 검토 단계·필수 정책·관찰을 만들지 않는다. 목표 초안의 로컬 규칙과 모델 답 뒤의 조정, 이 대화가 같은 판정을 쓴다.
- **요청.** `POST /api/v1/team-assistant`는 `{ operationId, mode: 'create' | 'edit', messages, decisions?, team? }`를 받는다. `messages`는 최근 12개, 각 2,000자까지다. `team`은 편집에서만 보내며 역할의 노드 id와 이름, 출력별 받는 결과(순번·이름·제출자 이름), 공통 Outrider 유무, 요청 글을 담는다. 역할 지시 본문, 스킬, 권한, 파일은 보내지 않는다. 응답은 위 형식 하나와 쓴 모델의 표시 이름이다.
  메시지는 `{ role: 'user' | 'assistant', content }`다. 한 제안의 요청에는 목적부터 현재 답까지의 대화만 넣는다. `assistant` 메시지는 앞서 보인 질문 하나를 뜻하며 두 개가 있으면 다음 응답으로 질문을 받지 않는다. 제안이 끝나고 다른 제안을 요청하면 질문 횟수도 새로 센다. 선택은 `decisions.material`, `reviewPolicy`, `observeWork`, `reviewTarget`으로 보낸다. 편집에서는 `team`이 필수다. `roles`에는 `{ nodeId, name }`, `outputs`에는 `{ outputId, results: [{ index, name, producerName }] }`를 넣고 `hasSharedOutrider`와 `brief`를 함께 보낸다. `index`는 필터링 전 출력 입력의 순번이다. HTTP 응답은 `{ reply, model }`이며 `model`은 표시 이름이다.
  `role: 'assistant'`인 메시지에는 화면에서 실제로 보인 질문의 `questionId`(`material`·`review_policy`·`review_target`)를 함께 보낸다. 사용자 메시지에는 이 필드를 넣지 않는다. 질문 문구를 분석해서 ID를 추측하지 않는다. 직접 입력한 답도 다음 사용자 메시지로 전달하며, 앞서 물은 정책이나 대상은 처음 요청이 모호했다는 이유로 다시 묻지 않는다. 유효한 모델 제안을 쓰되 사람이 고른 값이 있으면 그 값을 우선한다. 여전히 같은 질문이 필요하면 기존 팀에는 `unsupported`를 반환하고, 새 팀에서는 답을 쓸 수 없다고 알린다. 서로 다른 질문도 한 제안에 두 번까지만 허용한다.
- **멱등과 불명 결과.** `operationId`의 처리, 같은 id에 다른 본문의 거절, 결과를 확인하지 못한 요청을 다시 보내지 않는 규칙은 `POST /api/v1/team-drafts`와 같다. 연결이 끊기면 요청을 취소한다.
- **비용.** 한 번의 전송은 모델 요청 한 번이다. 실패한 형식의 답을 자동으로 다시 요청하지 않는다. 사용량은 관리형 요청의 기록을 따른다.
- **브라우저 데모와 모델 없음.** 서버가 없거나 모델이 없으면 선택지와 로컬 예시만 동작한다. 자유 입력은 해석하지 않고 할 수 있는 동작을 안내한다.
- **기존 호출자.** `POST /api/v1/team-drafts`의 계약은 그대로다.

## 수용 시나리오

```gherkin
Given 빈 프로젝트에서 새 Corral을 열었다
When 목적만 적어 보내고, 질문 하나에 답한 뒤 제안을 초안에 적용한다
```

## 보안·성능·접근성

- 요청에는 역할 지시 본문·파일·키·로컬 경로를 싣지 않는다. 서버는 대화 본문을 로그에 남기지 않는다.
- 모델의 답으로 도구 권한·연결·한도가 생기지 않는다. 구조는 패턴과 편집 명령이 정한다.
- 대화는 이름 있는 영역이고 새 응답은 정중한 live 영역으로 알린다. 선택지는 버튼이며 선택과 낡음, 실패를 색만으로 알리지 않는다.
- 펼침·접힘은 디자인킷의 움직임을 쓰고 움직임 줄이기에서는 바로 바뀐다.
