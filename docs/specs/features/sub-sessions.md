# 기능 명세: 서브세션

- 상태: accepted
- 비목표: 리드(모델)가 서브세션을 여는 것, 자동 합치기, 원격 저장소와 PR([워크벤치](../workbench.md#읽기-전용-git-관찰)의 push가 맡는다), Git이 아닌 프로젝트의 서브세션, 서브세션 브랜치 지우기

서브세션은 한 세션의 Paddock에서 갈라 나온 세션이다. 사람은 같은 일을 나란히 다른 사본에서 시도하거나, 일의 한 조각을 따로 맡긴 뒤 부모로 합친다. 서브세션은 부모 연결이 하나 더 있는 보통 세션이다. 대기열, Reins, Outrider, 검색, 보관, 삭제는 다른 세션과 같다.

## 사용자 관측 동작

- **열기.** 세션 상단 더 보기 메뉴의 "서브세션 열기"(Open sub-session)가 그 세션 밑에 서브세션을 만들고 연다.
  - Paddock이 있는 세션에서만 켜진다. Paddock이 없으면 항목은 꺼져 있고 그 이유를 단다. 이 항목이 Paddock을 만들지 않는다. Git이 아닌 프로젝트에는 Paddock이 없으므로 늘 꺼져 있다.
  - 서브세션도 서브세션을 연다. 단계에 한도는 없다.
  - 서브세션은 새 대화처럼 빈 채로 열리고 첫 요청이 이름을 짓는다. 팀(또는 자동 모드)과 자동 모드의 모델 선택은 부모의 것을 이어받는다. 목적·완료 기준·Outrider·고정은 이어받지 않는다.
- **시작점.** 서브세션은 처음부터 자기 Paddock과 브랜치를 갖는다.
  - 브랜치는 부모 Paddock의 지금 HEAD 커밋에서 시작한다. 이름은 Paddock 브랜치의 규칙([워크벤치](../workbench.md#paddock의-브랜치))을 따르되, 제목 자리에는 부모 세션의 제목을 쓴다. 서브세션 자신의 제목은 아직 첫 요청 전이라 정해지지 않았기 때문이다.
  - 부모 Paddock의 지금 파일이 서브세션 사본에 그대로 놓인다. 부모가 커밋하지 않은 변경(stage한 것도 stage하지 않은 채로), 지운 파일, 추적하지 않는 파일이 서브세션의 커밋하지 않은 변경으로 들어온다. Git이 무시하는 파일은 들어오지 않는다. 부모가 merge·rebase 도중이면 그 순서의 상태는 들어오지 않고 파일만, 충돌 표시가 있으면 그대로 들어온다.
  - 서브세션 변경 화면의 "세션 전체" 범위는 이 시작 상태에서 잰다. 부모에게서 받은 변경은 서브세션의 변경으로 보이지 않는다.
  - 부모는 바뀌지 않는다. 부모의 체크포인트도 늘지 않는다. 부모의 실행이 진행 중이어도 열 수 있고, 그 순간의 파일을 받는다.
  - 사본 준비가 실패하면 서브세션은 부모 연결을 가진 채 사본 없이 남는다. 화면은 Paddock이 없는 세션과 같고, 다시 열기(같은 명령)가 사본 준비를 잇는다. 그 서브세션에서 사람이 "사본 만들기"를 누르면 보통 세션처럼 원본 폴더의 HEAD에서 사본을 만든다. 사본을 지운 뒤에도 같다.
- **목록.** 프로젝트 세션 탭과 사이드바의 세션 목록에서 서브세션은 부모 행 바로 밑에 한 단계씩 들여쓴다. 부모와 그 밑의 모든 서브세션을 가족이라 한다.
  - 세션 탭에서 가족은 한 묶음에 함께 있다. 가족의 묶음은 구성원 각자의 묶음 가운데 묶음 순서(확인 필요 · 검토 · 진행 중 · 실행 전 · 완료 · 취소됨 · 빈 대화)에서 가장 앞의 것이다. 그래서 사람을 기다리는 서브세션은 접힌 묶음에 숨지 않는다.
  - 세션 탭의 행은 놓인 묶음 이름이 말한 상태를 다시 쓰지 않는다. 구성원 자기 묶음이 가족의 묶음과 다를 때만 자기 상태 낱말([표시 상태](presence.md))을 쓴다.
  - 사이드바에는 묶음이 없다. 행마다 지금처럼 자기 상태를 쓴다.
  - 형제끼리는 그 목록의 순서 규칙(고정한 세션 먼저, 그다음 최근 변경)을 따른다. 가족끼리의 순서는 맨 위 세션의 고정 여부와, 구성원 가운데 가장 최근의 변경 시각으로 정한다. 일하는 서브세션이 가족을 위로 올린다.
  - 부모가 목록에 없으면(보관됐거나 지워졌다) 서브세션은 맨 위 행으로 보인다. 검색하는 동안은 검색에 맞는 세션만 보이고, 부모가 보이지 않는 서브세션은 들여쓰지 않는다.
- **부모에 합치기.** 서브세션 변경 화면의 머리에 "부모에 합치기"(Merge into parent)가 있다. 누르면 부모 세션의 변경 탭 Git 보기가 열리고, merge 시작에 서브세션 브랜치가 골라져 있다. 합치기는 거기서 사람이 기존 merge 시작을 누를 때 일어난다. 충돌 해결·계속·중단도 부모의 기존 흐름이다([워크벤치](../workbench.md#git-hunk와-충돌-해결)).
  - 합쳐지는 것은 서브세션 브랜치의 커밋뿐이다. 서브세션 사본의 커밋하지 않은 변경은 합쳐지지 않는다. 버튼은 그런 변경이 있어도 꺼지지 않는다.
  - 버튼이 꺼지고 그 이유를 다는 경우는 둘이다. 서브세션 브랜치에 부모 HEAD에 없는 커밋이 없을 때와, 부모에 Paddock이 없을 때다.
  - 서브세션 사본에 브랜치가 없으면(브랜치 규칙 전에 만든 사본) 버튼은 없다. 부모가 없으면(지워졌다) 버튼은 없다.
  - 부모 사본이 깨끗하지 않거나, 브랜치가 없거나, 다른 Git 순서가 진행 중이면 부모의 merge 시작이 지금처럼 이유를 말하고 거절한다. 부모에 커밋하지 않은 변경이 있으면 부모가 먼저 커밋하거나 되돌린다.
  - 부모가 서브세션에 넘긴 변경을 부모도 커밋했다면, 서브세션이 그 줄을 다시 고치지 않은 한 합치기는 충돌 없이 끝난다. 서브세션이 그 줄을 다시 고쳤으면 그 줄은 충돌이다.
  - 합친 뒤에도 서브세션과 그 브랜치는 남는다. 더 일한 뒤 다시 합치면 새 커밋만 들어간다.
  - 원본 폴더에 반영하는 것은 지금처럼 각 세션의 반영이다. 서브세션의 일은 부모에 합쳐진 뒤 부모의 반영으로 원본 폴더에 간다. 서브세션도 자기 반영을 쓸 수 있다.
- **보관과 삭제.**
  - 부모를 보관해도 서브세션은 보관되지 않는다.
  - 세션을 지우면 그 바로 밑 서브세션은 남고 부모 연결만 지워져 맨 위 세션이 된다. 그 밑의 서브세션은 그대로 그 세션 밑에 있다.
  - Paddock이나 세션을 지워도 그 Paddock의 브랜치는 저장소에 남는다([워크벤치](../workbench.md#paddock의-브랜치)).

## 계약

- **기록.** 세션의 부모는 `work_sessions.parent_session_id`(없으면 NULL)다. `WorkSession.parentSessionId`는 저장소가 늘 돌려주며, 브라우저에서 만든 세션에만 없다. 부모는 같은 프로젝트의 세션이다. 세션을 지우면 그 세션을 부모로 적은 행의 값이 NULL이 된다.
- **열기 명령.** `POST /api/v1/sessions/:sessionId/sub-sessions`, 본문 `{ commandId, title }`.
  - `title`은 새 세션 제목과 같은 규칙이고, 서브세션은 `autoTitle`로 만든다.
  - 같은 `commandId`로 같은 부모와 본문을 다시 보내면 처음 만든 세션을 돌려준다. 같은 `commandId`에 다른 부모나 본문은 `REVISION_CONFLICT`다. 명령과 세션은 `sub_session_commands`(command ID, 부모와 본문의 hash, 부모, 서브세션, 시각)에 한 트랜잭션으로 묶인다. 서브세션을 지우면 그 명령 행도 지운다.
  - 사본 준비가 중간에 끊겼으면 같은 `commandId`로 다시 보낸 요청이 그 서브세션의 사본만 이어서 준비한다. 이미 있는 사본이 기록한 시작 상태와 다르면 `REVISION_CONFLICT`로 거절하고 새로 만들지 않는다.
  - 부모가 없거나 보관됐으면 `TARGET_NOT_FOUND`, 부모에 Paddock이 없으면 `CAPABILITY_DENIED`, 부모 Paddock 폴더가 없으면 `TARGET_NOT_FOUND`다.
  - 시작 상태는 부모 Paddock의 write lease 안에서 읽는다. 부모 사본의 HEAD와 지금 tree(`git add -A`로 만든 임시 index의 tree)를 읽는다. 서브세션 사본을 그 HEAD에서 브랜치와 함께 만들고, 그 tree를 서브세션 사본의 고정한 기준 체크포인트로 남겨 복원한다. 두 사본은 같은 저장소의 객체를 쓰므로 부모 쪽에는 아무것도 남기지 않는다. 서브세션 사본의 기준 tree(`base_tree`, `refs/corral/<세션>/base`)가 그 tree다.
- **합치기 준비 읽기.** `GET /api/v1/sessions/:sessionId/parent-merge`는 `{ parentSessionId, branch, commits, parentPaddock }`를 돌려준다.
  - `branch`는 서브세션 사본의 브랜치(없으면 null), `commits`는 그 브랜치에 있고 부모 HEAD에 없는 커밋 수(부모에 사본이 없으면 null), `parentPaddock`은 부모에 사본이 있는지다.
  - 부모가 없는 세션은 `TARGET_NOT_FOUND`다. 읽기만 하며 사본을 바꾸지 않는다.
- **합치기.** 새 서버 명령은 없다. 부모 사본의 기존 merge 시작(사람 operation receipt, 고정한 hash와 브랜치 OID)을 그대로 쓴다.
- **모의 실행.** 브라우저 안의 모의 실행에는 Paddock이 없으므로 "서브세션 열기"는 늘 꺼져 있다.

## 수용 시나리오

```gherkin
Scenario: 부모의 커밋과 커밋하지 않은 변경에서 시작한다
  Given 부모 Paddock이 브랜치 위에서 커밋 하나를 더 했고 파일 하나를 커밋하지 않은 채 고쳤다
  When 사람이 서브세션을 연다
  Then 서브세션 사본의 브랜치는 부모의 지금 HEAD에서 시작한다
  And 서브세션 사본에 부모가 고친 파일이 커밋하지 않은 변경으로 있다
  And 서브세션의 "세션 전체" 변경은 비어 있다
  And 부모 사본의 HEAD와 파일은 그대로다

Scenario: 같은 명령을 다시 보낸다
  Given 서브세션 열기 명령의 응답을 잃었다
  When 같은 commandId와 본문으로 다시 보낸다
  Then 처음 만든 서브세션이 돌아오고 세션과 사본은 하나다
  When 같은 commandId에 다른 제목으로 보낸다
  Then REVISION_CONFLICT로 거절된다

Scenario: Paddock이 없는 세션
  Given 세션에 Paddock이 없다
  Then "서브세션 열기"는 꺼져 있다
  And 서버는 열기 명령을 CAPABILITY_DENIED로 거절하고 Paddock을 만들지 않는다

Scenario: 부모에 합치기
  Given 서브세션이 커밋 두 개를 더했고 커밋하지 않은 변경이 없다
  When 사람이 "부모에 합치기"를 누른다
  Then 부모 세션의 변경 탭 Git 보기가 열리고 merge 시작에 서브세션 브랜치가 골라져 있다
  And 사람이 merge 시작을 누르기 전에는 부모 사본이 바뀌지 않는다

Scenario: 합칠 커밋이 없다
  Given 서브세션 브랜치에 부모 HEAD에 없는 커밋이 없다
  Then "부모에 합치기"는 꺼져 있고 그 이유를 단다

Scenario: 이어받은 변경만 있다
  Given 서브세션이 부모의 커밋하지 않은 변경을 받았고 커밋 하나를 더했다
  Then "부모에 합치기"는 켜져 있다
  And 부모의 merge에는 그 커밋만 들어간다

Scenario: 기다리는 서브세션은 접힌 묶음에 숨지 않는다
  Given 부모의 최신 실행이 취소됐고 서브세션이 사람의 답을 기다린다
  Then 부모와 서브세션은 확인 필요 묶음에 함께 있다
  And 부모 행은 자기 상태 "취소됨"을 쓰고 서브세션 행은 묶음 이름의 상태를 다시 쓰지 않는다

Scenario: 가운데 세션을 지운다
  Given 세션 A 밑에 B, B 밑에 C가 있다
  When B를 지운다
  Then C는 남고 맨 위 세션이 된다
  And B의 Paddock 브랜치는 저장소에 남는다
```

## 보안·성능·접근성

- 서브세션 사본도 신뢰한 프로젝트에서만 만들고, 원본 폴더 밖 Corral 데이터 폴더에 둔다. 부모 사본에서 Git이 무시하는 파일(`.env` 같은 것)은 옮기지 않는다.
- 목록의 들여쓰기는 시각만이 아니다. 행은 접근 이름에 부모가 누구인지를 담지 않고, 목록 구조로 단계를 알린다.
- 꺼진 메뉴 항목과 버튼의 이유는 화면에 보이는 글이고 접근 설명으로도 연결한다.
