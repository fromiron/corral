# 기능 명세: 감독

- 상태: accepted
- 비목표: 감독이 승인·취소·패치·권한을 바꾸는 것, 감독의 파일 쓰기와 명령 실행, 감독이 다른 역할을 부르거나 사람에게 묻는 것, 스트림 도중의 규칙 개입, 감독끼리의 감독, 동적으로 만든 하위 실행의 감독

감독은 다른 역할이 일하는 것을 별도 모델로 지켜보다가 필요할 때만 조언하는 역할이다. 일하는 역할은 구현에 집중하고, 감독은 요구에서 벗어남·잘못된 가정·확인되지 않은 주장을 찾는다. 팀 그래프의 노드와 연결 규칙은 [팀 그래프 모델](team-graph.md)이, 조언이 전달되는 경로와 상태는 [Reins](reins.md)가 정한다.

## 사용자 관측 동작

### 두는 곳

- **팀.** 팀 편집기에서 Agent 노드의 호출 방식을 **감독**으로 고르고, 지켜볼 Agent 노드로 `advise` 연결을 긋는다. 감독 노드는 실행 순서에 들어가지 않는다. 역할의 프롬프트(검토 원칙)와 모델은 다른 역할처럼 정한다.
- **대화.** 세션 설정에서 감독을 켜고 모델을 고른다. 다음 요청부터 대화에 답하는 역할을 지켜본다. 진행 중인 실행은 바뀌지 않는다. 검토 원칙은 내장 프롬프트를 쓴다.

### 하는 일

- 지켜보는 실행 단위가 모델 요청을 정해진 수(검토 간격, 기본 3)만큼 끝낼 때마다 감독이 그 사이에 새로 생긴 것(답변 글, 도구 호출과 결과 요약)을 읽는다. 첫 검토는 그 역할이 받은 작업 입력도 함께 읽는다.
- 검토가 도는 동안 생긴 새 기록은 다음 검토 하나로 합친다. 검토가 밀려 쌓이지 않는다.
- 지켜보던 실행 단위가 끝나면 아직 읽지 않은 기록에 대해 마지막 검토를 한 번 한다. 그동안 Run은 끝나지 않고, 대화에는 이미 나온 답이 그대로 보인다.
- 감독은 읽기 도구(검색, 문서 읽기, 파일 목록, 파일 읽기, 지켜보는 역할의 산출물 읽기)와 `advise` 하나만 쓴다.
- 할 말이 없으면 아무것도 하지 않는다. 조언 없이 끝난 검토는 대화에 아무것도 남기지 않는다.

### 조언

조언은 심각도와 짧은 글이다.

| 심각도 | 화면 이름 (KO / EN) | 뜻 | 전달 |
|---|---|---|---|
| `nit` | 참고 / Note | 고치면 좋은 것 | 대상의 다음 요청에 실린다 |
| `concern` | 우려 / Concern | 결과를 그르칠 수 있는 것 | 대상의 다음 요청에 실린다 |
| `blocker` | 중단 권고 / Blocker | 지금 방향을 계속하면 안 되는 것 | 대상의 응답을 끊고 바로 실린다(끼어들기) |

- 조언은 사람의 합류·끼어들기와 같은 지시 전달 경로로 가고, 모델에는 감독의 조언임과 심각도가 드러나게 감싸서 실린다. 대상이 승인이나 질문을 기다리면 그 결정 뒤에 읽힌다.
- 대상이 이미 끝났으면 다시 깨우지 않는다. 참고는 버리고, 우려와 중단 권고는 그 실행 행의 꼬리 줄과 [확인 필요](inbox.md)의 검토 묶음에 남는다. 접수된 뒤 읽히기 전에 대상이 끝난 우려와 중단 권고도 같은 곳에 남는다.
- 조언은 대상에게 하는 말이다. 대상이 따를지는 대상이 정하고, 전달됐다는 것이 따랐다는 뜻은 아니다.

### 문지기

감독이 낸 조언이 모두 전달되지는 않는다. 아래에 걸린 조언은 버리고, 감독에게는 버린 이유를 사실대로 돌려준다.

| 이유 | 조건 |
|---|---|
| `noise` | 글이 비었거나 "계속", "문제 없음", "LGTM" 같은 빈말뿐이다 |
| `duplicate` | 같은 감독이 이 Run에서 이미 낸 조언과 같은 글이고(대소문자·구두점·공백 차이는 무시) 심각도가 그때보다 높지 않다 |
| `over_budget` | 한 번의 검토에서 중단 권고가 아닌 조언이 3개를 넘었다 |
| `target_terminal` | 대상이 끝난 뒤의 참고 |

같은 문제를 더 높은 심각도로 다시 내는 것은 통과한다.

### 보이는 곳

- 활동 바를 펼치면 감독 행이 있다: 지켜보는 중 또는 검토 중, 그리고 전달된 조언 수.
- 전달된 조언은 대상 역할의 작업 과정 안에 한 줄(감독 이름 · 심각도 · 조언의 첫 줄 · 전달 상태)로 보인다. 펼치면 전문을 읽는다.
- 버려진 조언은 대화에 보이지 않고 실행 기록의 관계·판단 기록에만 남는다.
- 감독의 모델 사용량은 다른 역할처럼 그 실행 단위에 기록되고 사용량 상세에 역할별로 보인다.

### 멈추는 조건

- Run을 취소하거나 일시정지하면 감독도 함께 멈춘다.
- 한 번의 검토는 모델 요청 8회 안에 끝난다. 넘으면 그 검토를 끝내고 다음 검토를 기다린다.
- 감독이 실패해도 Run의 결과와 출력 확정은 바뀌지 않는다. 실패는 실행 기록에 실패로 남고, 그 감독은 그 Run에서 다시 검토하지 않는다.

## 계약

- 정의: Agent 노드의 `invocation`은 `observer`를 가질 수 있고, capability link의 `kind`는 `advise`를 가질 수 있다. 감독 노드는 `review: { interval, maxRequestsPerReview }`(기본 3, 8)를 갖는다. 컴파일 규칙은 [팀 그래프 모델](team-graph.md#구조-규칙)이다.
- 감독 노드마다 Run 안에 실행 단위 하나가 있다. 첫 검토 때 만들고, 검토 사이에는 `waiting_message`로 쉰다. 한 번의 검토는 지켜보는 실행 단위 하나의 기록을 다루고, 한 감독의 검토는 한 번에 하나씩 돈다. 자기 Task를 갖지만 Run의 필수 작업이 아니다. 대기 실행 단위 수와 모델 동시성 한도에는 다른 실행 단위처럼 든다.
- 검토의 시작은 지켜보는 실행 단위의 `model.finished`와 종료를 Coordinator의 관찰자가 받아 정한다. 관찰자는 읽기만 하며 실패해도 실행에 영향을 주지 않는다.
- 검토 입력은 Run의 공개 기록에서 만든다. 마지막으로 읽은 모델 호출 뒤의 호출마다 답변 글(호출당 6,000자까지)과 도구 행(이름·대상·상태·요약)을 넣는다. 첫 검토의 작업 입력도 6,000자까지다. 글자 수는 UTF-16 단위다.
  - 압축 요약과 확장 목적의 호출은 답변이 아니므로 넣지 않고 검토 간격에도 세지 않는다.
  - 끊기거나 실패한 호출은 받은 데까지의 글을 확정되지 않은 응답으로 표시해 넣는다.
  - 전체 24,000자를 넘으면 오래된 것부터 차례로 줄인다: 도구 요약을 빼고, 답변 글을 500자까지 줄이고, 도구 행을 수로 바꾼다. 그래도 넘을 때만 가장 오래된 호출을 뺀다. 줄이거나 뺀 수를 적는다.
  - 도구 행의 대상과 요약은 화면이 보이는 필드만 쓴다. 자격 증명으로 보이는 값은 가리고, 작업 폴더의 경로는 `[workspace]`로, 그 밖의 절대 경로는 `[path]`로 바꾼다(검사 출력과 같은 규칙).
- `advise`는 Coordinator 명령 `submit_advice { observerExecutionId, attemptNo, targetExecutionId, severity, note }`가 된다. `note`는 1–1,000자다. receipt는 접수됐는지와 전달 방식, 또는 버린 이유를 돌려준다. 감독의 현재 시도가 아니거나 `targetExecutionId`가 그 감독이 `advise` 연결로 지켜보는 노드의 실행 단위가 아니면 거절한다.
- 접수된 조언은 `advice.admitted`를, 버려진 조언은 `advice.suppressed`를 남긴다(필드는 [API 계약](../api-contract.md)의 이벤트 표). 둘 다 감독과 대상의 실행 단위, 심각도를 담는다. 조언의 글은 전달되는 조언이면 그 지시에, 보존되는 조언(`preserve`)이면 `advice.admitted`의 `note`에 있다. 버려진 조언의 글은 남기지 않는다. `delivery`는 `next_request`, `interrupt`, `preserve` 중 하나다. 전달되는 조언은 출처가 `advice`인 지시가 되고 그 뒤는 [Reins의 전달 상태](reins.md#2-지시-전달-상태)를 따른다. 조언에서 온 지시는 대기 요청으로 넘겨받지 않는다.
- 문지기의 이력은 감독 실행 단위마다 최근 512개다. 문지기와 전달 방식의 판정은 순수 함수다.
- 세션은 `advisor: { modelProfile } | null`을 저장한다. 켜져 있으면 대화 실행의 정의에 감독 노드와 대화에 답하는 역할로 가는 `advise` 연결을 더한다. Run의 snapshot에 고정되므로 진행 중인 실행에는 적용되지 않는다.
- 같은 `submit_advice`의 재전송은 처음 결과를 돌려준다.

## 수용 시나리오

```gherkin
Given 감독이 구현자를 지켜보는 팀 실행
When 구현자가 모델 요청 세 번을 끝낸다
Then 감독의 검토가 한 번 시작되고 그 세 요청의 답변과 도구 요약을 읽는다

Given 감독의 검토가 도는 동안 구현자가 요청을 여섯 번 더 끝냈다
Then 다음 검토는 한 번이고 그 여섯 요청을 함께 읽는다

Given 감독이 우려를 낸다
Then 구현자의 다음 요청에 그 조언이 감독의 조언으로 실리고
And 구현자의 작업 과정에 조언 한 줄이 "읽힘"으로 보인다

Given 감독이 중단 권고를 낸다
Then 구현자의 흐르던 응답이 끊기고 조언이 바로 다음 요청에 실린다

Given 감독이 "문제 없음, 계속"이라고 조언한다
Then 조언은 전달되지 않고 감독은 빈말이라 버려졌다는 결과를 받는다

Given 감독이 같은 글의 조언을 같은 심각도로 다시 낸다
Then 두 번째는 전달되지 않는다
When 같은 글을 더 높은 심각도로 낸다
Then 전달된다

Given 구현자가 끝난 뒤 감독이 우려를 낸다
Then 구현자는 다시 시작되지 않고
And 그 조언은 실행 행의 꼬리 줄과 확인 필요의 검토 묶음에 보인다

Given 감독이 지켜보는 실행
When 사람이 Run을 취소한다
Then 감독 실행 단위도 취소되고 종료가 확인된 뒤에 Run이 취소됨이 된다

Given 감독 노드에서 Decision 노드로 advise 연결을 그었다
Then 컴파일 오류다
```

## 보안·성능·접근성

- 조언은 지시일 뿐이다. 도구 승인, 권한 모드, 취소, 패치, 출력 승인에 닿지 않는다. 감독이 쓰는 도구는 읽기로 고정되며 역할 설정으로 넓힐 수 없다.
- 감독이 읽는 것은 같은 Run의 기록과 그 Run이 읽을 수 있는 파일이다. 다른 Run이나 다른 세션의 기록을 읽지 않는다.
- 조언의 글은 모델이 쓴 것이다. 화면에서 원시 HTML을 실행하지 않는다.
- 검토는 모델 요청마다 기존 허가와 사용량 정산을 거친다. 검토 간격과 합치기, 검토당 요청 상한이 비용을 묶는다. 감독은 지켜보는 실행이 모두 끝나면 끝난다.
- 심각도는 색만으로 구분하지 않고 이름을 함께 쓴다.
