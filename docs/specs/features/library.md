# 기능 명세: 라이브러리

- 상태: accepted
- 비목표: Hook·MCP·패키지 설정 폼을 설정 모달 밖으로 옮기기, 설정 주소 변경, 팀 정의·revision 규칙 변경

## 사용자 관측 동작

사이드바 주 메뉴의 **라이브러리**는 다시 쓰는 구성 요소를 찾고 상태를 확인하는 곳이다. 다섯 보기로 나뉜다. 보기는 화면의 Tabs이며 사이드바에 따로 나오지 않는다.

| 보기 | 주소 | 내용 |
|---|---|---|
| 팀 | `/library/teams` | 저장한 Corral(팀) 목록 → 상세 → "이 팀으로 새 대화"·"편집"·"복제" |
| 에이전트 | `/library/agents` | 프로젝트의 에이전트 원본 목록 → 상세 → 만들기·편집·복제·보관. [에이전트 라이브러리](agent-library.md) |
| 스킬 | `/library/skills` | 설치된 스킬 목록 → 상세 → 만들기·가져오기·편집·사용 승인·보관. [스킬 라이브러리](skill-library.md) |
| 템플릿 | `/library/templates` | 팀 템플릿과 목표에서 초안 만들기 |
| 리소스 | `/library/resources` | Hook·MCP 서버·패키지·확장 목록과 상태, 스킬 보기로 가는 행 |

- 보기마다 주 동작은 하나다: 팀은 **새 Corral**, 에이전트는 **에이전트 만들기**, 스킬은 **스킬 만들기**. 팀을 만들려고 에이전트·스킬을 먼저 등록할 필요가 없다.

- 팀·에이전트·템플릿은 프로젝트 필터(`?project=`)를 가진다. 필터가 없으면 마지막으로 연 프로젝트를 쓴다. 스킬 보기는 필터를 사용처 조회와 돌아갈 문맥에 쓴다. 프로젝트 작업공간에는 팀 탭이 없다. 옛 `/projects/:projectId#corrals` 주소는 `/library/teams?project=:projectId`로 replace 이동한다.
- 팀 보기의 **새 Corral**은 저장하지 않은 새 팀을 편집기의 팀 구성으로 연다([AI로 팀 만들기와 편집](team-assistant.md#새-팀)). 그 화면에서 목적을 적어 제안받거나, 에이전트를 직접 추가하거나, 템플릿으로 시작한다. 고르는 대화상자를 거치지 않는다. 둘러보거나 떠나면 저장하지 않고, 첫 저장이 현재 프로젝트에 팀을 만든다. 새 팀에 예시 문구를 넣어 두지 않는다. 템플릿의 **사본 편집**과 **목표에서 초안 만들기**도 같은 화면으로 들어온다: 템플릿은 그 정의가 저장하지 않은 초안으로 열리고, 목표는 대화의 입력에서 시작한다. 같은 프로젝트에 이름이 같은 팀이 있으면 첫 저장 때 번호를 붙인다. 기존 정의와 가져오는 파일의 값은 그대로 읽는다.
- 기본 제공 템플릿과 목표에서 만든 초안은 결과의 승인을 넣지 않는다. 팀은 사람의 승인 없이 끝까지 돈다. 승인 단계(결정 노드의 승인 모드, 결과의 승인 요구)는 사람이 편집기에서 더한다. 이미 저장한 팀은 바뀌지 않는다.
- 템플릿 보기는 아래 열한 개를 카드로 보인다. 카드는 이름과 역할 이름을 실행 순서대로 보이고(동시에 도는 역할은 한 단계로 묶는다), 어떤 역할도 파일을 바꾸거나 명령을 실행하지 못하는 템플릿에는 "읽기 전용"을 표시한다. 흐름을 문장으로 다시 풀어 쓴 설명은 두지 않는다. 카드의 동작은 "새 대화"와 "사본 편집" 둘이고 어느 쪽도 화면의 주 버튼이 아니며, 빈 캔버스에는 새 대화가 없다. 역할 이름은 모든 템플릿에서 화면 언어를 따른다.

  | 템플릿 | 흐름 | 파일을 바꾸는 역할 | 명령을 실행하는 역할 |
  |---|---|---|---|
  | 단일 에이전트 | 에이전트 → 결과 | 없음 | 없음(읽기 전용) |
  | 구현·검토 | 구현 → 검토, 돌려보내면 다시 구현(검토 최대 2회) → 결과 | 구현 | 구현 |
  | 기능 구현 | 설계 → 구현 → 검증, 돌려보내면 다시 구현(검증 최대 2회) → 결과 | 구현 | 구현, 검증 |
  | 버그 수정 | 원인 조사 → 수정 → 검증, 돌려보내면 다시 수정(검증 최대 2회) → 결과 | 수정 | 원인 조사, 수정, 검증 |
  | 리팩터링 | 동작 고정 → 구조 변경 → 검증, 돌려보내면 다시 구조 변경(검증 최대 2회) → 결과 | 동작 고정, 구조 변경 | 동작 고정, 구조 변경, 검증 |
  | 성능 개선 | 기준 측정 → 개선 → 재측정, 돌려보내면 다시 개선(재측정 최대 2회) → 결과 | 개선 | 기준 측정, 개선, 재측정 |
  | 반증 리뷰 | 범위 정리 → 반증 둘을 동시에 → 합류 → 심사 → 결과 | 없음 | 반증 둘 |
  | 기술 결정 | 질문 정리 → 두 안의 조사를 동시에 → 합류 → 심사 → 결과 | 없음 | 없음(읽기 전용) |
  | 코드 조사 | 범위 정리 → 동작 추적과 기록 조사를 동시에 → 합류 → 작성 → 결과 | 없음 | 없음(읽기 전용) |
  | 조사 팀 | 조사(보조에게 위임) → 작성(질문) → 검토, 돌려보내면 다시 작성 → 결과 | 없음 | 없음(읽기 전용) |
  | 빈 캔버스 | 노드 없음 | — | — |

- 구현·검토부터 코드 조사까지 여덟 템플릿의 자리는 [기본 제공 에이전트](builtin-crew.md#기본-제공-에이전트)로 채운다. 에이전트가 그 자리의 도구·결과 형식·모델 자리·기본 지시·스킬을 정하고, 자리의 이름과 맡은 일의 문구는 화면 언어를 따른다. 동시에 도는 두 자리는 서로 다른 모델 자리를 쓴다.

  | 템플릿 | 자리(역할 id) → 에이전트 |
  |---|---|
  | 구현·검토 `implement-review` | 구현 `implement` → 구현, 검토 `review` → 검토 |
  | 기능 구현 `feature` | 설계 `design` → 설계, 구현 `implement` → 구현, 검증 `verify` → 검증 |
  | 버그 수정 `bug-fix` | 원인 조사 `investigate` → 원인 조사, 수정 `fix` → 구현, 검증 `verify` → 검증 |
  | 리팩터링 `refactor` | 동작 고정 `pin` → 구현, 구조 변경 `reshape` → 구현, 검증 `verify` → 검증 |
  | 성능 개선 `performance` | 기준 측정 `baseline` → 원인 조사, 개선 `improve` → 구현, 재측정 `measure` → 검증 |
  | 반증 리뷰 `adversarial-review` | 범위 정리 `scope` → 설명, 반증 `attack_a`·`attack_b` → 반증, 심사 `verdict` → 심사 |
  | 기술 결정 `tech-decision` | 질문 정리 `frame` → 설계, 두 안 `option_a`·`option_b` → 조사, 심사 `decide` → 심사 |
  | 코드 조사 `code-investigation` | 범위 정리 `scope` → 설명, 동작 추적 `trace` → 설명, 기록 조사 `history` → 설명, 작성 `write` → 작성 |

- 단일 에이전트와 조사 팀은 안내 데모가 함께 여는 템플릿이고 스킬을 지정하지 않는다.
- 목표에서 만드는 팀은 [AI로 팀 만들기](team-assistant.md#새-팀)의 제안이다. 제안은 팀 패턴 하나를 고른다. 패턴은 열한 가지다: 단일 에이전트, 작성·검토, 조사·작성·검토와 템플릿 패턴 여덟(구현·검토, 기능 구현, 버그 수정, 리팩터링, 성능 개선, 반증 리뷰, 기술 결정, 코드 조사). 로컬 제안은 모델을 부르지 않고 목표의 낱말로 고르며, 모델 제안은 전송 한 번에 요청 한 번으로 고른다. 별도 역할이나 작업 순서를 정하지 않고 요청형 자문만 요구한 목표에서는 모델 답이 별도 단계를 추가하거나 필수 정책으로 바꾸면 같은 목표의 로컬 제안을 보여 주고 바꾼 이유를 알린다. 별도 역할이나 순서를 명시한 목표와 모델 연결·요청 실패는 실패와 다시 시도를 보인다. 제안에는 일이 늘어나는 대안 패턴을 함께 고를 수 있고, 패턴을 바꾸면 역할 문구와 기준은 그 패턴의 기본값이다. 패턴의 이름은 템플릿 카드의 이름과 같다. 적용한 뒤의 이름·요청·기준·역할 문구·검토 횟수·최종 승인은 편집기에서 고친다. 최종 승인은 어느 패턴에서도 꺼진 채로 제안된다. 로컬 제안은 켜지 않고, 모델 제안은 목표가 결과를 승인받겠다고 적었을 때만 켠다.
- 리소스 행은 이름, 범위(개인·프로젝트), 상태, 실패 원인과 다음 행동을 보인다. 스킬은 리소스 보기에 나열하지 않는다. 지금 서버가 자원별로 알려 주는 원인은 루트 `SKILL.md` 패키지의 Skill 판정이며 그 패키지 행에 보인다.
  - 패키지 설치 거부(크기·파일 수 한도)는 저장되지 않고, 하네스 보고 코드(`extension_load_failed`, `resource_invalid`, `policy_denied`, `sdk_start_failed`, `packages/contracts/src/harness.ts`)는 실행의 `harness.load_failed` 이벤트로만 남는다. 그래서 리소스 행에는 보이지 않는다.
  - 충돌한 도구 이름처럼 계약에 없는 세부도 보이지 않는다.
- 리소스의 "관리"는 라이브러리 주소에 `settings=<section>`·`settingsProject=<id>`를 더해 [설정 모달](../workbench.md#문맥형-설정)을 그 위에 열고, 그 리소스를 고른 채로 보인다. 보관된 리소스면 보관한 항목 보기를 켜고 고른다. 고르는 목록이 없는 패키지는 그 패키지의 줄로 가서 초점을 둔다. 리소스가 더는 없으면 구역만 연다. 고를 리소스는 주소에 싣지 않으므로 그 주소를 따로 열면 구역만 열린다. 모달 안에서 사람이 다른 항목을 고르면 그 선택을 따른다. 편집·신뢰·설치·미저장 보호는 설정 모달이 소유한다. 모달을 닫으면 라이브러리의 같은 보기와 스크롤로 돌아온다.
- 세션의 팀 선택기에서 "Corral 만들기·관리"는 `/library/teams?project=<id>&returnTo=<세션 주소>`로 간다. 돌아가기는 세션의 초안·탭을 그대로 복원한다.

## 계약

- 팀 목록·상세·생성·복제·삭제는 기존 Corral API와 revision 규칙을 그대로 쓴다. 명시한 Corral이 삭제된 세션은 조용히 auto로 바뀌지 않는다.
- 템플릿에서 만든 팀의 도구와 연결은 템플릿이 정한다. 첫 저장과 재시도는 [팀 편집기의 저장 규칙](canvas.md#계약)을 따르며, 저장한 뒤의 팀은 템플릿과 연결되지 않는다.
- 읽기 전용 템플릿의 모든 역할은 `write_file`·`delete_file`·`move_file`·`run_command`·`preview_action`을 갖지 않는다. 그 밖의 템플릿에서는 위 표의 파일을 바꾸는 역할만 `write_file`·`delete_file`·`move_file`을, 명령을 실행하는 역할만 `run_command`·`preview_action`을 갖는다.
- 빈 캔버스를 뺀 모든 템플릿은 진단 없이 strict 컴파일을 통과한다. 구현·검토는 검토 루프로 시작한다. 기능 구현, 버그 수정, 리팩터링, 성능 개선의 루프는 검토 자리 대신 검증 자리(성능 개선은 재측정)가 판정한다. 템플릿과 초안, 자동 팀의 검토 루프는 `exhausted`가 `next`와 같은 다음 단계로 이어진다: 상한에 닿으면 사람에게 묻지 않고 마지막 후보로 끝까지 가며, 마지막 검토는 결과와 함께 남는다. 템플릿의 구조는 검증하지만 역할 문구의 품질은 보장하지 않는다.
- 템플릿과 목표 초안이 만드는 자리는 맡은 일과 기본 지시를 나눠 갖는다([에이전트 라이브러리](agent-library.md#맡은-일과-기본-지시) 11). 역할 문구의 맡은 일이 그 자리의 단계 지시가 되고, 공통 작업 규칙이 역할의 지시가 된다.
- 로컬 추천과 모델 제안은 목표에서 작업 진행 중 자동 관찰을 명시하면 `observeWork`를 함께 제안한다. 요청할 때의 조언이나 원고 리뷰만으로는 관찰을 켜지 않는다. 모델 답이 원래 요청에 없는 자동 관찰을 제안해도 제안의 관찰은 꺼져 있다. 원래 요청의 명시적인 관찰 선택은 모델 답에서 빠졌거나 잘못된 답에서 로컬 제안으로 복구할 때도 보존한다. 제안에서 관찰을 별도로 켜거나 끌 수 있고, 켜면 모든 작업자에 적용되는 모델·검토 간격·마지막 검토 시점과 추가 호출을 표시한다. 대안 패턴으로 바꿔도 이 선택을 유지한다. [공통 Outrider](shared-outrider.md)
- 제안의 계획(`TeamPlan`)은 패턴, 이름, 요청, 기준, 역할 문구, 검토 횟수, 최종 승인 여부와 선택적인 공통 Outrider 제안을 담는다. 자문 요청은 실행 단계나 권한을 추가하지 않는다. 작업자가 받아서 반영할 리뷰와 제출 전 통과 조건이 모호한 목표에는 의견 수신과 필수 통과 중 한 가지를 확인한다. 제출 전 필수 통과가 필요한 제안은 해당 정책이 구성될 때까지 적용할 수 없다. 목표가 제출 전 통과를 명시하면 모델이 정책을 생략해도 제안에서 확인한다. 필수 통과를 고르면 출력 입력과 수정할 생산자를 표시한다. 사용자가 그 대상을 확인한 뒤 편집기와 같은 [필수 출력 검토](shared-outrider.md) 명령으로 만든 결과를 초안에 적용한다. 대안 패턴으로 바꿔 후보가 달라지면 새 대상 확인이 필요하다. 도구·연결·한도·스킬은 패턴이 정하며 템플릿 패턴 여덟은 같은 이름의 템플릿과 같은 구조·도구·스킬을 쓴다. 계약에 없는 패턴·역할 자리·필드가 든 모델 답은 쓰지 않는다. 최종 승인 여부를 적지 않은 모델 답은 승인 없음으로 읽는다. 그래서 모델 답이나 붙여 넣은 글이 도구 권한이나 연결을 줄 수 없다.
- 팀을 고르지 않은 세션의 자동 구성은 이 확장과 무관하게 지금의 세 구성(단일 에이전트, 작성·검토, 조사·작성·검토)만 고른다. 자동 구성의 선택 프롬프트와 구성 버전은 바뀌지 않는다. 자동 구성과 대화의 리드는 역할 지시 하나에 맡은 일과 공통 규칙을 함께 담는 형태를 그대로 쓰고, 단계 지시를 쓰지 않는다.
- 패턴 선택의 품질은 실제 모델로 한 번 재서 기록한다(`tests/live/team-draft.live.test.ts`, 일반 CI에서는 돌지 않는다). 측정하지 않은 정확도를 화면이나 문서에서 주장하지 않는다.
- 리소스 보기는 읽기 전용이다. 저장할 폼은 에이전트·스킬 보기의 대화상자에만 있다.
- 리소스 조회가 실패하면 그 묶음만 실패와 다시 시도를 보이고 다른 묶음은 유지한다. 조회 실패를 "없음"으로 표시하지 않는다.
- 브라우저 데모에서 서버 전용 리소스는 "로컬 서버에서 사용" 상태 하나로 보인다.

## 수용 시나리오

```gherkin
Given 프로젝트 A에 저장한 팀 두 개가 있다
When 사용자가 /projects/A#corrals 를 연다
Then 주소가 /library/teams?project=A 로 바뀌고 두 팀이 보인다
And 뒤로가기는 이전 작업 화면으로 간다

Given 새 Corral을 열었다
When 아무것도 고치지 않고 라이브러리로 돌아간다
Then 확인 없이 떠나고 팀은 생기지 않는다
When 다시 열어 요청을 고치거나 템플릿 사본을 연 뒤 떠난다
Then 저장하지 않은 변경을 버릴지 묻고, 버린 뒤 새 Corral을 열면 빈 팀이다

Given 템플릿 사본의 이름을 같은 프로젝트에 있는 팀의 이름으로 고쳤다
When 처음 저장한다
Then 번호를 붙인 이름을 알리고 그 팀의 편집 주소로 바뀐다
And 보고 있던 보기와 행이 그대로이고 되돌리기는 저장 전의 마지막 편집을 되돌린다

Given 저장 전인 팀의 첫 저장이 실패했다
Then 초안과 주소가 그대로이고 실패 원인이 보인다
When 다시 저장하거나 저장을 기다리는 사이 저장을 다시 누른다
Then 같은 사본에서 팀이 두 개 생기지 않는다

Given 라이브러리 리소스에 Hook이 둘 있다
When 둘째 Hook의 "관리"를 누른다
Then 설정 모달이 Hook 구역에서 둘째 Hook을 고른 채로 열린다
And 모달을 닫으면 라이브러리의 같은 보기로 돌아온다

Given 라이브러리 리소스에서 MCP 서버의 "관리"를 누른다
When 설정 모달에서 값을 바꾸고 저장하지 않은 채 닫으려 한다
Then 저장하고 이동 / 버리기 / 계속 편집을 묻는다

Given 템플릿 보기를 연다
When "기술 결정"의 사본을 저장한다
Then 저장한 팀은 strict 컴파일을 통과하고 어떤 역할에도 파일 쓰기·명령 도구가 없다
And 같은 템플릿을 한 번 더 저장하면 이름이 겹치지 않는 별개의 팀이 된다

Given 템플릿 보기를 연다
When "반증 리뷰"의 사본을 저장한다
Then 두 반증 자리는 명령 실행 도구를 갖고 파일 쓰기 도구는 어느 역할에도 없다
And 두 반증 자리는 서로 다른 모델 자리를 쓴다

Given 템플릿 보기를 연다
When "기능 구현"의 사본을 연다
Then 설계 · 구현 · 검증 자리마다 기본 제공 에이전트가 지정한 스킬이 보인다

Given "구현·검토" 템플릿으로 만든 팀이 있다
When mock 실행을 시작한다
Then 검토가 한 번 돌려보낸 뒤 통과하고 실행이 결과까지 간다

Given 목표 "로그인 후 가끔 흰 화면이 뜨는 버그가 있어. 원인을 찾아서 고쳐 줘"를 적고 로컬 제안을 고른다
Then 버그 수정 패턴의 초안이 원인 조사 · 수정 · 검증 역할과 함께 보이고 모델 요청은 0회다
And 저장한 팀에서 파일을 바꿀 수 있는 역할은 수정뿐이다

Given 모델 답이 계약에 없는 패턴 이름이나 도구 목록 필드를 담고 있다
Then 그 답으로 초안을 만들지 않고 실패와 다시 시도를 보인다

Given 팀을 고르지 않은 세션에서 같은 목표로 요청을 보낸다
Then 자동 구성은 지금의 세 구성 중 하나만 고른다

Given 루트에 SKILL.md가 있는 패키지를 설치했다
When 리소스 보기를 연다
Then 그 행에 Skill로 판정했다는 원인과 다음 행동이 보인다
```

## 보안·성능·접근성

- 리소스 행은 로컬 경로·토큰을 보이지 않는다.
- 보기 전환은 디자인킷 Tabs이고 목록은 Table이다. 좁은 화면에서 탭 줄은 가로로 스크롤되고 고른 탭이 보이는 자리로 온다.
