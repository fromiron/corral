# 개인 하네스 상세 계약


구체적인 DTO·IPC는 `packages/contracts/src/harness.ts`와 `packages/adapter-pi/src/protocol.ts`의 현재 정의를 따른다. 과거 계획의 SDK 호출 예시를 현재 라이브러리 API로 복사하지 않는다.

## H2 실행·권한·기록

- SDK는 실행 소유 worker에서 구동한다. 서버 프로세스가 native 확장을 직접 로드하지 않는다. 기존 core worker와 SDK worker의 호환 경로를 보존한다.
- turn·압축·재시도·확장 중첩 모델 호출은 Corral permit을 받고 같은 Run의 사용량으로 기록한다. 자격 증명 없는 proxy와 host의 요청별 허가 경계를 우회하지 않는다.
- 도구는 최종 인자·descriptor·현재 정책으로 승인한다. Corral broker를 거치지 않는 Pi 기본 도구로 교체하지 않는다. 승인 뒤 변경·예외·unknown 효과는 fail closed다.
- 도구 승인 카드는 해당 요청의 대화 안에서도 승인·거절할 수 있다. 검증한 호출 본문에서 파일 경로와 쓸 내용 또는 교체 전후를 먼저 보여 주며, 현재 파일을 읽지 않았다면 전체 파일 diff나 새 파일이라고 주장하지 않는다. 원시 인자와 지문은 접힌 상세 정보에 남긴다. 한 번 허용은 현재 호출에만 적용된다. 이 실행 동안 허용은 같은 Run에서 지문이 같은 호출을 다시 묻지 않고 허용한다. 지문은 도구 등록, 최종 인자, 하네스 snapshot과 정책 revision이다(Run은 시작부터 끝까지 한 Paddock에 묶여 있다). 명령 실행(`run_command`)의 지문은 여기에 실행 파일과 그 내용 hash, 인자, 셸, 작업 폴더, 환경 hash, 제한 시간, 실행 방식, 사본 identity가 더해진다. 호출마다 새로 생기는 식별자와 작업 트리의 내용은 들지 않으므로, 허용한 명령은 그 Run이 파일을 고친 뒤에도 다시 묻지 않고 실행된다. 서버가 실행 직전에 하는 호출별 계획 대조는 그대로다. 이 허용은 그 Run이 끝나면 사라지고 다른 Run, 다른 세션, Harness의 규칙에는 남지 않는다. 지문이 하나라도 다르면 다시 묻는다. 같은 지문으로 이미 기다리던 다른 승인 카드는 함께 허용되어 닫힌다. 이 허용으로 넘어간 호출은 어느 승인에 근거했는지와 함께 기록하고 대화의 도구 줄에 허용된 호출로 보인다. Run을 넘는 규칙은 하네스 설정으로 직접 이동해 별도로 저장한다. 대화 밀도·작업 기록 접힘으로 승인 카드를 숨기지 않는다.
- 역할 allowlist·resource revision·directive·요청 context를 고정하고 실제 payload의 hash·크기를 기록한다. 공개 이벤트에 본문·키·내부 경로를 노출하지 않는다.
- 필수 확장 로드 실패는 다른 runtime으로 조용히 fallback하지 않는다. 취소는 소유 worker·MCP·codemode의 실제 종료와 늦은 이벤트를 구분한다. Task/Run 완료는 Coordinator가 확정한다.
- `sdk-worker.ts`, `worker.ts`, `worker-tools.ts`, `worker-leases.ts`가 구현 입구다. SDK 세션의 settled가 곧 제품 성공은 아니다.

## H3 리소스·역할·UI

- 발견 → 설치 검토 → 설치 → hash별 신뢰 → 바인딩 → 실행은 별개다. 발견·미리보기는 확장 코드를 실행하지 않는다.
- 실행 자산과 `HarnessProfileRevision`은 불변이다. 내용 변경은 신뢰 재검토 대상이며 실행 중 snapshot을 바꾸지 않는다. reload로 현재 Run 자산을 교체하지 않는다.
- 기본 Harness는 고정한 revision의 이름과 번호를 표시한다. 새 revision 저장·새로고침으로 고정 버전을 최신으로 바꾸지 않으며, 과거 revision의 이름은 해당 불변 기록에서 읽는다.
- 설정에서 사용 중인 버전은 현지화한 범위와 프로젝트 이름을 우선 표시한다. 내부 참조 ID는 접힌 진단 정보에서 선택·복사할 수 있으며 표시 변경으로 고정 binding을 바꾸지 않는다.
- 리소스 문서의 설치 검토는 사용자가 입력한 표시 이름을 해당 문서의 이름으로 먼저 보여 준다. 같은 묶음의 다른 스킬 이름은 바꾸지 않는다. 스킬 frontmatter의 내부 이름과 원문은 유지하며, 내부 이름은 접힌 검토 상세에서 확인할 수 있다.
- 실행의 **적용된 Harness**는 기록된 스킬의 해시와 항목에 해당하는 라이브러리 표시 이름을 우선한다. 표시 이름을 조회하지 못하면 스냅샷에 기록된 이름을 쓴다. 접힌 항목을 펼치면 기록된 내부 이름, 패키지 버전과 해시를 확인할 수 있다. 표시 이름을 조회해도 실행 기록은 바뀌지 않는다.
- 개인 → 프로젝트 → 역할 → 실행의 scope를 구분하고, 하위 설정이 필수 정책·허용 도구 제한을 확대하지 못한다.
- 정적 미리보기와 실제 Run은 같은 해석 경로를 사용한다. 설치·선택·읽기·payload 전달·실제 수행은 다른 상태다.
- Harness 편집에서는 선택한 저장 revision의 적용 설정 미리보기와 정책·상속·도구 요약을 상세 편집보다 먼저 확인할 수 있다. 미저장 편집을 이미 적용된 설정으로 표시하지 않으며 프로젝트·revision이 바뀌면 이전 미리보기를 유지하지 않는다.
- 사용자 홈 설정은 명시적 복사 import만 허용한다. 실행용 HOME/XDG 분리는 설정 충돌을 줄이는 장치이며 OS 보안 격리 자체가 아니다. `strict` 역할에 trusted-native 확장을 우회 결합하지 않는다.
- 확장 UI 질문은 원래 실행·요청 ID·timeout을 가지며 stale/중복 답변·종결 뒤 응답을 거절한다.
- 구현 입구는 `apps/server/src/harness/`, Studio `workbench/harness/`, storage의 revision·binding이다.

### 역할의 스킬 선택

`AgentRole.skills`(`{ resourceHash, entry }`의 목록, [스킬 라이브러리](features/skill-library.md))는 그 역할이 쓸 선택적 스킬을 정한다. 편집기 미리보기, 서버의 실행 준비, Coordinator, 작업자 어댑터는 아래 한 가지 해석 결과를 쓴다.

| 고정 Harness(`role.harness`) | `role.skills` | 해석 |
|---|---|---|
| 없음 | 없음 | 하네스를 해석하지 않는다. 이 필드가 생기기 전과 같은 실행 경로다. 팀을 열거나 저장하는 것으로 필드를 채우지 않는다. |
| 있음 | 없음 | 고정 revision과 개인·프로젝트·역할·실행 계층의 병합 결과를 그대로 쓴다. |
| 있음 또는 없음 | 빈 목록 | 상위 계층과 고정 Harness가 정한 필수 스킬(`required` 또는 `mandatory`)만 남는다. 선택적 스킬은 0개다. |
| 있음 또는 없음 | 목록 | 필수 스킬과 고른 스킬을 합친다. 같은 해시·항목은 한 번만 쓴다. 필수가 아닌 상속 스킬은 목록에 없으면 빠진다. |

- **기준 계층.** 고정 Harness가 있으면 그 revision이 역할 계층이다. 없으면 버전이 고정된 **내장 최소 정책**이 역할 계층이다. 어느 쪽이든 개인 기본과 프로젝트 기본이 있으면 지금과 같은 순서로 그 위에 겹치고 제한한다. 스킬만 고른 역할은 내장 최소 정책에 고정한 역할과 같은 규칙으로 해석된다.
- **내장 최소 정책.** 기준 참조는 `role-skills-minimal`의 revision 1이다. `strict`이고, 허용 목록은 어댑터의 Corral 브로커 도구 이름 전체(`WorkerTool`)와 스킬 본문을 읽는 `read`의 합집합이다. 따라서 고정 Harness가 없는 역할이 받던 도구는 파일 권한과 편집 방식에서 파생되는 `read_hashline`·`edit_hashline`까지 유지한다. 역할의 `allowedWorkTools`·`allowedCollaborationTools`, 편집 방식, 협업 관계가 실제 도구를 제한한다. `trusted-native`가 필요한 명령 실행·앱 미리보기와 조작은 고정 Harness가 없는 경우와 마찬가지로 사용할 수 없다. 쓰려면 역할에 실행 정책을 직접 고른다. Pi의 쓰기·편집 도구, 시작 명령, 검사, LSP, MCP 서버, 확장, codemode가 없다. 처음 필요할 때 설치마다 이 프로필만 한 번 저장하고 역할마다 프로필을 만들지 않는다. 선택기를 열거나 미리보는 동작은 다른 프로필이나 기본값을 만들지 않는다.
- **권한.** 스킬 선택은 도구를 더하지 않는다. 스킬 본문이 외부 도구를 말해도 그 도구의 권한이 생기지 않는다. 상위 계층의 `strict`, 허용 도구 교집합, 필수 스킬은 어느 경우에도 유지된다. 고정 Harness가 없는 역할은 기본값의 확장 가운데 필수가 아닌 것을 받지 않는다. 필수 확장은 `strict`가 거절하며, 이때 그 역할에 실행 정책을 직접 고르라고 안내한다.
- **모드.** 고른 스킬은 요청할 때 쓰는 스킬(`auto`)로 전달한다. 상속이 같은 항목에 이미 정한 `mandatory`·`explicit`과 `required`는 약화하지 않는다.
- **고른 항목을 쓸 수 없을 때.** 고른 항목의 패키지가 없거나 꺼졌거나, 그 해시를 신뢰하지 않거나, 필수 스킬과 내부 이름이 같은 다른 해시이면 실제 시작을 거절한다. 조용히 빼고 시작하지 않는다. 미리보기는 역할과 항목별로 원인(`missing`, `disabled`, `untrusted`, `name_conflict`)을 돌려준다.
- **스냅샷.** 해석 결과는 기준 참조, 계층별 고정 revision, 스킬의 해시·항목·모드, 스냅샷 해시를 담는다. 고른 스킬이 달라지면 스냅샷 해시가 달라진다. 시작한 Run은 시작 때의 스냅샷으로 끝나고, 이후 라이브러리·기본값 변경은 다음 실행에만 적용된다.
- **실행 재정의.** 고정 Harness가 없는 역할의 실행별 Harness 재정의는 지금처럼 거절한다.
- **브라우저 데모.** 해석기가 없으므로 스킬을 고른 역할은 고정 Harness 역할과 같이 실행할 수 없고 이유를 보인다.
- **전달의 구분.** 쓸 수 있음(스냅샷에 있음), 본문을 읽음(`skill.read`), 모델 요청에 전달됨(payload 기록), 결과에 반영됨은 서로 다른 사실이다.

## H4 코딩 도구와 LSP

- Pi read/edit/write의 사용자 계약을 Corral broker에 연결한다. execution별 읽기 근거·원본 hash·직렬화·원자 쓰기·불변 diff를 유지한다.
- BOM/CRLF/Unicode·부분 읽기·원본 변경/삭제·scope 밖 경로·취소를 처리한다. 모델 인자로 OS 임의 경로를 허용하지 않는다.
- LSP 조회와 text-edit 제안·사용자 적용은 별개다. 임의 command·파일 생성/삭제/rename resource operation은 지원하지 않는다. 기존 UTF-8 파일의 선언적 edit만 취급한다.
- 다중 파일 적용은 파일별 결과를 보존한다. stale/부분 실패를 전체 성공으로 표시하거나 자동 rollback/replay하지 않는다. Git tree와 bytes 일치 및 적용 직전 재검증을 유지한다.
- 기존 Pi edit를 자동 대체하지 않는다.

## H5 등록 검사

- Paddock의 고정 tree를 별도 검증 사본에서 등록 argv로 실행한다. 일반 명령/service(ABS-01)와 같은 기능으로 합치지 않는다.
- tree·명령·설정·실행 fingerprint에 승인과 보고서를 묶는다. 취소·stale·실패·unknown을 pass로 바꾸지 않는다. 출력 크기·시간·프로세스 소유권과 정리를 검증한다.
- 보고서의 실행 상태와 품질 판정은 다르다. schema 통과만으로 실제 검사 성공을 인정하지 않는다.

## H6 검토·제한된 개선·평가

- 기준 파일/hash와 산출물 버전을 고정하고 모델이 바꾼 기준으로 자기 결과를 승인하지 못하게 한다. 실제 검사 실패가 모델의 긍정적 검토보다 우선한다.
- 시도·수정 횟수 상한, 같은 실패/출력 반복·무진전 중단과 이유를 유지한다. 시간·출력 토큰 상한은 없다. 모델 호출 수에는 상한이 없다([제품 계약 §9](product-contract.md#9-사용량과-자원-정책)).
- `personal_harness`의 다섯 비교군과 calibration/holdout을 보존한다. fixture 성공은 실제 모델 품질 향상 증거가 아니다. [Evaluation](../guides/evaluation.md)을 따른다.
- CLI와 같은 평가 경로를 사용하며 기존 Run snapshot은 변경하지 않는다. 텍스트 fixture와 mock/live 증거를 구분한다.

## H7–H8 반복·MCP·codemode

- 항목별 입력을 분리하고 앞 항목 성공 전 다음 항목을 시작하지 않는다. 부모 취소·깊이·소환 상한과 같은 사본의 writer 소유권을 유지한다.
- MCP는 등록 서버·정확한 도구 allowlist·인증 binding을 사용한다. stdio 프로세스, HTTP/OAuth, probe 및 실제 실행의 수명과 취소 소유권을 구분한다.
- codemode의 중첩 도구도 같은 승인 경로를 사용한다. 별도 무제한 실행 엔진을 만들지 않는다. worker 상한과 host 공통 process admission을 모두 적용한다.
- native 확장·원격 MCP의 신뢰는 코드 불변성이나 sandbox 보장이 아니다.

## 추적과 검증


기존 `core/test/harness`, `review-recipe`, `items`, adapter의 SDK/MCP·리소스, server의 harness/LSP/검사 회귀에서 변경 범위의 반례를 고른다. 새 실행 결과는 현재 후보·OS·mock/live를 기록하며 과거 보고서의 수치를 덮어쓰지 않는다.

MCP 연결 검사 실패는 인증, 연결 거부, 이름 조회, 시간 초과, HTTP 상태처럼 허용된 범주만 프로세스 경계를 넘어 전달한다. 주소·키·서버 오류 본문은 전달하지 않는다. 종료 확인 실패와 취소는 연결 실패로 덮지 않으며, 원래 명령 receipt의 실패 결과도 같은 안전한 분류를 유지한다.
