# Corral 팀 편집기 디자인안

[구현 계획](team-composition-and-agent-library.md) · [팀 구성 시안](team-composition-prototype.html) · [필수 검토 흐름 그래프 예시](team-composition-prototype.html#graph-review) · [AI로 팀 만들기 시안](team-composition-prototype.html#ai-builder)

**첫 화면에서 답할 질문은 세 가지다. 누가 무슨 일을 하는가, 무엇을 받아 쓰는가, 누구의 결과를 받는가.** 팀을 만들기 위해 에이전트·스킬 라이브러리부터 채워 둘 필요가 없어야 한다. 반대로 여러 팀에 쓸 작성자를 먼저 정의하려는 사람은 팀 없이 라이브러리에서 시작할 수 있어야 한다. 아래는 구현할 경험이다. 예시 데이터는 화면 시연용이다.

## 0. 시안에서 가져오는 것과 바꾸는 것

시안은 **동작과 순서**의 근거다. 화면 틀과 겉모습은 현재 제품과 [DESIGN.md](../../DESIGN.md)를 따른다. 시안의 겉모습을 그대로 옮기면 지금 제품보다 후퇴하는 곳이 아래 표다. 구현 기준은 오른쪽 열이며, 화면별 계약은 [팀 구성](../specs/features/team-composition.md) · [에이전트 라이브러리](../specs/features/agent-library.md) · [스킬 라이브러리](../specs/features/skill-library.md) 명세가 가진다.

| 시안의 모습 | 후퇴인 이유 | 구현 |
| --- | --- | --- |
| 사이드바에 **라이브러리 › 팀·에이전트·스킬** 그룹과 프로젝트 팀 목록 | 사이드바 주 메뉴와 프로젝트 그룹이 유일한 내비게이션이다. 화면이 자기 옆 메뉴를 만들지 않는다. | 라이브러리 화면의 디자인킷 Tabs에 **팀 · 에이전트 · 스킬 · 템플릿 · 리소스**를 둔다. 사이드바는 그대로다. |
| 화면마다 큰 제목과 소개 문장. 팀 이름이 사이드바·경로·제목에 세 번 | 화면 이름은 경로 막대에 한 번만 쓴다. 제목 아래 소개 문장은 쓰지 않는다. | 경로 막대 → 한 줄 도구 막대 → 내용. 팀의 요청과 완료 기준은 팀 구성 목록의 첫 행이 보인다. |
| 하단 고정 저장 바(상태 문장·되돌리기·팀 저장)와 상단의 모의 시험, 그 위의 AI 바 | 같은 결정의 동작이 위아래로 흩어지고 가로 띠가 네 겹이 된다. 비활성 저장 버튼이 이미 말하는 상태를 문장으로 되풀이한다. | 경로 막대 아래 **한 줄**: 왼쪽에 보기 탭, 오른쪽에 되돌리기·다시 하기·모의 시험·저장·더 보기. 하단에는 접힌 **AI로 팀 편집** 한 줄만 둔다. |
| 행마다 테두리 카드, 같은 로봇 아이콘 타일, 오른쪽 화살표 | 카드는 문법이 아니다. 묶음이나 선택을 말하지 않는 테두리·타일은 밀도만 낮춘다. 역할 10개가 한 화면에 들어오지 않는다. | 목록은 행이다. 종류 아이콘 16px, 이름, 한 줄 요약, 끝에 내는 결과. 라이브러리 목록은 지금의 Table과 옆 상세를 쓴다. |
| 선택을 파란 테두리와 토큰 밖의 옅은 파란 바탕으로 표시 | 선택 행은 사이드바 활성 행의 채움 하나로 통일돼 있다. 강조색은 상태에만 쓴다. | 선택 행 채움(`chosenRow`). |
| 상세가 페이지 격자 안의 테두리 카드이고, 항목마다 **편집 / 자료 변경** 버튼이 대화상자를 연다 | 한 줄 고치려고 대화상자를 여닫는다. 지금 설정 시트는 그 자리에서 고친다. | 오른쪽에 붙은 상세 패널. **맡은 일**은 그 자리의 입력란이고, 받는 자료는 행에서 바로 바꾼다. 여러 개를 고르는 스킬·에이전트만 대화상자를 쓴다. |
| 흐름 그래프를 세로 그림으로 다시 그림 | 제품에는 끌어 놓기·키보드·자동 배치가 되는 캔버스가 있다. | 기존 캔버스를 그대로 연다. |
| AI 대화의 말풍선·“AI” 머리표·보내기 버튼 | 대화 입력은 디자인킷 `InputMessage` 하나다. | 같은 입력창과 대화 본문 구성을 쓴다. |
| 새 빈 팀에서 **최종 결과 선택** 카드가 먼저 선택돼 있음 | 아직 아무도 없는 팀에서 결과부터 고르게 한다. | 빈 팀은 요청 행이 선택된 채 열리고, 목록에는 **에이전트 추가**가 있다. 첫 에이전트를 넣으면 최종 결과가 함께 생긴다. |

**목록의 문법.** 팀 구성은 일의 순서가 조직 원리인 작업 흐름이다. 요청 → 단계 → 최종 결과 → 자문이 모두 같은 종류의 행이고, 오른쪽 패널은 고른 행의 설정이다. 아무것도 고르지 않았을 때 패널은 팀의 요청과 완료 기준을 보인다. 새 항목(판정, 반복, 참조 팀, 도우미)이 생겨도 새 컴포넌트 종류 없이 행과 들여쓰기로 들어온다. 순번은 붙이지 않는다. 병렬·조건·반복에서 거짓 순서를 말하지 않기 위해서다.

**맡은 일의 한 칸.** 사람은 지시가 어느 필드에 저장되는지 고르지 않는다. 그 자리에 재사용 원본이 있으면(라이브러리·기본 제공에서 왔거나 단계 지시가 이미 있으면) **맡은 일**은 이 팀의 단계 지시를 고치고 원본의 지시는 **기본 지시**로 접어 둔다. 원본이 없는 자리(직접 만든 에이전트, 예전 팀)는 **맡은 일**이 그 역할의 지시 자체다.

**좁은 화면.** 팀 구성 목록의 행은 이미 요약이다. 폭이 좁으면 행을 누를 때 상세가 목록 자리를 대신하고, 상단의 **팀 구성** 돌아가기가 같은 행으로 포커스를 돌린다.

## 1. 어디서 시작하는가

| 하려는 일 | 시작점과 첫 행동 | 다음에 보이는 것 |
| --- | --- | --- |
| 팀을 처음 만든다 | **라이브러리 → 팀 → 새 Corral**. 기존의 목표 초안·템플릿·직접 구성을 유지한다. 빈 팀에서 **에이전트 추가** | 기본 제공 또는 저장해 둔 에이전트. 저장된 에이전트가 0명이면 바로 기본 제공 역할을 보여준다. 라이브러리 등록을 요구하지 않는다. |
| 여러 팀에서 쓸 작성자를 준비한다 | **라이브러리 → 에이전트 → 에이전트 만들기** | 이름·기본 지시·사용할 스킬. 이 화면에서 스킬을 찾아 여러 개 붙이고 **에이전트 저장**을 누른다. |
| 재사용할 업무 절차를 준비한다 | **라이브러리 → 스킬 → 스킬 만들기** 또는 **가져오기** | 이름·언제 사용하는지·지침. 로컬 파일과 패키지는 기존 설치 검토를 거친다. 에이전트 연결은 나중에 해도 된다. |
| 팀을 쓰다가 스킬이 필요해진다 | **작성자 → 스킬 추가 → 새 스킬 만들기** | 만들기를 끝내면 원래 작성자의 선택기로 돌아온다. 팀의 요청·스크롤·다른 선택을 유지한다. |

**팀을 만들기**를 전체 제품의 첫 경로로 두고, 각 라이브러리는 직접 들어온 목적에 맞는 주 버튼 하나를 가진다. 두 라이브러리를 거치는 등록 마법사를 만들면 기존 에이전트 한 명으로 시험하려는 사람에게도 사전 작업이 생긴다. 크기가 큰 프로젝트에서는 이름·맡은 일·스킬 용도로 검색한다. 출처와 버전은 동명 항목을 구분하거나 갱신할 때 먼저 보인다.

### AI와 함께 팀을 만들거나 고치기

팀을 처음 만드는 사람에게는 역할의 이름보다 받을 결과가 먼저다. **새 Corral → AI로 팀 만들기**에서 “이 팀이 어떤 일을 하면 좋을까요?”라고 묻고 목적을 바로 적게 한다. 쓸 수 있는 예를 누르거나 자신의 말로 써도 된다. 수동 구성과 템플릿도 같은 생성 진입에서 계속 고를 수 있다. 기존 팀에서는 **팀 구성**과 **흐름 그래프** 양쪽의 편집 영역 하단에 **AI로 팀 편집**을 두고, 펼친 대화에서 현재 초안에 대해 묻거나 변경을 요청한다. 팀원의 실제 작업 대화·Outrider와 다른 목적이므로 버튼에는 항상 팀을 **만들기** 또는 **편집**한다는 말을 쓴다.

| 사용자 상황 | AI의 다음 응답과 사람이 결정할 일 |
| --- | --- |
| “매주 동네 행사 소식지를 만들고 싶어.” | “행사 목록은 직접 주시나요, 팀이 찾아야 하나요?”처럼 답에 따라 구성이 달라지는 질문 하나만 한다. **내가 자료 제공 / 팀이 자료 조사 / 직접 답하기**. “모르겠어, 추천해 줘”도 진행할 수 있다. |
| “목록은 내가 줄게.” | 가장 단순한 예로 **작성자 한 명 → 소식지**를 보여준다. 결과와 역할 차이를 한 문장으로 읽고, 필요하면 **작성 → 검토 통과 → 소식지** 같은 대안을 고를 수 있다. 사용자가 “작성자 한 명이면 돼”라고 처음부터 정했다면 중간 질문을 건너뛴다. |
| “이 팀에서 발행 전에 검토받게 해 줘.” | “작성자가 필요할 때 의견만 받을까요, 통과해야 제출할까요?” **필요할 때 의견 / 통과 후 제출** 중 고른다. 필수 검토를 명시했다면 바로 제안한다. 제출할 결과가 여럿일 때만 어느 결과에 적용할지 묻는다. |
| “지금 최종 소식지는 누가 내?” | 현재 초안에서 선택한 제출자와 결과 이름으로 바로 답한다. 설명만으로 충분한 요청에는 적용 버튼이 없다. |

쉬운 요청에는 추가 질문이 0개다. 한 번에 하나만 묻고, 보통 두 번 안에 비교할 수 있는 예시를 보여준다. 정확한 대상이나 권한을 정할 수 없으면 추측해서 적용하지 않고 고를 항목을 보여준다. 목표 예시를 눌러 문장을 채우는 조작에는 모델 비용이 들지 않는다. 추천에는 이유가 있어야 한다. “행사 목록을 직접 주시니 작성자 한 명으로 완성할 수 있어요”처럼 **지금 말한 목적과 선택**을 근거로 삼는다. 모델이 이미 아는 역할 수·실행 모드·스킬부터 되묻는 설문은 피한다. 팀 예시는 들어갈 사람·흐름·끝에 받을 결과를 함께 보인다. 자료 조사나 검토로 일이 늘어나는 경우 한 줄로 차이를 설명한다.

**적용 전.** 새 팀은 제안된 역할과 최종 결과를, 기존 팀은 실제로 달라지는 항목을 먼저 보여준다. 필수 검토라면 어느 원고를 누가 검토하고, 수정 요청이 누구에게 돌아가며, 최종 제출자가 누구인지 읽을 수 있어야 한다. 아직 공통 Outrider가 없는 팀에서 검토 정책에 필요하면 함께 추가된다는 사실도 표시한다. 저장된 에이전트나 스킬을 쓰겠다는 요청은 실제 프로젝트 라이브러리의 항목을 확인한다. 이름이 같거나 적합한 항목이 없으면 선택지를 묻거나 기본 역할로 만들 것을 제안한다.

**적용 후.** 사용자가 적용하면 두 보기의 같은 초안에 역할·흐름·결과가 실제로 생긴다. **흐름 그래프**에서 결과를 살펴보고 수동으로 계속 고칠 수 있다. Undo 한 번으로 그 제안 전체가 돌아간다. 앞서 손으로 바꾼 내용은 유지한다. 팀을 보관하는 **팀 저장**, 팀이 일을 시작하는 **시험 실행**은 사용자가 각각 선택한다. 기존 팀에서 대화를 접었다가 열면 같은 팀의 입력과 제안으로 돌아온다. 초안이 바뀐 동안 도착한 제안은 적용 전에 현재 초안을 기준으로 다시 계산한다.

데스크톱에서는 인스펙터·줌을 가리지 않게 편집 영역 아래에 자리를 확보한다. 접혀 있을 때는 **AI로 팀 편집** 한 줄을 보인다. 열 때 입력으로, 적용 직후에는 변경한 역할이나 최종 결과 행으로 포커스를 옮긴다. 390px에서는 한 줄 진입을 누르면 대화 시트가 열리고, 키보드를 띄워도 입력·주 동작까지 스크롤할 수 있다. 닫으면 같은 탭과 진입점으로 포커스가 돌아간다. 팀마다 항상 열려 있는 대화창이나 설명 없는 원형 아이콘은 두지 않는다. 제품은 모델을 부르는 동작과 로컬 예시·수동 경로를 구별한다. 모델 연결이 끊어져도 입력과 초안으로 돌아올 수 있다.

## 2. 팀 화면에서 읽는 순서

| 위치 | 평소 보이는 정보 | 언제 더 여는가 |
| --- | --- | --- |
| 상단 | 경로 막대의 팀 이름과, 그 아래 한 줄의 보기 탭·되돌리기·**모의 시험**·**저장**. 초안이 변경됐으면 시험 동작은 **저장하고 모의 시험**으로 표시한다. | 실행 패널에서만 **실제 모델 실행**을 고른다. 실제 시작 시 저장본·비용이 발생하는 모드·가용 모델을 확인할 수 있다. |
| 본문 | 팀이 할 일 → 실제 작업자와 흐름 → **최종 결과 · 작성자** | 생산자가 둘 이상이면 결과 행에서 **제출자 변경**. 카드 선택은 결과 출처를 건드리지 않는다. 복수 결과 팀은 실제 선택한 결과마다 이름과 생산자를 표시한다. |
| 선택한 역할 | **이 팀에서 맡은 일**, **받는 자료**, **사용할 스킬**. ‘기획자 · 기획안’처럼 실제 출처를 읽어 보여준다. | 자료를 고치거나 스킬을 붙일 때 해당 행을 연다. 모델·권한·정책은 **상세 설정**에 모은다. 상위 설정이 동작을 막을 때에는 이 자리에서 이유와 고칠 곳을 보여준다. |
| 팀 자문 | 설정이 있으면 **공통 Outrider · 팀 전체** 또는 실제 선택 범위. 없으면 **공통 Outrider 추가**만 제공한다. | *요청할 때 의견 받기*와 *진행 중 자동 관찰*은 팀에서 설정한다. *검토 통과 후 제출*은 정확한 최종 결과 행에서 켠다. |
| 현재 흐름 | 단순 팀은 실행 순서대로, 병렬은 갈래별로 묶어서 보여준다. | 사용자가 **흐름 그래프**를 열거나, 분기·Loop 경계를 바꾸는 조작을 할 때 기존 그래프로 들어간다. 같은 초안과 Undo를 사용하고 닫으면 원래 카드로 돌아온다. |

예를 들어 ‘동네 자전거 소풍 초대장’에서 기획자와 작성자를 연결하면 작성자의 **받는 자료**에 ‘기획자 · 기획안’이 보인다. 새 빈 팀의 첫 생산자는 자동으로 최종 출처가 된다. 이미 기획자의 결과를 받는 팀에 작성자를 추가하면 **작성자 결과 받기**를 그 자리에서 제공한다. 직접 고른 기존 출처는 계속 표시한다. 처음부터 두 역할을 가진 템플릿은 저장된 템플릿의 실제 출처를 보여준다.

**시험 버튼 한 번.** 유효한 저장 팀에서 **모의 시험**을 누르면 바로 시작해 시험 결과를 연다. 수정한 팀에서는 **저장하고 모의 시험** 한 번으로 확인한 초안을 저장한 뒤 그 revision을 시험한다. 저장 실패 또는 저장 중 재편집이면 실행을 보류하고 편집 중인 내용을 보존한다. 무료 모의 시험에 두 번째 시작 확인을 붙이지 않는다.

**평소 숨길 것.** 포트 이름, 입력 바인딩 종류, 호출 모드, 재시도 수, Harness revision, 도구 식별자는 상세 설정과 흐름 그래프의 편집 조작에 둔다. 필수 자료가 비거나 실행이 막히면 해당 카드에 원인과 조치 한 가지를 보인다. 브리프·모델·권한·그래프 오류를 한꺼번에 배지로 올리지 않는다. 일반 작업자, 호출 전용 도우미, 자문자와 검토자의 차이는 각자 등장하는 위치와 실제 동작으로 설명한다.

### 팀 구성과 흐름 그래프를 오가는 방법

팀 이름 아래에 **팀 구성 / 흐름 그래프**를 같은 수준의 보기로 둔다. 처음 팀을 만드는 사람은 팀 구성으로 시작한다. 그래프는 모델·권한이 있는 상세 설정을 거치지 않고 한 번에 연다. 보기를 바꿔도 현재 팀·초안·선택 카드와 Undo 기록은 같아야 한다.

| 그래프에 보이는 것 | 읽는 방법 |
| --- | --- |
| 방향이 있는 실행선 | 화살표가 다음에 실행할 단계를 가리킨다. 조건이 있는 선에는 실제 경로명을 붙인다. 독립적인 병렬 갈래와 합류점은 팀 정의에 존재할 때 표시한다. |
| 반복 경계와 되돌아가는 화살표 | 필수 검토 예시에서는 작성 → 검토 → 판정을 한 반복 범위로 읽는다. **수정 요청**은 같은 작성자로 돌아가고, **통과**는 반복 밖의 다음 작업 또는 최종 결과로 나간다. 상한 소진은 통과와 다른 종료다. 소진 시 확정할 수 없는 결과를 제출된 결과처럼 잇지 않는다. 일반 Loop의 소진 경로는 각 팀의 실제 정의를 따른다. 팀에 사람의 최종 승인도 설정했다면 검토 통과 뒤에 별도 단계로 표시한다. |
| 자료와 제출자 | 선택한 역할의 받는 자료와 결과 카드의 생산자를 확인한다. 실행상 바로 앞에 있는 검토자가 최종 작성자로 표시돼서는 안 된다. |
| 요청할 때 자문 | 공통 Outrider는 허용 대상과의 선택적 관계다. 필수 실행선을 추가하지 않는다. 결과별 의무 검토가 있는 팀에만 실제 검토 절차가 나타난다. |

그래프는 설계 가능한 경로를 보여준다. 실제 실행에서 몇 번째 회차에 수정했는지, 어떤 버전을 제출했는지는 시험 기록에서 확인한다. 390px에서도 그래프 진입을 상단에 유지하고 라벨이 잘리지 않게 한다. 탭은 좌우 화살표로 바꾸고 포커스는 선택한 탭에 남긴다. 노드에서 열었던 설정을 닫으면 해당 노드로 돌아온다. 키보드로 노드를 선택할 수 있고 그림을 보지 않아도 경로의 시작·조건·도착점을 읽을 수 있어야 한다. 현재 제품의 그래프 편집기는 [TeamGraphCanvas](../../packages/react/src/team-editor/TeamGraphCanvas.tsx)를 유지한다. 이 디자인 시안은 예시 팀의 선언 상태에서 계산한 그래프를 보여준다.

## 3. 스킬 하나를 만들고 작성자에게 붙이는 과정

| 지금 누르는 동작 | 즉시 남는 것 | 이 시점에 닫거나 취소하면 |
| --- | --- | --- |
| **스킬 추가**에서 기존 스킬 두 개 체크 | 선택기 안의 임시 선택. 아무것도 바꾸지 않았으면 적용할 편집도 없다. | 기존 작성자 설정이 그대로다. |
| 선택기 → **새 스킬 만들기** → **라이브러리에 저장** | 성공 응답 뒤 해당 자산이 라이브러리에 남는다. 검토·신뢰가 필요한 경우 같은 흐름에서 이유와 사용할 버전을 확인한다. 기존 체크를 보존하고 사용 가능한 새 항목을 체크해 선택기로 돌아온다. | 새 자산은 남는다. 선택기를 취소하면 작성자에게는 붙지 않는다. 저장 실패 시 지침과 체크를 유지한다. 미신뢰 버전은 **사용 승인 필요**로 표시하고 적용할 수 없게 한다. |
| **작성자에게 적용** | 이 팀의 작성자 초안에 선택 전체를 한 번 적용한다. 원본 편집에서 열었다면 **에이전트 원본에 적용**으로 대상이 달라진다. | 적용 후에는 초안이 수정된 상태다. 팀에서는 Undo 한 번으로 배정만 되돌릴 수 있다. |
| **팀 저장** / **에이전트 저장** | 각각 팀 revision / 라이브러리 원본 revision이 확정된다. | 다른 팀과 같은 에이전트의 기존 사본에는 전파하지 않는다. 실패하면 현재 초안에서 다시 시도한다. |

자산 생성과 배정을 구분하는 **저장됨 · 적용 전**은 새 자산을 만든 직후 그 행에만 잠시 표시한다. 평소에는 칩과 대상이 포함된 적용 버튼으로 충분하다. 스킬 선택에서 원본 편집까지 같은 이름의 ‘저장’을 연달아 누르게 하지 않는다. 여러 개를 골라도 적용은 한 번이다. 직접 만든 스킬의 신뢰를 사용자 몰래 승인하거나, 신뢰 승인과 팀 저장을 한 버튼에 묶지 않는다.

## 4. 목록·상세·갱신

- **에이전트 라이브러리.** 행에는 이름·맡은 일·선택한 스킬을 보인다. 상세에서 원본을 편집한다. 팀 선택기에서 **팀에 사본 추가**는 독립 사본을 만들고, 이미 팀원이 선택돼 있어도 새 자리를 추가한다. 교체는 선택한 카드의 **다른 에이전트로 교체**에서만 시작한다. 권한이나 결과 계약이 달라지는 경우 차이를 먼저 확인한다.
- **스킬 라이브러리.** 행에는 이름·언제 쓰는지와 필요한 상태 하나를 보인다. 상세에서 지침, 선택 버전, 사용처, 새 버전 저장, 보관·복원을 제공한다. 프로젝트가 볼 수 있는 저장 자산과 팀의 직접 참조를 표시한다. 조회하지 못한 사용처를 0개로 쓰지 않는다. 패키지 해시·항목 경로·품질 평가의 상세는 펼쳐 본다.
- **사본과 버전.** 에이전트는 팀에 복사되고 스킬은 선택한 버전을 참조한다. 팀원 메뉴에서 필요할 때만 ‘이 팀의 작성자’와 원본 출처를 확인한다. 스킬 v2가 나와도 v1을 쓰던 팀은 그대로다. 작성자의 스킬 상세에서 **이 작성자만 새 버전 사용** → 버전·변경 지침·신뢰 상태 확인 → **작성자에게 적용** → **팀 저장**으로 바꾼다. 라이브러리 원본에서 갱신하면 이후 새로 추가할 사본에 반영된다. 현재 사용 중인 다른 팀까지 일괄 갱신하지 않는다.
- **이탈과 복구.** 휴지통처럼 보이는 동작을 배정 해제에 쓰지 않는다. 선택 해제, 보관, 신뢰 해제는 각각 다른 영향이다. 보관은 새 선택 목록에서 숨기고 이미 유효한 고정 참조를 보존한다. 버전이 없거나 신뢰가 철회된 경우에는 대상 이름·원인·**다시 연결**을 보인다. 상속 필수 항목에는 해제 동작을 주지 않는다. 복구 후 열었던 팀원, 자료 선택과 스크롤이 유지된다.

## 5. 예측 가능한 검토와 결과

| 선택 | 실행 전에 읽을 말 | 시험 기록에서 확인할 사실 |
| --- | --- | --- |
| 공통 자문 / 요청형 산출물 리뷰 | 대상 작업자가 필요할 때 질문한다. 초안 의견을 받은 작성자가 최종본을 낸다. | 실제 질문·답변과 리뷰 대상 V1, 작성자가 제출한 V1 또는 V2. 질문이 없었던 실행은 자문 요청 0건. |
| 진행 중 자동 관찰 | 지정한 작업자와 검토 시점, 별도 모델 사용을 표시한다. | 의견이 작업 중 전달됐는지, 종료 뒤 사용자에게 남았는지. 전달과 채택을 구분한다. |
| 결과별 **검토 통과 후 제출** | ‘작성자의 초대장’을 검토하고 수정을 요청하면 작성자에게 돌아간다. 통과한 후보를 제출한다. | 수정된 V2라면 V2를 통과한 판정과 실제 제출 버전이 같은지 확인한다. 소진·취소 시 미통과 출력은 확정되지 않는다. |

## 6. 작은 화면과 조작 계약

1280px에서는 팀 흐름과 선택한 카드의 편집 영역을 함께 본다. 390×844와 좁은 세션 패널에서는 팀 → 역할 → 스킬 선택 → 스킬 작성의 현재 단계 하나를 보인다. 상단 돌아가기에는 목적지를, 주 동작에는 적용 대상을 쓴다. 뒤로·Esc는 한 단계씩 돌아간다. 편집한 내용을 잃는 경우에만 기존 미저장 보호를 사용한다. 검색어·체크·스크롤·초안은 이 경로에서 보존한다.

구현에서는 [DESIGN.md](../../DESIGN.md)의 Button·Field·CheckboxGroup·Dialog·Sheet·Banner와 타입·밀도 토큰을 사용한다. 행 선택·제거·상세 열기는 이름 있는 키보드 조작으로도 수행한다. 새 스킬 저장 뒤 초점은 돌아온 항목, 역할 설정을 닫은 뒤에는 원래 카드로 간다. 모바일 키보드가 열린 상태에서 저장 버튼까지 스크롤할 수 있어야 한다. 색이나 애니메이션에만 선택·오류를 맡기지 않는다. 영어·한국어 및 동작 줄이기를 함께 검증한다.

### 리뷰에서 채택하거나 조정한 판단

- 앞선 Fable 5.2 플랜·UX 리뷰 두 건에서 공통으로 지적한 첫 출시 범위를 조정했다. 두 라이브러리와 함께 단순 팀 카드, 제출자, 첫 모의 시험을 1C에 넣는다. 모든 고급 설정 화면을 다시 만드는 일은 이 범위에 넣지 않는다.
- ‘라이브러리에서 에이전트부터 만들기’는 에이전트 보기의 빈 상태에 적용한다. 팀 보기에 들어온 사람에게는 **새 Corral**, 스킬 보기에 들어온 사람에게는 **스킬 만들기**가 첫 행동이다. 별도의 온보딩 설명을 읽기 전에 목적에 맞게 시작할 수 있다.
- 스킬 버전 갱신은 한 자리에서 명시적으로 채택한다. 팀 사본 출처는 상세에서 확인한다. 갱신 안내·기존 사본 설명을 모든 카드에 계속 반복하는 방안은 제외했다.
- 처음 리뷰가 제기한 교체 위험은 코드로 나누어 확인했다. 자문 대상은 유지되는 노드 ID를 사용하고, 계획 소유자는 교체될 역할 ID를 사용한다. 이 둘에는 각각 다른 회귀 검사가 필요하다.

- 그래프에 대한 세 번째 Fable 5.2 리뷰에서는 **흐름 그래프**라는 탭 이름을 채택했다. 사용자가 그 탭에서 보는 것은 설계한 경로이고, 이번에 실제로 지나간 경로와 산출물 버전은 **시험 기록**에서 확인하기 때문이다. 모바일에서는 두 탭을 같은 너비로 표시하고 탭마다 높이 44px 이상을 확보한다. 구현 시 좁은 세션 탭에도 편집기 패널의 실측 폭을 기준으로 같은 배치를 적용한다.
- Fable이 제안한 방향키로 실행선을 따라가는 조작은 기존 제품의 공간 탐색과 충돌한다. 탭 안에서는 좌우로 보기를 바꾸고, 캔버스 안에서는 기존대로 해당 방향의 가까운 노드로 이동한다. 반복 한도 역시 첫 회차를 포함해 계산하므로 예시에는 **필수 검토 · 3회차까지**라고 표시한다. [캔버스 키보드 계약](../specs/features/canvas.md) · [반복 실행](../specs/features/team-graph.md#루프-실행)

- 대화형 팀 구성에 대한 Fable 5.2의 추가 리뷰에서 하단 접이식 패널, 새 팀에서 바로 펼치기, 명확한 목표의 추가 질문 생략, 기존 팀의 변경 미리보기 한 개, 낡은 제안 차단을 채택했다. Fable은 **설계 맡기기**라는 공통 이름을 제안했다. Corral에서는 작업 대화와 구별하고 적용 대상을 드러내기 위해 **AI로 팀 만들기 / AI로 팀 편집**을 선택했다. 첫 버전의 편집 명령도 기존 자문·필수 검토·목표 변경부터 제공한다.

**시안에서 확인한 범위.** 독립 HTML을 Chrome에서 열어 새 스킬 저장 후 배정 취소, 작성자에게 여러 스킬 적용·되돌리기, 원본과 팀 A·B 사본의 독립, 팀 A에서만 스킬 v2 채택, 카드 교체 시 이름·단계 지시 유지, 먼저 일하는 역할만 입력 후보에 표시, 첫 생산자 자동 선택과 이후 제출자 보존, 필수 검토 중 제출자 변경 차단을 확인했다. 모의 시험은 한 번의 조작으로 현재 제출자의 예시 결과를 연다. 1280×800과 390×844에서 선택기 복귀와 가로 넘침을 확인했다. 시안은 브라우저 안의 예시 데이터를 사용한다. 제품의 저장소·모델·권한 집행과 실제 사용자의 이해도는 [구현 계획의 검증 단계](team-composition-and-agent-library.md)에서 확인한다.

그래프 시안에서는 일반 팀의 직선 경로와 검토 팀의 수정 복귀·통과·소진 경로를 1280×800, 390×844에서 확인했다. 같은 작성자가 제출자로 표시되고, 사람의 최종 승인을 켰을 때만 해당 단계가 나타난다. 예시 바로가기와 보기 전환은 기존 팀 데이터를 보존한다. 병렬·조건이 있는 임의 그래프의 작성은 제품 구현 단계의 검증 대상이다.

대화형 시안에서 “작성자 한 명이 동네 소식지를 작성한다”를 입력해 질문을 건너뛰고 실제 초안에 작성자와 출력을 생성했다. 기존 예시 팀에서 현재 제출자를 물은 뒤 필수 검토를 적용하고, 그래프에 검토가 추가된 것과 Undo 한 번으로 원래 두 연결이 복원되는 것을 확인했다. 1280×800과 390×844의 로컬 Chromium에서 확인한 예시 응답이다. 임의 목표에 대한 모델 대화와 기존 팀의 모델 기반 부분 변경은 제품 인수 검증에 남아 있다.
