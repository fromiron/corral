# Corral 에이전트·스킬 라이브러리와 팀 구성 개편 계획

[화면 설계와 문구](team-composition-design.md) · [클릭 가능한 디자인 시안](team-composition-prototype.html) · [AI로 팀 만들기 시안](team-composition-prototype.html#ai-builder)

계획 기준은 `1727560d`다. [이전 편집기 계획](team-editor-usability.md)에서 만든 공통 자문, 제출 버전 검증, 연결 편집, Undo를 바탕으로 **팀을 처음 만드는 경험**을 다시 설계한다. 아래 화면명과 저장 방식은 제안이며, 구현 단계마다 동작을 소유한 명세를 먼저 갱신한다.

**첫 출시는 «저장해 둔 작성자를 팀에 추가하고, 두 스킬을 붙여서, 그 작성자의 최종 결과를 연다»까지다.** 에이전트와 스킬은 각각 팀 없이 만들어 쓸 수 있다. 팀을 쓰려는 사람은 기본 제공 역할부터 골라 시작할 수 있다. 두 라이브러리와 함께, 역할·자료·스킬·최종 제출자만으로 단순 팀을 시험할 수 있는 기본 화면을 이 범위에 포함한다. 같은 첫 출시에서 원하는 결과를 말해 새 팀을 구성하고, 기존 팀에는 필요한 수정을 제안받아 한 번에 적용할 수 있어야 한다. 수동으로 같은 과제를 마치는 경로도 함께 검증한다.

## 1. 완성되면 사용자가 하는 일

라이브러리에서 **새 Corral**을 누르고 “동네 자전거 소풍 초대장 작성”을 입력한다. **에이전트 추가**에서 기본 제공 **기획자**와 미리 저장해 둔 **우리 팀 작성자**를 차례로 고른다. 작성자를 누르면 그 사람이 할 일, 받을 자료, 쓸 수 있는 스킬이 보인다. 최종 결과를 작성자의 초대장으로 정하고 시험한다. 이 경로에서 모델 프로필, 입력 바인딩, 실행 방식, Harness를 직접 설정할 필요가 없어야 한다. 실제 모델로 실행하려는데 쓸 수 있는 모델이 없을 때에는 그 자리에서 모델 연결·선택으로 이동하고 같은 초안으로 돌아온다.

| 작성자를 선택한 기본 화면 | 이 예에서 보일 내용과 동작 |
| --- | --- |
| 맡은 일 | “기획안을 바탕으로 두 문장짜리 초대장을 작성한다.” 팀에서 이번 단계의 지시를 편집한다. |
| 받는 자료 | **기획자 · 기획안**. 현재 정의에서 읽은 출처를 누르면 자료를 바꿀 수 있다. |
| 사용할 스킬 | **문장 교정**, **브랜드 문체**, **스킬 추가**. 작성자가 필요할 때 사용할 수 있다. |
| 팀 화면의 최종 결과 | **작성자 · 초대장**. 둘 이상의 결과를 제출하는 팀은 실제 선택한 결과를 모두 확인할 수 있다. |

작성자 카드에서 **맡은 일**을 고치는 것은 이 팀의 지시 편집이다. 원본의 일반 지시는 카드를 펼쳐 필요할 때 확인한다. 예시 이름과 문장은 설계 설명용이다. 새 팀에 예시 내용을 저장하지 않는다. 참가자가 설계자의 도움 없이 **기존 에이전트 선택 → 첫 모의 시험 → 예상한 생산자의 결과 열기**를 마치는 것이 1C의 제품 기준이다. 개인·프로젝트 정책과 그래프 세부 필드는 복구가 필요한 경우에만 첫 과제에 등장한다.

## 3. 두 라이브러리에서 준비하고 팀에서 사용하기

| 화면 | 들어가서 하는 일 | 저장 단위 |
| --- | --- | --- |
| **라이브러리 → 에이전트** (`/library/agents`) | 기본 제공 또는 현재 프로젝트의 에이전트를 검색한다. 이름·맡은 일·사용할 스킬을 보고 원본을 만들거나 편집한다. | 기본 제공 역할은 사본으로 시작한다. 프로젝트 원본에는 재사용할 지시와 선택한 스킬 버전들을 저장한다. |
| **라이브러리 → 스킬** (`/library/skills`) | 스킬 이름·설명으로 찾아 지침·출처·버전을 읽고, 직접 만들거나 기존 `SKILL.md`를 가져온다. 팀이나 에이전트가 없어도 쓸 수 있다. | 실제 스킬 항목을 기존 리소스 저장소에서 읽는다. 하나의 패키지에 스킬 세 개가 있으면 각각 고를 수 있다. |
| **에이전트 원본 또는 팀원 카드 → 스킬 추가** | 같은 스킬 목록에서 여러 개를 고르고 한 번에 적용한다. 필요한 스킬이 없으면 **새 스킬 만들기**를 열고, 저장 후 원래 선택기로 돌아와 적용한다. | 원본 편집에서는 원본의 다음 revision에, 팀원 편집에서는 그 팀 초안의 역할 사본에만 선택을 기록한다. |

**스킬 라이브러리의 동작**

1. **찾기.** 현재 프로젝트 문맥에서 사용할 수 있는 스킬을 기본으로 보여준다. 행에는 표시 이름과 용도를 두고, 동명 항목은 패키지·출처로 구분한다. 검색 결과 없음, 등록된 스킬 없음, 조회 실패와 재시도, 보관 항목 보기를 구분한다. 설정이나 Harness를 먼저 열 필요가 없다.
2. **작성·가져오기.** 새 스킬은 이름·언제 쓰는지·Markdown 지침으로 만든다. 파일이나 패키지를 가져올 때는 기존 설치 검토에서 실제 스킬 항목과 변경 내용을 확인한다. 설치와 해당 해시 신뢰는 기존 관리 서비스를 거친다. 설치·저장 전에 취소하면 새 항목이 생기지 않는다. 스킬을 저장한 뒤 선택기만 취소하면 스킬은 라이브러리에 남고 에이전트에는 배정되지 않는다. 설치만 끝난 항목은 실제 실행 가능 상태와 구별해 표시한다.
3. **버전·보관.** 상세에서 지침과 버전을 읽고 새 버전을 저장하거나 보관·복원한다. 기존 참조에는 새 버전이 있을 때 해당 스킬 상세에서 **이 작성자만 새 버전 사용**을 제공한다. 달라진 지침과 신뢰 상태를 확인한 뒤 역할 초안에 적용한다. 내용 변경은 새 해시에 귀속되고 신뢰 상태도 다시 확인한다. 기존 에이전트와 팀 사본은 이미 선택한 버전을 유지한다. 보관은 새 선택 목록에서 숨기는 동작이다. 물리적으로 누락되거나 신뢰가 철회된 버전은 실행 전 복구 대상으로 표시한다.
4. **사용처와 적용.** 1B는 현재 확인할 수 있는 Harness 사용처를 표시한다. 1C에서 현재 프로젝트의 에이전트 원본 및 저장된 팀의 현 revision 가운데 해당 버전을 직접 참조하는 항목을 더하고 해당 상세로 이동시킨다. 초기 규모에서는 저장된 참조를 조회하며 별도 역색인은 성능 근거가 생길 때 도입한다. 기존 Harness를 통한 사용처는 따로 표시한다. 접근할 수 있는 범위만 조회하며, 스킬을 여러 에이전트에 붙여도 본문은 한 곳에서 관리한다. 선택 취소는 역할을 바꾸지 않고, 팀에서 여러 스킬을 한 번에 적용·해제한 편집은 Undo 한 번으로 복원한다.
5. **기존 진입과 연결.** 기존 설정의 스킬 관리와 리소스 행의 ‘관리’도 같은 스킬 상세·편집 동작을 연다. 진입한 프로젝트·검색·선택 카드·미저장 초안을 복원한다. 리소스 보기에서 스킬을 다시 나열하던 자리는 스킬 라이브러리 진입으로 정리한다. 데모에서는 서버 설치가 필요한 스킬을 ‘로컬 서버에서 사용’으로 표시한다. ### 사전 정의한 에이전트를 고르는 흐름

**원본은 라이브러리가, 팀에서 쓰는 사본은 팀이 소유한다.** 초기 범위는 모든 프로젝트에서 보이는 기본 제공 프리셋과 **현재 프로젝트**에 사용자가 저장한 에이전트다. 팀 두 곳에서 같은 작성자를 골라도 두 팀의 지시·스킬은 독립적이다. 사람의 요청 없이 여러 팀에 변경을 전파하는 ‘항상 최신 버전’ 연결은 도입하지 않는다.

| 진입점 | 선택과 결과 |
| --- | --- |
| 라이브러리 → 에이전트 → 에이전트 만들기 | 팀 없이 이름과 기본 역할 지시를 저장한다. 사용할 스킬 여러 개와 외부 도구는 선택 사항이다. 원본 상세에서 편집·복제·보관할 수 있다. 보관한 원본은 기본 선택 목록에서 빠지고 기존 팀 사본은 계속 쓸 수 있다. |
| 팀 구성 → 에이전트 추가 | 한 선택기에서 **내 에이전트**(프로젝트명 표시), **기본 제공**, **직접 만들기**를 제공한다. 이름·역할 설명으로 검색하고 선택 전 맡은 일과 선택된 스킬을 본다. 내 에이전트가 없어도 기본 제공·직접 만들기를 바로 선택할 수 있다. 같은 이름의 원본은 출처와 설명으로 구분한다. |
| 선택기 → 팀에 추가 | 원본의 선택한 revision을 한 번 복사해 새 노드와 새 역할 ID를 만든다. 같은 작성자를 두 번 고르면 두 자리가 생긴다. 카드 하나가 선택된 상태여도 그 카드를 덮어쓰지 않는다. 위치가 명확하면 바로 추가하고, 분기나 Loop 경계를 바꾸면 기존 삽입 미리보기에서 영향을 확인한다. |
| 팀원 카드 → 라이브러리에 저장 | 이름과 재사용할 기본 지시를 확인한 뒤 현재 프로젝트에 새 원본을 저장한다. 기존 원본과 이름이 같아도 덮어쓰지 않는다. 이번 팀의 요청·자료·단계 지시는 복사 대상에서 뺀다. 필요한 문장은 저장 전에 기본 지시에 직접 반영할 수 있다. 선택기를 열거나 팀에 사본을 추가하는 동작으로 새 라이브러리 원본이 생기지 않는다. |
| 팀원 카드 → 다른 에이전트로 교체 | 역할 능력과 기본 지시가 달라지는 부분을 미리 본다. 그 자리의 이름·단계 지시·연결·명시 입력·최종 결과 선택은 유지한다. 기대 출력 형식이나 필수 검토 계약과 충돌하면 원래 카드를 보존하고 원인을 표시한다. 취소·같은 내용 재선택은 Undo 0건, 실제 교체는 1건이다. |

다른 저장 팀에서 역할을 빌려오는 기존 진입은 선택기 보조 동작 **다른 팀에서 가져오기**로 유지한다. 기존 Markdown 위임 에이전트 가져오기는 부모와의 위임 관계와 권한 미리보기가 있는 별도 흐름이다. 일반 팀원을 고르는 일로 바꾸면 그 의미가 사라진다. 기존 참조 팀은 현재와 같이 팀 revision을 고정해 재사용한다. 공통 Outrider와 관찰 전용 역할은 일반 작업자 목록에 섞이지 않는다. [캔버스의 역할 복사 규칙](../specs/features/canvas.md) · [Markdown 위임 가져오기](../specs/desktop-contract.md)

## 4. 팀 구성과 흐름 그래프

- **팀 구성.** 상단에 팀의 할 일과 완료 기준, 본문에 역할과 실제 일 순서, 끝에 받을 결과를 둔다. 팀을 만드는 경로에서 라이브러리 방문을 의무화하지 않는다. 팀 안의 선택기와 독립 라이브러리는 같은 자산을 사용한다. 공통 Outrider는 팀 설정 한 곳에서 추가한다. 모델·연결 상태가 준비된 평범한 팀은 이 화면에서 저장과 시험까지 끝난다. 목표·템플릿·직접 구성은 모두 같은 화면으로 들어온다. AI가 제안한 역할도 저장된 에이전트로 교체할 수 있다. 이름이 같다는 이유로 라이브러리 원본을 자동 배정하지 않는다.
- **최종 결과.** 새 빈 팀에 첫 일반 생산자를 추가하면 역할·출력·실행선·입력을 한 번의 명령으로 구성하고 그 결과를 받는다고 표시한다. 다음 생산자를 넣으면 기존 출력 출처를 표시하면서 **이 단계의 결과 받기**를 제공한다. 사용자가 작성자의 결과를 고른 뒤에만 기획자에서 작성자로 바뀐다. 기존 복수 출력과 직접 고른 입력에는 추가·재배치만으로 손대지 않는다.
- **자료.** 단순한 선행 결과는 실제 입력에서 이름을 읽어 바로 보여준다. 팀 요청, 둘 이상의 자료, 이전 작업 외의 출처도 각각 표시한다. 새 단계에 후보가 여럿이고 필요한 입력을 결정할 수 없으면 **받을 자료 선택**을 그 자리에 제공한다. 이때 필수 자료만 시험을 막는다. 실행 순서의 변경과 자료 출처의 변경은 별도 명령이다.
- **복잡한 팀.** 병렬은 한 묶음과 갈래별 작업자, 조건은 실제 경로명, 반복은 되돌아가는 위치와 한도, 호출 전용은 요청자를 표시한다. 참조 팀은 팀 이름과 고정 버전으로 접는다. 판독할 수 없는 구조에는 단정적인 순번을 붙이지 않고 해당 부분을 **흐름 그래프에서 보기**로 연결한다. 열기·보기 전환만으로 그래프를 재작성하지 않는다. 기본 보기의 추가·교체가 분기나 잠긴 참조 내부를 정확히 다룰 수 없으면 초안을 보존한 채 흐름 그래프의 해당 위치로 이동한다.
- **흐름 그래프.** **팀 구성 / 흐름 그래프**를 팀 화면 상단에서 바로 전환한다. 실제 제어선과 방향, 조건 이름, Loop의 경계·복귀·탈출·설정된 한도를 확인할 수 있다. 기존 캔버스의 포트 연결, 팔레트·구조 목록 D&D, 자동 배치, 키보드 연결, Undo/Redo를 계속 제공한다. 두 보기는 같은 에디터 초안·컴파일 결과·명령을 사용한다. 보기 전환은 저장이나 Undo를 만들지 않는다. 문제 행을 열면 해당 단계나 연결을 가리키고, 돌아오면 같은 카드와 포커스로 복귀한다. 세션 설계 탭도 같은 규칙이다. 새 팀은 팀 구성으로 연다. 기존 팀은 5단계 전까지 현재 캔버스 진입을 흐름 그래프로 유지하고 팀 구성을 선택할 수 있게 한다.
- **도우미와 시험.** 일반 **에이전트 추가**는 순서에 따라 일할 팀원을 만든다. 작업을 위임하는 전용 도우미는 **흐름 그래프 → 도우미 연결**에서 요청자와 위임 대상을 고른다. 팀 공통 자문과 수동 질문선은 각자의 관계를 유지한다. 시험 패널은 팀 요청·예상 최종 결과·**모의 시험**을 먼저 보여준다. 유료 호출을 시작하는 **실제 모델 실행**은 별도로 선택한다. 실행별 모델·추론·한도 재정의는 상세에 둔다.
- **좁은 화면.** 390×844에서는 팀 목표 → 역할 → 결과 순으로 읽는다. 역할을 고르면 자리에서 요약을 읽고 **설정 열기**로 이동한다. 선택기·설정을 닫으면 같은 카드로 돌아온다. 원본 100개, 역할 10개가 있어도 처음에는 현재 프로젝트·검색·역할 이름으로 찾게 한다. 카드마다 모델·권한·버전 배지를 반복하지 않는다. 첫 출시부터 독립 편집기와 좁은 세션에서 같은 카드로 복귀하는 경로를 검증한다.

기본 화면에 모든 필드를 펼치는 방식은 간단한 팀에도 입력 계약을 설명해야 한다. 반대로 모든 팀을 편집 가능한 일렬 목록으로 축소하면 분기·병렬·필수 검토의 의미가 달라진다. **팀 구성에서 결과를 예측하고, 의미가 달라지는 지점에서 구조를 여는 방식**을 택한다.

### 대화로 만드는 팀과 기존 팀의 부분 변경

새 팀의 입구는 라이브러리와 빈 편집기, 기존 팀의 입구는 **팀 구성 / 흐름 그래프**에 공통으로 둔다. 목표에서 만드는 사람에게 두 개의 별도 AI 대화를 보여주지 않는다. 새 UI의 목표 생성 진입은 같은 패널을 열고, 프로젝트의 임시 초안에서 시작한다. 목적·예시를 둘러본 뒤 취소해도 빈 팀이 라이브러리에 생기지 않는다. 구체적인 진입·질문·선택지는 [화면 설계](team-composition-design.md#ai와-함께-팀을-만들거나-고치기)를 따른다.

| 경계 | 구현과 검증 |
| --- | --- |
| 현재 재사용할 부분 | `POST /api/v1/team-assistant`는 요청 ID와 대화·카탈로그를 받아 검증된 질문 하나나 구성(`TeamComposition`) 하나를 돌려준다. [모델 요청](../../apps/server/src/app.ts) · [프롬프트와 한도](../../apps/server/src/models/team-assistant.ts) · [답 판독](../../packages/core/src/team-assistant.ts) · [구성을 팀으로 변환](../../packages/core/src/team-composition.ts). [편집기의 AI 대화](../../packages/react/src/team-editor/TeamAssistant.tsx)는 이 구성을 펼쳐 제안을 임시 초안에 적용한다. 저장은 별도 동작이며, 첫 저장에서 팀이 하나 생긴다. |
| 대화 응답 | 역할과 산출물에 영향을 주는 정보가 비었으면 질문과 선택지를, 정보가 충분하면 바로 구체적인 안을 제공한다. 기존 구성에 관한 사실 질의는 현재 초안의 역할·바인딩·최종 출력에서 읽는다. 모델 호출이 필요하면 활성 모델과 호출 동작을 표시한다. 추천 이유와 자연어 설명은 화면 문구다. 변경은 허용한 구조의 제안만 해석한다. 모델이 제안한 문자열을 명령으로 실행하지 않는다. |
| 변경을 적용하는 곳 | 새 팀은 검증된 계획을 기존 생성기로 펼친다. 기존 팀은 명시한 팀·현재 초안·대상 노드나 출력 입력에 대한 제한된 편집 목록을 적용한다. [기존 편집 명령](../../packages/react/src/team-editor/commands.ts)을 초안 복사본에 순서대로 실행하고 같은 컴파일러·진단으로 결과를 미리 본다. 보이는 차이와 적용 시 사용할 결과가 같아야 한다. 모든 변경을 만들 수 있을 때만 [공유 에디터 저장소](../../packages/react/src/editor/store.ts)의 `applyDraft` 한 번으로 반영한다. 선택·질문·취소·같은 상태 적용은 Undo 0건이다. |
| 손편집·재시도 | 제안 후 다른 보기에서 수동 편집하거나 팀을 바꾸면 예전 적용을 막고 요청과 현재 편집을 보존한다. 현재 초안 기준으로 **다시 제안**을 선택한 뒤 최신 미리보기에서 계속한다. 응답이 늦거나 요청을 취소한 경우 다시 나타나 적용되지 않도록 팀·요청을 대조한다. 결과 불명인 유료 요청은 현행 요청 ID 처리 방식을 따른다. 새 결제 요청의 자동 재전송은 하지 않는다. |
| 자산·권한·저장 | 에이전트 원본은 선택한 프로젝트의 사본 규칙, 스킬은 실제 자산·고정 버전과 신뢰 규칙을 따른다. 제안만으로 권한이나 MCP 인증, 사람의 승인, 자동 관찰이 추가되지 않는다. 필요한 권한·대상·비용 변화는 적용 전 확인한다. 원본 변경과 다른 팀 수정은 편집 대화의 범위 밖이다. 저장은 기존 [revision 확인](../../apps/studio/src/workbench/editorDraft.ts)을 사용한다. 팀을 실제로 실행하는 것은 독립적인 사용자 동작이다. |

**명시 선택과 자연어의 충돌.** “작성자가 필요할 때만 전문가에게 자문한다. 검토 통과나 자동 관찰은 필요 없다”는 요청으로 현행 서버 경로를 확인했다. DeepSeek와 GLM 모두 단일 작성자와 요청형 자문을 제안했으나, Studio가 사용하는 `planAfterModel`은 로컬 규칙의 산출물 리뷰로 두 제안을 교체했다. 새 대화 경로에서 사용자가 직접 누른 자문·필수 검토·관찰 선택은 구조화된 값으로 저장한다. 낱말 매칭이나 모델의 다음 답이 그 값을 덮지 못한다. 부정문 안에 ‘검토’가 있다는 이유로 검토를 추가하지 않는 반례를 현재 목표 초안과 새 대화 모두에서 확인한다. [판독·미리보기 규칙](../../packages/core/src/team-draft.ts) · [라이브 측정](../../tests/live/team-assistant.live.test.ts)

**첫 출시 범위.** 새 팀은 이미 지원하는 패턴에서 시작한다. 편집은 현재 구성 설명, 팀 목표 변경, 요청형 자문 추가, 선택한 산출물의 필수 검토 추가를 먼저 지원한다. 복잡한 요청을 지원하는 수정으로 임의 해석하지 않는다. 가능한 수정과 직접 조작할 위치를 보여준다. 이후 실제 요구를 보고 역할·흐름 편집에 사용할 기존 명령을 확장한다. [기존 목표 초안 명세](../specs/features/library.md) · [공통 자문과 필수 검토](../specs/features/shared-outrider.md)

## 5. 스킬, MCP, Harness, Outrider의 경계

| 사용자 의도 | 기본 편집 동작 | 실행 시 보장할 것 |
| --- | --- | --- |
| 이 작성자가 문장 교정과 브랜드 문체를 쓸 수 있게 한다 | 역할의 **스킬 추가**에서 설치된 스킬 여러 개를 선택·해제한다. 상속된 필수 스킬은 출처를 보여준다. | 해당 역할의 실행에만 선택을 적용한다. 사용 가능, 본문을 읽음, 모델 요청에 전달됨과 실제 결과에 반영됨을 구별한다. 스킬 선택은 의무 검토나 추가 도구 권한을 만들지 않는다. |
| 조사자만 외부 이슈를 검색한다 | 역할의 **도구 추가**에서 승인된 연결의 **이슈 검색**만 고른다. 연결이 없으면 기존 리소스 관리로 이동한 뒤 같은 카드로 돌아온다. | 실행 스냅샷에 서버와 정확한 도구 식별자를 고정한다. 같은 서버의 이슈 수정, 나중에 추가된 도구가 따라오지 않는다. 기존 인증·승인·취소 규칙을 적용한다. |
| 작업자가 필요할 때 전문가의 의견을 듣는다 | 팀에서 **공통 Outrider** 한 번 설정. 기본은 전체 작업자, 필요할 때 대상 선택. **산출물 리뷰**는 별도 선택이다. | 질문이 없으면 자문 호출 0회. V1 리뷰는 V1에 남고 제출자는 원래 작성자다. 전체와 직접 선택의 저장 의도를 유지한다. |
| 진행 중 관찰하거나 제출 전 통과를 요구한다 | 자동 관찰은 팀 자문 설정에서 대상·주기·추가 호출을 보여준다. **검토 통과 후 제출**은 해당 최종 결과에서 켜고 수정받을 생산자를 보여준다. | 전달·채택을 구별하고, 조건이 붙은 입력의 정확한 후보 버전만 통과 후 제출된다. 소진·취소·검토 실패로 미검토 결과를 확정하지 않는다. |

Harness는 개인·프로젝트·역할·실행 정책, 고정 버전과 허용 한도를 해석하는 내부 실행 계약으로 둔다. 일반 사용자는 처음부터 Harness를 고르지 않는다. 이미 고정한 설정의 이름·버전·권한과 관리자 편집기는 **상세 설정 → 실행 정책**으로 접근한다. 권한 때문에 “Outrider에게 질문”이나 “이슈 검색”이 불가능하면 해당 동작 옆에 이유와 복구 경로를 표시한다. 기존 `strict` 정책에서 금지되는 MCP 사용은 기본 설정을 숨겨도 계속 금지된다. ## 6. 저장과 실행 계약

1. **에이전트 원본.** 프로젝트 소유의 독립 레코드에 안정 ID·revision·보관 상태와 재사용할 역할 설정을 저장한다. `AgentRole`의 지시·모델·추론·출력 계약·허용 도구·기존 Harness 참조를 재사용한다. 노드 위치·호출 관계·팀 입력·파일 본문·인증 정보는 저장하지 않는다. 서버는 프로젝트 범위에서 목록·revision 읽기·생성·수정·보관을 제공한다. SQLite와 브라우저 데모 저장소에 같은 저장소 계약 테스트를 적용한다. 기존 팀 저장에서 쓰는 operation ID·예상 revision 패턴으로 중복 생성과 오래된 원본 덮어쓰기를 막는다.
2. **사본과 팀별 지시.** 선택한 원본 revision의 역할을 팀 정의에 실제로 복사한다. 사본에는 선택 당시의 원본 ID·revision을 선택적 출처 정보로 보존한다. 원본이 보관되거나 다른 프로젝트로 내보내도 팀의 역할은 그대로 실행하며, 권한 없는 원본 이름을 역조회하지 않는다. 실행 시 라이브러리를 다시 읽지 않는다. 원본과 팀의 저장은 별개이며 팀 Undo로 원본을 삭제하지 않는다. 카드에서 사본을 추가하는 시점에는 팀 초안만 바뀌고, 팀 저장 시점에 해당 팀의 revision이 생긴다. 라이브러리 저장과 팀 저장이 각각 실패해도 사용자가 입력하거나 편집한 내용은 보존한다. `WorkAgentNode`에 선택적인 단계 지시를 추가한다. 역할의 재사용 지시와 이번 단계의 일을 런타임의 서로 다른 입력으로 전달한다. 단계 지시가 없으면 기존 역할의 지시가 적용된다. 과거 역할 지시를 복제해 두 번 보내지 않는다. 기존 여러 노드가 한 역할 ID를 공유한 팀에서도 한 자리의 일 또는 스킬을 바꿨을 때 다른 자리가 달라지지 않도록, 역할 단위 변경에는 그 자리의 역할 사본을 만든다. [역할·노드 계약](../../packages/contracts/src/definition.ts) · [작업자에게 전달하는 입력](../../packages/adapter-pi/src/worker-tools.ts)
3. **스킬 원본과 능력 선택.** 스킬 카탈로그는 기존 `HarnessEntryView`의 스킬 항목을 사용한다. 에이전트 원본은 프로젝트 소유다. 스킬 본문은 기존 설치 리소스의 범위를 따르고, 선택기와 사용처는 현재 프로젝트의 유효 정책과 열람 가능한 팀에 한정한다. 같은 본문을 프로젝트마다 복제하거나 전체 설치 목록을 그대로 ‘이 팀에서 사용 가능’이라고 표시하지 않는다. 표시 이름을 바꿔도 참조를 유지하며, 새 해시의 후속 버전과 기존 버전을 구분한다. 사용처 조회에는 기존 프로필 참조와 새 에이전트 원본·팀 사본의 버전 참조를 각각 사용한다. 역할에 선택적 스킬·MCP 도구 선택을 추가하고 라이브러리 원본과 팀 사본이 같은 형식을 쓴다. 선택기를 열거나 권한 미리보기를 하는 과정에서 숨은 Harness 프로필을 생성하지 않는다. 스킬은 패키지 해시와 패키지 안의 항목, MCP는 등록 서버와 정확한 도구 이름으로 식별한다. 항목별 필드 부재는 기존 상속 동작, 명시적인 빈 목록은 선택적 항목 0개, 목록은 고른 항목이다. 상위의 필수 스킬과 허용 한도는 어느 경우에도 유지한다. 이름만 같은 새 패키지나 다른 프로젝트의 동명 서버로 교체하지 않는다. [리소스 관리 계약](../../packages/contracts/src/harness-management.ts) · [리소스 조회·정책 서비스](../../apps/server/src/harness/service.ts)
4. **미리보기와 실제 권한.** 현재 Coordinator의 실행 준비는 `role.harness`가 없으면 그 역할의 Harness 해석을 건너뛴다. 따라서 UI에 스킬 칩만 추가하면 런타임과 어긋난다. 새 능력 선택이 있는 역할은 기존 개인·프로젝트 기본값 또는 시스템 기본 정책을 명시적으로 해석해 한 스냅샷을 만든다. 명시된 역할·실행 정책을 함께 적용해 유효 도구를 제한한다. 역할 필드와 바인딩이 모두 없는 기존 팀은 이전 경로를 따른다. 편집기 미리보기·서버 실행 준비·Coordinator·작업자 어댑터가 같은 해석 결과를 사용한다. [정책 해석](../../apps/server/src/harness/service.ts) · [실행 준비](../../packages/core/src/coordinator.ts) · [MCP 실행](../../apps/server/src/harness/mcp-service.ts)
5. **모델과 누락 자산.** 기본 제공 역할의 모델 자리와 사용자가 고정한 모델 ID를 구분한다. 새 내장 역할은 모의 시험 또는 사용 가능한 프로젝트의 실제 기본 모델로 시작하며, 실제 기본값이 없으면 한 번 선택해 저장한다. 사용자 원본에 고정된 모델은 보존한다. 누락되거나 신뢰가 바뀐 선택 자산은 초안에 남기고 대상 역할·항목과 **다시 연결 / 선택 제거**를 보여준다. 명시적 선택을 조용히 빼고 실제 실행하지 않는다. 프로젝트 변경이나 가져오기에서 자격 증명을 복사하지 않는다. 현행 역할 가져오기의 미해석 Harness 제거는 새 선택기에서 **초안에 참조 보존 후 복구**로 바꾼다. 브라우저 데모에서는 로컬 원본·사본을 재열기할 수 있고 실제 공급자·MCP 인증이 필요한 동작은 서버에서만 검증한다.
6. **이전 데이터와 복귀.** 필드가 없는 기존 JSON·팀 revision·초안을 먼저 읽을 수 있게 하고 새 쓰기를 연다. 저장 후 재열기, 팀 복제, JSON 내보내기·가져오기는 사본의 실제 역할·자료·능력·검토 설정을 보존한다. 새 라이브러리 DB가 비어도 기존 팀은 열리고 실행된다. 이미 시작한 Run은 시작 당시 스냅샷으로 끝낸다. 문제가 있으면 새 쓰기와 기본 보기 전환부터 되돌리고, 새 필드를 읽는 경로는 남긴다. 새 형식을 모르는 구버전 바이너리로 새 데이터를 덮어쓰지 않는다.

### 교체할 때 무엇을 유지하는가

| 소유자 | 적용 규칙 |
| --- | --- |
| 라이브러리 원본 | 기본 지시·선택 스킬과 도구·모델·추론·출력 계약. 사본 추가나 팀원 편집은 원본을 쓰지 않는다. |
| 팀의 자리 | 노드 ID·사용자 지정 이름·이번 단계의 일·받을 자료·연결·출력 입력 식별자와 최종 선택. 교체 후에도 유지한다. 원본이 가져온 출력 계약이 후속 단계 또는 필수 검토와 호환되지 않으면 차이를 설명하고 기존 자리를 보존한다. |
| 역할 ID를 참조하는 팀 설정 | 기존 역할이 계획 소유자라면 교체 후에도 같은 한 자리가 소유자인지 확인한다. 지원되는 새 역할로 명시적으로 이전하거나, 불가능하면 교체를 거절하고 소유자 조정을 안내한다. 역할 가져오기 중 소유자를 조용히 해제하는 현재 경로를 그대로 호출하지 않는다. |
| 노드 ID를 참조하는 설정 | 공통 Outrider의 직접 대상은 노드 ID다. 교체 시 자문 대상·수동 관계를 유지하고 **유효한** 질문 가능 여부를 새 역할의 정책으로 다시 판정한다. 공유 역할 수정은 해당 자리만 복제한다. 한 번의 Undo가 교체 전 상태 전체를 복구한다. |

단계 지시는 **1A**에서 UI·저장·실행 전달을 함께 도입한다. 예전 팀의 역할 지시는 그대로 한 번만 전송한다. 저장된 기본 제공 모델 자리와 사람이 고정한 모델을 구분한다. 모의용 모델 ID를 실모델 프로필로 가장하거나 미설치 고정값을 임의로 바꾸지 않는다. [가져오기 명령](../../packages/react/src/team-editor/commands.ts) · [계획 소유자 검사](../../packages/core/src/compiler/index.ts)

### 스킬 선택과 권한의 결정표

한 해석기가 개인·프로젝트·역할·실행 계층, 역할의 새 선택 필드, 설치·신뢰 상태를 읽는다. 현재 `allowedTools`는 계층별 교집합이고 스킬 자원은 해시·항목별 병합이다. **프로젝트 프로필에 어떤 스킬이 없다는 사실만으로 금지 목록을 추정하지 않는다.** 역할에 추가할 수 있는 후보는 그 프로젝트에서 보이고 설치·신뢰·정책 검사를 통과한 정확한 스킬 항목이다. 선택 자체는 실행 도구를 추가하지 않는다.

| 역할 고정 Harness | 역할의 스킬 필드 | 선택 결과와 오류 처리 |
| --- | --- | --- |
| 없음 | 부재, 새 MCP 선택도 부재 | 기존 바인딩 없는 실행 경로와 동작을 유지한다. 기존 팀을 열거나 저장하는 것으로 새 필드를 채우지 않는다. |
| 있음 | 부재 | 기존 고정 revision과 개인·프로젝트·역할·실행 계층 병합 결과를 그대로 사용한다. |
| 있음 또는 없음 | 명시적 빈 목록 | 상속된 필수 항목(`required` 또는 `mandatory`)은 유지하고 선택적 스킬은 0개다. 기존 스킬 모드와 필수 정책을 약화하지 않는다. |
| 있음 또는 없음 | 선택한 스킬 목록 | 필수 항목과 선택 목록을 합쳐 동일 해시·항목은 한 번만 쓴다. 신뢰되고 사용 가능한 선택 항목은 요청 시 사용할 수 있게 전달한다. 필수 버전과 다른 해시가 같은 내부 이름을 차지하거나 선택 자산이 누락·비활성·미신뢰이면 실제 시작을 막고 해당 항목의 복구·선택 해제로 안내한다. |
| 있음 또는 없음 | MCP 도구 선택 | 스킬 목록과 별도로 해석한다. 역할의 선택, 상위의 허용 도구·등록 서버·개별 도구 목록을 모두 만족해야 한다. `strict`의 MCP·네이티브 제한, 승인·자격 증명 검사는 유지한다. 필수 스킬이 외부 도구를 언급해도 사용 권한이 새로 생기지 않는다. |

명시 역할 바인딩은 그 ID·revision을 쓴다. 새 선택만 있는 역할은 실행 시 프로젝트 기본 → 개인 기본 → 버전이 고정된 내장 최소 정책 순으로 **기준 참조**를 결정하고, 존재하는 상위 제한을 모두 합성한다. 기본값이 전혀 없을 때의 내장 정책은 신뢰한 선언형 스킬에 필요한 읽기만 허용하고 역할 본래의 도구 권한 안에서 동작한다. 선택만으로 외부 도구·명령 권한을 부여하지 않는다. 이 기준 정책을 위해 역할마다 숨은 프로필을 저장하지 않는다. 개인·프로젝트가 달라지면 현재 문맥의 실제 허용 결과를 새로 보여준다. 기존 바인딩 없는 역할의 임의 Run 재정의는 기존대로 거절한다.

실행 준비 결과에는 기준 참조, 각 계층의 고정 revision, 자산 식별자와 유효 스냅샷 해시가 포함된다. 확인한 뒤 시작하기 전에 권한·버전·능력이 달라지면 바뀐 대상과 다시 확인할 동작을 표시한다. 확인 전 새 조건으로 실모델 호출을 시작하지 않는다. Run이 시작된 뒤에는 이 스냅샷을 사용한다. 프로젝트에 보이는 다른 두 스킬, 상속 필수, 동명 충돌, 미신뢰, 해시가 다른 새 버전, 서로 다른 역할을 포함한 표 기반 테스트를 서버·편집기·작업자 경계에서 공유한다.

**첫 출시 인수 경로**

1. 준비된 작성자를 처음 쓰는 사람이 팀 화면에서 선택 → 두 스킬 확인 또는 추가 → 모의 시험 → 예상한 작성자의 확정 결과 열기까지 수행한다. 입력 바인딩·실행 모드·Harness 설정을 가르치지 않는다.
2. 스킬을 새로 만들어 저장한 뒤 선택기에서 취소한다. 라이브러리에는 새 스킬이 하나 있고 작성자·팀 원본·Undo는 바뀌지 않는다. 다시 골라 **작성자에게 적용**하고 Undo 한 번으로 배정만 복구한다.
3. 하나의 원본을 팀 A·B에 넣고 A에서만 스킬을 변경한다. 실행된 각 역할의 스냅샷에서 A와 B의 차이를 확인한다. 원본 편집은 이후 추가하는 사본에만 영향을 준다.
4. 유효한 저장 팀의 모의 시험은 한 번에 시작한다. 수정된 팀은 **저장하고 모의 시험**을 한 번 눌러 확인한 revision만 시작하며 저장 실패·저장 중 편집이면 초안과 기존 실행 수를 보존한다. 모의 시험과 유료 실행은 별도 행동이다. 실모델이 없거나 필수 자산을 사용할 수 없으면 해당 자리에서 복구하고 같은 초안으로 돌아온다. 제한을 조용히 풀지 않는다.

**대화형 구성의 첫 출시 인수 기준**

1. 빈 프로젝트에서 목적만 입력한다. 구성에 필요한 정보 하나를 고르거나 추천을 받아 역할·흐름·최종 결과를 미리 보고 초안에 적용한다. 적용 전·후 라이브러리의 저장본 수는 같고 첫 **팀 저장**으로만 1개 증가한다.
2. “작성자 한 명으로 이 안내문을 써 줘”처럼 충분한 요청은 이미 답한 항목을 다시 묻지 않는다. 현재 제출자를 물으면 실제 바인딩에서 답하고 Undo·저장·Run이 늘지 않는다.
3. 손으로 지시를 고친 팀에 “필요할 때만 조언”과 “통과해야 제출”을 각각 요청한다. 첫 경우는 자문 권한만, 둘째는 확인한 결과의 생산자로 돌아가는 검토를 제안한다. 여러 출력이면 대상을 고른다. 한 번 적용하고 한 번 Undo하면 앞선 손편집·스킬·다른 출력이 보존된다.
4. 미리보기를 본 뒤 손편집, 팀 전환, 제안 취소, 실패 후 재시도를 각각 수행한다. 오래된 결과는 적용되지 않고 현재 초안과 사용자 입력이 남는다. 모델이 없을 때 가능한 로컬 예시에는 출처가 표시된다.
5. 독립 편집기와 좁은 세션 탭, 390×844에서 키보드로 목표 입력 → 선택 → 미리보기 → 적용 → 흐름 그래프 확인까지 수행한다. 대화와 관련 없는 캔버스 조작·저장·작업 채팅도 계속 쓸 수 있어야 한다. 한국어 IME 조합의 Enter로 중복 전송하지 않는다.

**흐름 그래프의 첫 출시 인수 기준**

1. 1280×800과 390×844에서 작성자를 고른 뒤 탭을 바꾸면 같은 작성자가 선택된다. 탭 전환만으로 저장 상태와 Undo가 바뀌지 않는다. 모바일에서 설정을 닫으면 열었던 노드로 포커스가 돌아온다.
2. 필수 검토 한도를 2회로 설정하고 매번 수정을 요청하는 Coordinator 시험에서 확정 결과는 0건이다. 그래프에서 한도 소진은 반복 경계의 **최종 제출 없음**으로 끝나며, 이 종료 표시는 연결 편집 대상이 아니다.
3. 공통 Outrider를 허용하고 아무도 질문하지 않는 시험에서 요청형 자문 호출은 0건이다. 그래프에는 이 권한만으로 생긴 필수 실행선이 없다.
4. 작성자의 초대장을 최종 결과로 고른 뒤 후속 역할을 추가해도 제출자는 작성자다. 추가를 한 번 되돌리면 원래 구조와 선택한 출력이 복구된다.

**사람 검증은 두 번 한다.** 1C 전에 첫 사용자 5명을 대상으로, 팀을 만들려는 사람에게 팀원·스킬을 먼저 등록하는 법을 가르치지 않고 1번 과제를 준다. 제안 기준은 4명 이상이 도움 없이 예상한 결과를 열고, 스킬 저장 뒤 선택기를 닫는 순간과 A만 수정하는 순간에 무엇이 남는지 각각 맞히는 것이다. 실패한 위치·도움·복구·소요 시간을 기록한다. 그래프는 팀 구성에서 출발해 “검토가 끝까지 통과하지 않으면 무엇이 제출되나요?”, “아무도 자문을 구하지 않으면 Outrider는 몇 번 호출되나요?”라고 묻는다. 탭을 스스로 찾았는지와 예상 답(최종 제출 없음, 요청형 자문 0회)을 별도로 기록한다. 4–5단계에서는 다른 동등 난이도의 과제로 요청형 자문과 필수 검토에서 **누가 고치고 어느 버전을 제출하는지, 질문이 없을 때 호출이 생기는지**를 확인한다. 제안 기준은 5명 중 4명 이상의 정확한 예측이며, 미통과 후보 제출은 자동 검증에서도 0건이어야 한다. 현재판에 없는 라이브러리 생성 과제를 억지로 A/B 비교하지 않는다. 소규모 결과는 다음 수정 판단에 사용하며 모집단의 개선율로 해석하지 않는다.

**계획에서 달라진 결정**

- 하단 저장 바, 화면 제목과 소개 문장, 사이드바의 라이브러리 하위 메뉴, 카드 목록은 만들지 않는다(디자인안 0절).
- 팀 구성 목록은 구조 목록과 같은 순서·묶음을 처음부터 쓴다. 그래서 병렬·반복·판정·참조 팀의 사실대로의 요약(계획 2단계의 목록 부분)이 묶음 2에 들어온다.
- 원본의 과거 revision 본문은 조회하지 않는다. 쓰는 화면이 없다. `origin`은 revision 번호만 적는다.
- 스킬만 고른 역할의 기준은 설치마다 하나인 내장 최소 정책(`strict`)이다. 고정 Harness가 없는 역할은 지금도 명령 실행·미리보기 도구를 받지 못하므로 `strict`가 빼는 것이 없고, 스킬 본문 읽기만 더해진다. 기본값의 MCP·검사·LSP와 필수가 아닌 확장은 받지 않는다. 명령 실행이나 확장이 필요하면 그 역할에 실행 정책을 직접 고른다.
- 보기(팀 구성/흐름 그래프)는 팀마다 브라우저에 기억한다. 주소에 싣지 않는다.
- 기본 제공 역할의 모델 자리(`model-a`·`model-b`)는 서버의 기본 프로필 id와 같다. 자리와 고정값을 가르는 필드는 두지 않고, 설치에 없는 프로필은 지금처럼 문제로 표시한다.
- 팀 구성의 "에이전트 추가"는 언제나 선택기를 연다. 최종 결과가 한 단계에서만 들어오면 그 앞에 넣고(반복의 `다음`·`소진`을 모두 이어받는다) 최종 결과가 받던 결과를 기본 자료로 준다. 그 밖의 모양은 연결 없이 추가해 "연결 안 됨"에 보인다.
- 저장한 팀을 세션 대화에서 쓰면 리드가 역할에 위임하는 방식으로 돌고, 저장한 그래프는 지침이다. 편집기의 시험 실행은 저장한 노드를 그대로 실행한다. 단계 지시는 두 경로 모두 그 자리의 실행에 전달한다. 이 차이를 화면에서 알리는 일은 이 계획의 범위 밖으로 둔다.
- 새 팀은 저장 전 초안으로 연다. 초안을 열 때 받은 팀 id가 첫 저장의 `createId`가 되어 그 id로 팀이 만들어지고, 같은 요청이 다시 오면 원래 결과를 돌려준다. 고르는 대화상자(빈 팀·템플릿 사본·목표 초안)는 없앴다.
- 역할의 MCP 도구 선택은 권한을 좁히기만 한다. 실행 정책이 없는 역할은 도구를 골라도 쓸 수 없고 "실행 정책 고르기"로 안내한다. 카드에서 고르는 것만으로 쓰게 하려면 MCP를 허용하는 내장 기준 정책이 하나 더 필요한데, 그 정책은 명령 실행·앱 미리보기·작업 사본 접근까지 함께 열 수 있어 넣지 않았다. 도구 목록은 서버에 저장하지 않고 연결 검사를 쓴다.
- "채택된 자문"은 기록이 없으므로 화면이 말하지 않는다. 의견을 받은 것과 그 뒤 새 버전이 나온 것을 따로 보인다. 아무도 묻지 않았을 때의 "0회"는 실행이 시작된 저장 revision이나 시험 세션의 시작 정의를 알 때만 말한다.
- 템플릿, 목표 초안, 선택기의 기본 제공 에이전트가 만드는 자리는 맡은 일(단계 지시)과 공통 작업 규칙(역할의 기본 지시)을 나눠 갖는다. 맡은 일에는 그 자리의 일만 보인다. 이 팀들의 모델 입력은 한 덩어리 지시에서 기본 지시와 단계 지시 두 부분으로 바뀐다. 팀을 고르지 않은 대화의 자동 구성과 리드, 이미 저장된 팀은 그대로다. 목록의 첫 문장 요약은 예전 팀을 위해 남긴다.
- AI 대화에서 질문의 선택지는 한 번 누르면 그 답으로 바로 다음 응답을 받는다. 모델을 부르는 누름은 누르기 전에 모델 이름과 요청 한 번임을 보인다. 예시는 입력만 채운다.
- 팀 구성의 상세는 344px 패널이 아니라 작업 영역 전체다. 목록은 흐름 그래프의 구조 목록과 같은 머리·행·선택을 쓰는 구조 열이다. AI 대화는 두 보기에서 같은 자리에 놓인다. 편집기가 88rem 이상이면 오른쪽 열이고, 그보다 좁으면 작업 영역 아래에서 내용만큼만 펼쳐진다(디자인안 0절 "두 보기의 틀"). 라이브러리의 팀·에이전트·스킬 보기는 동작을 탭 줄 끝에 같은 크기로 두고, 상세는 이름 · 동작 · 내용 순이다.

**실제 모델 검증.** DeepSeek·GLM 실제 실행은 저장소 소유자가 허용했다. 임시 워크스페이스에 모델 설정만 복사해 돌리고, 일반 CI에는 넣지 않는다. 첫 사용자 5명 과제(1C 전과 4–5단계)는 사람이 해야 하며 자동 검증으로 대신하지 않는다.
