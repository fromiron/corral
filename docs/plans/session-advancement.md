# 세션 묶음·템플릿·증거 요약 플랜

작업 중인 플랜이다. 명세가 아니며 완료되면 삭제한다. 동작 계약은 각 단계가 고치는 [workbench](../specs/workbench.md), [라이브러리](../specs/features/library.md), [기능 미리보기](../specs/features/feature-preview.md), [canvas](../specs/features/canvas.md)와 새 기능 명세가 소유한다.

## 목표

"Corral 통합 기능 고도화" 제안서를 로드맵으로 채택하지 않고 부족분만 메운다. 사용자의 작업 단위는 세션이다. 새 Task 원장, 의존성 그래프, Agent Definition 원장, 추천·분해·Refiner, Scratch, 차트, 이벤트 트리거, 원격 협업은 만들지 않는다.

브랜치 `feat/session-advancement`는 `feat/product-redesign`(83671d64) 위에 쌓는다. 리디자인 브랜치에 커밋이 더해지면 merge로 가져온다.

## 확정 결정 (2026-11-10)

1. **작업 단위는 세션이다.** 화면에 "작업 보드", "Task", "백로그"를 쓰지 않는다. 작업 보드 미리보기는 1단계에서 지운다.
2. **6단계는 라이브 평가를 거친다.** 로그인된 GPT 모델 luna와 terra로 잰다. terra가 등록되어 있지 않으면 등록한다. 결과가 있을 때만 병합한다.
3. **auto 모드는 지금의 세 템플릿으로 고정한다.** 새 패턴은 초안 기능만 쓴다.
4. **세션 완료 기준은 그 세션의 요청이 쓰는 기준이 된다.** 구현하며 확인한 사실: 세션 요청은 저장한 팀의 그래프를 그대로 돌리지 않고 역할만 빌리므로, 팀이 가진 기준이나 검토 레시피의 고정 기준과 부딪히는 경우가 없다. 그 검사는 저장한 정의를 그대로 실행하는 시작에만 있고 세션 기준을 쓰지 않는다.
5. **예약은 auto 세션만 받는다.** 저장 팀 세션 예약은 하지 않는다.

## 진행표

| 단계 | 내용 | 크기 | 선행 | 상태 | 커밋 |
|---|---|---|---|---|---|
| 1 | 프로젝트 세션 탭을 상태별 묶음으로, 작업 보드 미리보기 삭제 | 작음 | 없음 | 완료(확장 E2E `session-discovery`의 빈 세션 시나리오는 `CI=1`에서 실패, 마지막 E2E 정리에서 고침) | 1단계 5커밋 + 행 정리 2커밋의 cherry-pick |
| 2 | 템플릿 다섯 개와 역할 프리셋 | 중간 | 없음 | 완료(확장 E2E 선택자는 고쳤으나 미실행) | 2단계 3커밋 + 카드 정리 3커밋의 cherry-pick |
| 3 | 프로젝트 수준 증거 요약(검사 · 판단 · 반영) | 중간 | 1 | 서버 조회 완료, 화면 진행 중 | 3a 커밋의 cherry-pick |
| 4 | 편집기에서 역할 가져오기(복사) | 작음~중간 | 2 | 완료(로컬 서버 화면에서의 모델 문제 표시와 작업 방식 판정은 화면으로 확인하지 못함) | 4단계 5커밋의 cherry-pick |
| 5 | 세션 완료 기준 | 중간 | 3 | 저장·전달 완료, 화면 진행 중 | 5a 6커밋의 cherry-pick |
| 6 | 목표 → 팀 초안의 패턴 확장 | 중간 | 2, 라이브 평가 | 구현 완료(`adv-stage-6`, 미병합). 라이브 평가는 계정 사용 한도 소진으로 대기 | |

각 단계의 순서는 스펙 → 실패하는 반례 테스트 → 구현 → 검사 → 실제 화면 확인 → 커밋이다. 이 표는 단계를 끝내는 커밋에서 갱신한다.

## 단계별 메모

- **1단계**: 서버와 계약은 바꾸지 않는다. 사이드바가 같이 쓰는 `sessionListState`는 고치지 않는다. 플래너 안과 달리 완료 묶음은 펼친 채 둔다. 대부분의 세션이 완료라서 접으면 목록이 비어 보인다.
- **2단계**: 프롬프트 품질은 재지 않는다. 구조(strict 컴파일, 도구 범위, mock 실행 완주)만 검증한다.
- **3단계**: 목록에서는 기록 시각만 비교한다. 정확한 현재 유효성은 기존 검사 보기가 계산한다. 터미널에서 직접 바꾼 변경은 잡히지 않는다.
- **5단계**: `work_sessions`에 열을 더하며 마이그레이션은 쓰지 않는다. 화면에 "기준 충족"이라고 쓰지 않는다.
- **6단계**: `AUTO_TEMPLATES`를 `TEAM_PATTERNS`에서 분리해 세 개로 고정한다. `AUTO_TEMPLATE_VERSION`과 auto 라우터 프롬프트는 바뀌지 않는다.

## 6단계 라이브 평가 (실행 전에 정한 기준)

- 올리려는 수치: 목표 문장에서 고른 패턴이 사람이 받아들일 패턴 집합에 드는 비율.
- 자료: 목표 40개(한국어·영어 반반, 패턴 여덟 가지를 고르게). 라벨은 모델을 돌리기 전에 썼다. 개발 세트 20개는 `tests/live/fixtures/team-draft-goals.dev.json`에 있고 프롬프트를 고칠 때 본다. 최종 세트 20개는 저장소 밖에 두고 마지막에 한 번만 연다.
- 모델: 로그인된 GPT의 luna(`gpt-6-luna`)와 terra(`gpt-6.1-terra`). 요청은 목표마다 한 번, 출력 상한은 지금 초안 요청과 같다. 개발 세트는 최대 세 번 돌린다(120요청 이내), 최종 세트는 한 번(40요청).
- 병합 기준: 최종 세트에서 두 모델 모두 20개 중 16개 이상이 받아들일 패턴이고, 계약을 통과하지 못한 답이 모델마다 1개 이하다. 못 미치면 6단계는 병합하지 않고 결과만 남긴다.
- 로컬 제안(모델 호출 없음)의 같은 비율도 함께 적는다. 비교 기준이지 병합 기준은 아니다.
- 진행(2026-11-11): 구현은 `adv-stage-6` 브랜치에 있고 병합하지 않았다. 개발 세트를 두 번 돌렸으나(41요청) 로그인된 계정의 사용 한도가 소진돼 모델 답을 하나도 받지 못했다. 프롬프트는 한 번도 고치지 않았다. 답이 없는 실행은 프롬프트를 조정할 기회가 아니므로 "최대 세 번"에 세지 않고, 요청 수 상한(120)에는 센다. 한도가 풀리면 개발 세트부터 다시 돌린다.
- 병합 기준의 "계약을 통과하지 못한 답"은 모델이 돌려준 답만 센다. 한도·제공자 오류로 답이 없으면 그 실행은 측정으로 치지 않는다.
- 개발 세트에서 로컬 제안은 20/20이었다(이전 규칙 9/20). 규칙을 쓴 사람이 개발 세트를 본 뒤라 높게 치우친 값이다. 치우치지 않은 값은 최종 세트에서 잰다.

## 구현 전에 확인할 것

- MockAdapter가 병렬 + Join 구조를 완주하는지(2단계 첫 테스트).
- 일반 세션 요청이 실행 입력의 기준을 만드는 경로와 `work_sessions` 스키마 생성 코드(5단계).
- `/preview/task-board`를 지운 뒤 알 수 없는 feature 주소의 처리(1단계).
- 세션이 수백 개일 때 프로젝트 세션 목록의 비용(1단계에서 한 번 잰다).
