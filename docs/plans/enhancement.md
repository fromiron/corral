# 강화 구현 계획

2026-11-28에 샘플 네 저장소의 비교 보고서를 근거로 외부 고문이 강화 플랜을 냈고, 주 세션이 그것을 명세와 코드에 두 번 대조했다. 이 계획은 대조를 통과한 항목을 누가 어떤 순서로 구현하는지와 진행 상태를 적는다. 고문의 플랜과 검토서는 저장소에 싣지 않는 곳에 있으므로, 묶음마다 위치·고칠 내용·확인 방법은 이 문서가 직접 갖는다.

[UI/UX 점검 개선](ux-audit-fixes.md)의 3단계, 4단계, "결정을 기다리는 것"도 이 계획이 묶음으로 나눠 맡는다. 그 문서에 있는 항목 ID의 뜻은 그 문서가 갖고, 거기 없는 ID는 이 문서가 풀어 적는다. 담당과 진행은 이 문서에만 적는다.

명세: [Workbench](../specs/workbench.md), [대화 입력 흐름](../specs/features/composer-flow.md), [확인 필요](../specs/features/inbox.md), [세션 패널](../specs/features/session-panel.md), [실행 기록 관찰](../specs/features/execution-monitor.md), [채팅 위젯 계약](../specs/chat-widgets-contract.md), [변경 검토의 실행별 묶음](../specs/features/review-run-groups.md), [팀 편집기](../specs/features/canvas.md), [팀 구성](../specs/features/team-composition.md), [AI 팀 채팅](../specs/features/team-assistant.md), [모델 연결](../specs/features/model-connections.md), [API 계약](../specs/api-contract.md), [용어집](../specs/glossary.md), [디자인 계약](../../DESIGN.md).

## 일하는 방식

- **묶음은 파일로 나눈다.** 한 파일은 한 묶음의 것이다. 두 항목이 같은 파일을 고치면 한 묶음으로 합치거나 순서를 정한다. 주제나 역할(명세 담당, 테스트 담당)로 나누지 않는다.
- **한 묶음은 한 담당이 끝까지 한다.** 명세 문장 → 실패하는 테스트 → 구현 → 검증을 같은 담당이 그 묶음의 파일과 지식 안에서 마친다.
- **담당은 물음 하나로 가른다: 화면을 보기 전에 수용 기준을 테스트로 쓸 수 있는가.**
  - 쓸 수 있으면 Opus 5.5가 맡는다.
  - 보면서 고쳐야 결과가 정해지면 주 세션(Fable)이 직접 만든다.
  - 결정은 몇 문장인데 구현이 큰 파일의 배관이면 Fable이 정하고 Opus가 구현한다. Fable은 결정을 그 묶음 브랜치의 명세 문장으로 먼저 커밋하고, Opus는 그 커밋에서 시작한다. Opus에게 미학적 선택을 남기지 않는다.
  - 같은 문법을 여러 화면에 되풀이하는 일은 Fable이 기준 화면 하나를 만들고 나머지를 Opus가 화면 파일 단위로 맡는다.
  - 파일 한두 개의 작은 수정은 에이전트를 띄우지 않고 주 세션이 한다.
- **병렬.** Opus는 한 번에 둘까지, 소스 파일이 겹치지 않을 때만 함께 돈다. `en.json`·`ko.json`, `tools/lint/`의 기준선, 여러 묶음이 고치는 명세는 주 세션이 합칠 때 맞춘다. 기존 키의 이름과 문구를 바꾸는 묶음(B1)은 다른 UI 브랜치가 열려 있지 않을 때만 돈다.
- **브랜치와 PR.** 단계마다 브랜치 하나에 묶음을 모으고, 항목 ID마다 커밋 하나다. Opus는 자기 worktree의 묶음 브랜치에서 일하고 push, PR, E2E는 하지 않는다. worktree에는 추적하는 파일만 있으므로 브리프는 이 문서의 묶음 절과 줄 번호만으로 선다. 주 세션이 코드와 화면을 검토해 단계 브랜치에 합치고, 합친 브랜치에서 `pnpm contracts:check`, lint, typecheck, 건드린 테스트를 돌린 뒤 `develop`을 향한 PR을 연다. PR gate가 push마다 전부 돌므로 push는 PR마다 한 번이다. PR의 병합은 소유자가 한다. 로컬 `develop`에는 직접 합치지 않는다. 소유자가 커밋하지 않은 변경이 있는 파일은 브랜치에서도 고치지 않는다.
- **시안과 전후 화면.** 정적 HTML 시안 묶음을 따로 만들지 않는다. 화면을 다시 짜는 묶음에서는 kit로 실제로 만든 기준 화면이 시안이다. 주 세션이 PR 본문에 전후 화면을 싣는다(같은 시나리오·폭·테마·언어의 짝, 1280×800과 390×844, 색이나 글 길이가 바뀌면 dark와 ko도). 저장소가 공개이므로 화면은 한 장씩 열어 경로나 요청 본문이 없는지 본 뒤에만 올린다. 모델이 있어야 생기는 상태는 화면이 없다고 적는다. 적힌 결정을 뒤집는 묶음은 따로 PR로 내어 소유자가 보고 병합한다.
- **판정.** 카드 2(결과 찾기)와 카드 3(변경 출처)은 사람을 모으지 않는다. 호버 없이 구별되는지를 정적 화면으로 확인하고, 소유자가 3분 써 본다.
- **검증.** 묶음마다 `pnpm lint`, `pnpm typecheck`, 건드린 패키지의 단위 테스트를 돌린다. 계약이 바뀌면 `pnpm contracts:check`도 돌린다. E2E는 건드린 spec만, 에이전트가 테스트를 돌리지 않을 때 주 세션이 돌린다. 전체 E2E는 끝에 한 번이다. 문자열은 en·ko에 함께 넣고, 화면은 모델 없는 서버의 Studio에서 걸어 확인한다.

## 정한 것

2026-11-28에 소유자가 분담을 정했다: 디자인 결정이나 미학적 판단이 드는 일은 Fable이, 단순 구현은 Opus가 한다. 아래는 그 분담에 따라 주 세션이 명세와 앞선 결정을 근거로 정한 것이다. `ux-audit-fixes.md`가 "결정을 기다리는 것"으로 두었던 항목이 여기에 들어 있으므로, 소유자가 달리 정하면 그 행을 고친다.

| 결정 | 근거 |
|---|---|
| 사이드바의 확인 필요 배지는 끝나지 않은 응답 대기 실행의 수다. 대화의 최신 실행만 보지 않는다. | `inbox.md` 배지 문단의 첫 문장이 "실행 수"이고, 확인 필요 목록도 기다리는 실행마다 항목 하나를 만든다. 둘째 문장("세션의 최신 실행 상태")을 첫 문장에 맞춘다. |
| 본문 수명 계약은 그대로 둔다. 앞선 실행의 본문을 더 오래 두는 기능은 더하지 않는다. | `api-contract.md`의 산출물 본문 수명. 화면은 "더 보관하지 않는다"를 정직하게 말하는 쪽으로 고친다. |
| 실패를 빈 값으로 받는 남은 조회(변경 탭의 Git 상태와 부모 병합, `@` 참조 검색)도 실패를 말하고 다시 시도를 둔다. | `ux-audit-fixes.md` "정한 것"의 첫 행과 같은 규칙이다. |
| 대기 카드의 제거에 되돌리기를 두지 않는다(CON-02). | 편집으로 되살리는 길이 있다. 보관 되돌리기 알림을 뺀 결정(`sample-absorption.md` T5)과 같은 선이다. |
| 실행 중에는 "지금 시작"을 꺼진 버튼으로 두지 않는다. 자동 시작이 켜져 있으면 그 자리를 비우고, 꺼져 있으면 실행이 끝난 뒤에 시작할 수 있다고 한 줄로 말한다(CON-05). | 스위치가 언제 시작하는지 이미 말하므로 켜져 있을 때의 이유는 같은 말의 반복이다. 꺼져 있으면 사람이 직접 시작해야 하므로 길을 말해야 한다(저장소의 디자인 스킬: 꺼진 상태는 이유와 다른 길이 있어야 한다). |
| 쓸 수 있는 모델이 없는 서버에서 AI 팀 채팅의 입력 자리는 지금 명세(모델 연결 버튼 하나)대로 둔다. | `team-assistant.md`와 그 수용 시나리오가 그렇게 정한다. 모델을 부를 수 없는 서버는 명세에 없는 다른 경우라 아래에 따로 둔다. |
| 빈 화면의 첫 동작은 하나이고 상자 안에 있다(SCR-03). | `glossary.md`의 빈 화면 규칙. |
| 제품 화면에 팔레트 비교 UI를 만들지 않는다. 카드 5는 QA 절차로만 둔다. | 좁은 화면에서 칸이 무너지고, 보려는 것은 같은 상태의 테마별 회귀다. |

아직 정하지 않은 것은 그 묶음에서 Fable이 화면을 보고 정한다.

- 3단계의 문구표: B1.
- 모델을 부를 수 없는 서버(시뮬레이션만 되는 서버)에서 모델 화면과 AI 팀 채팅 자리가 보일 것(SET-02, TEAM-04): C4에서 정하고 C5가 같은 문구를 쓴다.
- 좁은 폭에서 탭을 kit의 스크롤로 둘지 보기 선택기로 바꿀지: C6.

### A1 결과 행

- 명세: `session-panel.md`에 세션 결과 목록의 행과 해제 표시 문장을 더한다(지금은 없다). `execution-monitor.md`의 결과 보기에는 좁은 폭에서 출처와 버전이 어떻게 되는지를 더한다.
- 첫 단계: 앞선 실행의 해제된 최종 결과 줄을 지금 누르면 무엇이 나오는지 화면에서 본다(코드로만 확인했다).
- 커밋 1: 세션 결과 목록은 최종 결과이면 본문이 해제됐어도 여는 버튼으로 그리고 해제를 말하지 않는다. 본문을 읽을 수 있는 줄만 버튼이고, 해제된 줄은 종류와 무관하게 해제를 말하며 열리지 않는다.
- 커밋 2: 해제된 줄은 해제 문구가 앞에 와 역할과 실행 번호가 잘리고, 같은 역할이 두 실행에서 같은 종류를 내면 두 줄이 똑같이 보인다. 세션 결과 목록을 실행별 묶음으로 나누고, 행을 이름과 버전, 역할과 실행 번호, 끝의 종류 또는 해제 사실로 다시 짠다. 실행 안의 결과 목록은 표를 그대로 두고 좁은 폭만 고친다(SES-09): 출처는 부분 사이에서 줄을 바꾸고 버전 낱말은 줄을 바꾸지 않는다.
- 확인: `SessionPanels.test.tsx`, `RunResultVersions.rows.test.tsx`. 판정 화면은 실행 둘, 같은 역할의 실행 둘, 해제된 본문이 섞인 여섯 줄이다. 패널 360px과 390×844에서 모든 줄이 서로 다른 글로 읽힌다. 통과하면 카드 2는 끝이고 역할 필터는 만들지 않는다.

### A2 현황과 하단 통계

- 명세: `chat-widgets-contract.md`의 세션 하단 합계와 현황 문단. 이름을 한 번만 쓰는 규칙은 `workbench.md`에 이미 있다.
- Context 이름의 반복: "Context" 제목 옆에 "Context · awaiting request"처럼 이름이 다시 나온다. 대기뿐 아니라 오류·부분 측정 상태도 같다. 그 문구는 툴팁, 접근 이름, 낭독기 요약에도 쓰이므로 메시지를 고치지 않고, 제목 아래에 그리는 자리만 상세의 배지가 쓰는 이름 없는 상태 낱말(측정 전, 부분 측정, 측정 오류)을 쓴다.
- 하단 토큰 합계: 입력이나 출력 토큰을 보고한 호출이 없으면 0이 아니라 "토큰 보고 없음"(tokens not reported)이라고 적는다. 캐시의 "보고 없음"과 같은 규칙이다.
- 현황의 절(SCR-15): 상세를 여는 요약 셋(에이전트·컨텍스트·사용량)은 같은 Card 머리를 쓴다. 다른 곳으로 가는 행 둘(결과·변경)은 이름 아래 한 줄을 두는 inline 행이다. 여는 표시는 한 세로줄에 선다.
- 확인: `OverviewWidgets.test.tsx`, `ComposerStats.test.tsx`, `overview.test.ts`, 현황을 연 화면의 light·dark, en·ko.

### C5 팀 편집기의 첫 화면

- 첫 단계: 점검은 모델을 부를 수 없는 서버에서 새 Corral의 AI 요청 자리가 눌리지 않고 "Available on the local server"라고 말하는 것을 봤다(TEAM-04). 코드에서 그 문구는 모델 연결 동작이 없는 분기이고, 명세는 서버가 없는 브라우저 데모에만 그 문구를 정한다. 어느 조건에서 그 분기로 가는지 확인한다. 쓸 수 있는 모델이 없을 뿐인 서버에서는 명세대로 "모델 연결" 버튼이어야 하고, 모델을 부를 수 없는 서버에서는 C4가 정한 문구를 쓴다.

- 실행 탭 안에 탭 줄이 세 층이다(패널의 탭, 보기 다섯, 관계도와 목록). 관계도와 목록의 전환을 그래프 안으로 옮겨 두 층으로 줄인다. 보기 다섯은 합치지 않는다(SCR-14).
- 양방향 관계의 화살촉이 겹친다.
- 390px에서 탭 줄이 옅은 페이드 뒤로 탭을 통째로 숨기고(SCR-22), 서랍 폭의 실행 탭에서는 "Results"가 실행 정보 아이콘 밑에 깔린다(SES-10). kit 탭의 스크롤을 두고 가리는 것을 치우는 안과 보기 선택기로 바꾸는 안을 만들어 보고 정한다. 정한 규칙을 `WorkspacePage.tsx`의 탭 줄에도 쓴다. 같은 파일의 떨어져 보이는 분할 버튼도 고친다(SCR-17). Environment 탭의 읽기 실패 표시는 소유자가 미뤘으므로 건드리지 않는다.
- 확인: `RunPage.layout.test.tsx`, 390×844와 서랍 폭의 전후 화면.

### C7 새 회의 폼

- Fable이 먼저 커밋할 것: 폼의 구성을 `workbench.md`의 회의 문단에 적는다.
- 지금은 기본 참가자마다 다섯 필드(이름, 모델, 별칭, 역할 태그, 역할 설명)가 다 펼쳐져 있다(CON-11). 처음에는 제목, 참가자마다 이름과 모델, 서기 모델, 시작 버튼만 보인다. 별칭·역할 태그·역할 설명은 참가자의 세부를 펼치면 나온다.
- 수용 기준: 처음 보이는 입력이 여덟 개 이하다. 스크롤 없이 시작 버튼이 보인다. 펼치면 다섯 필드를 모두 고칠 수 있다. 회의를 만드는 API는 그대로다.
- 확인: `NewMeeting.test.tsx`, 1280×800과 390×844.

### C8 동시에 기다리는 승인 카드

- Fable이 먼저 커밋할 것: 요청 한 줄의 자리와 길이를 `composer-flow.md`의 "지금 필요한 것"에 적는다.
- 한 대화에서 서로 다른 실행의 승인 카드가 둘 이상 서면 카드가 똑같이 보인다. 그때만 실행 번호 옆에 그 실행을 시작한 요청의 첫 줄을 붙인다. 하나만 기다릴 때는 붙이지 않는다. 내부 ID는 보이지 않는다.
- 확인: `ApprovalPanel`의 단위 테스트(카드 하나, 실행이 다른 카드 둘). 승인은 모델이 있어야 생겨 화면으로는 걷지 못한다.

### C9 토큰과 대비, C10 토큰 정리와 테마 QA

- C9: 선택된 행과 채움 위의 보조 글자가 내장 테마에서 대비에 못 미친다(TOK-02, 03, 06). dark에서 Tabs 트랙과 그 아래 표면의 값이 같아 경계가 없고, 상태 배지가 꺼진 버튼과 같은 채움을 쓴다(SCR-19). 고정폭 글꼴(SCR-20). 단축키 목록의 키를 kit의 `Keycap`으로 그린다(SCR-18).
- C10: 쓰지 않는 토큰, 호환 별칭, 문서에 없는 값, 대화 폭의 문서·CSS 불일치, scrim 토큰 우회를 정리한다(TOK-09~14). 기존 스토리를 light, dark, 내장 팔레트로 돌려 대비와 접근성 검사를 통과하는지 보는 절차를 테스트로 고정한다(카드 5).
- 확인: `design.test.ts`, `density.test.ts`, 내장 테마의 표면별 대비 테스트, 테마 화면 다시 캡처.

## 이 계획에 없는 것

- 프로젝트 화면 Environment 탭의 읽기 실패 표시: 소유자가 미뤘다.
