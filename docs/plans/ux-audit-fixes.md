# UI/UX 점검 개선: 작업 계획

2026-11-26에 develop `0c9a0dc5`의 Studio를 점검했다. 흐름 지도 7개를 다시 그리고, 화면 221장을 캡처해 자동 접근성 검사와 렌더값 측정을 돌렸고, 디자인 토큰의 대비를 계산했다. 이 계획은 그 점검에서 나온 항목을 고치는 순서와 진행 상태를 적는다. 점검의 원자료(지도, run, 캡처, 영역 노트)는 저장소에 싣지 않는 곳에 있으므로, 각 항목의 위치·고칠 내용·확인 방법은 이 문서가 직접 갖는다.

명세: [Workbench](../specs/workbench.md), [대화 입력 흐름](../specs/features/composer-flow.md), [팀 편집기](../specs/features/canvas.md), [실행 기록 관찰](../specs/features/execution-monitor.md), [포크·중단점](../specs/features/fork-and-breakpoints.md), [기능 미리보기](../specs/features/feature-preview.md), [모델 연결](../specs/features/model-connections.md), [디자인 계약](../../DESIGN.md).

2026-11-15의 흐름 개선 계획(저장소에 싣지 않은 문서)의 P1 가운데 아직 남은 것은 이 계획의 ID로 옮겼다: UX-01은 TEAM-01, UX-02는 TEAM-10·TEAM-02, UX-03은 SET-04, UX-04는 MODEL-01, UX-06은 WB-02, UX-07은 WB-09다.

## 일하는 방식

- 두 갈래로 나눈다. 화면 흐름과 상태(페이지, 컴포저, 패널)는 `fix/ux-audit-flows`에서 Opus 5.5가, 디자인 kit·토큰·팔레트·사이드바·명세 문장과 검토·병합은 `fix/ux-audit-design`에서 주 세션이 맡는다. 두 갈래는 같은 파일을 고치지 않는다.
- 항목마다 명세 → 실패하는 테스트 → 구현 순서로 하고, 항목 ID마다 커밋 하나를 만든다.
- 문자열은 en·ko에 함께 넣는다. 기존 키의 이름과 문구를 바꾸는 일(3단계)은 흐름 갈래가 합쳐진 뒤에 한다.
- 단계마다 `pnpm lint`, `pnpm typecheck`, 건드린 패키지의 단위 테스트를 돌린다. E2E는 건드린 spec만 돌리고, 전체 E2E는 이 작업의 끝에 한 번 돌린다.
- 끝난 갈래는 로컬 `develop`에 합친다. `canvas.md`처럼 소유자가 커밋하지 않은 변경이 있는 파일은 합칠 때 그 변경을 보존한다.

## 정한 것

2026-11-27에 사용자가 방향 결정을 맡겼다("어느 쪽이 타당한지 검토해 그에 맞춰 고친다, 샘플을 참고한다"). 근거는 명세와 샘플 세 저장소의 같은 상황 처리다.

| 결정 | 근거 |
|---|---|
| 조회가 실패하면 "없음"이 아니라 원인과 다시 시도를 보인다. 코드를 명세에 맞춘다. | `workbench.md`가 이미 요구한다. 샘플은 실패한 조회를 모두 하나의 오류 상태(원인 + 다시 시도)로 그린다. |
| 원본 문서 탭의 읽기 전용 사유, 사이드바 미리보기의 돌아가기, Automation에서 연 설정의 복귀도 코드를 명세에 맞춘다. | 명세가 각각 분명히 적고 있고, 같은 화면의 다른 진입로는 이미 지킨다. |
| 예약 삭제는 줄 안에서 한 번 확인한다. 다른 행을 골라도 쓰던 폼은 남는다. 지금 실행은 그대로 둔다. | Library의 팀 삭제가 같은 확인을 쓴다. 샘플도 반복 작업의 삭제만 확인한다. |
| 중단점·한도 카드의 "실행 중지"는 다시 묻지 않는다. 카드가 이미 계속할지 멈출지를 묻는 질문이다. | 샘플은 그 자리에서 한 중지는 바로 실행하고, 목록에서 한 중지와 여럿을 한꺼번에 멈추는 중지만 묻는다. Corral의 컴포저 규칙(활성 실행 단위가 둘 이상이면 묻는다)과 같은 선이다. |
| 연결 추가 대화상자는 뒤로 가거나 방식을 바꿔도 대화상자가 열려 있는 동안 입력을 그대로 둔다. | 확인을 하나 더 두는 것보다 잃지 않게 하는 쪽이 덜 막는다. |
| 저장 충돌(팀, 예약)에는 같은 자리에 두 동작을 둔다: 최신본 불러오기, 내 편집으로 저장. | 지금은 새로 고침뿐이라 편집을 잃는다. |
| 요청을 입력창으로 가져올 때 쓰던 글이 있으면 그 뒤에 붙인다. | `composer-flow.md`가 질문에 쓰던 글에 이미 쓰는 규칙이다. |

## 3단계: 이름과 문구 (흐름 갈래를 합친 뒤)

- 요청의 이름: 바로 시작하는 첫 요청을 "다음 요청"이라 부르지 않는다(CON-03, SES-11). 대기 카드와 스위치는 한 명사를 쓴다.
- 팀 편집기: 요청·Brief·Run brief를 한 이름으로, Final result·Output을 한 이름으로(TEAM-07).
- Paddock을 만드는 동작의 네 이름을 하나로(WB-05), 폴더 용어를 한 경로 안에서 하나로(WB-06), "Link a folder"와 "Paddock"이 한 화면에 함께 나오는 곳을 하나로(SES-12).
- 대화상자 제목과 확인 버튼이 같은 "실행 중지"(SES-07), 이름이 같은 "열기" 버튼 둘(SES-06), 이름과 pressed가 겹치는 최대화(SES-08), 명령문으로 된 서랍 이름(NAV-06), 이동처럼 읽히지만 메뉴를 여는 경로 막대 버튼(CON-06).
- 번역 없이 드러나는 서버·core 문장을 코드로 받아 Studio에서 번역한다(TEAM-11). 요청 한도에 걸렸을 때의 문구도 여기서 고친다.
- 보이는 레이블이 접근 이름에 없는 네 요소(A11Y-02).

## 4단계: 화면 다시 짜기 (시안을 먼저 본다)

- 설정 폼: Folders & tools, Harnesses, 기본 Harness, Hooks & extensions, Settings vault. 필드 사이 설명 문장, 네 번 반복되는 이름, 행마다 늘 보이는 버튼 세 개, native 파일 입력(SCR-01, 02, 04, 10, 12, 13).
- 빈 상태와 첫 동작의 자리를 kit `EmptyState`의 action 자리 하나로(SCR-03, TEAM-12).
- 템플릿 목록, 새 Corral의 첫 화면, 데모 편집기의 툴바(SCR-07, 08, 09). 실행 패널의 탭 세 층(SCR-14). 새 회의 폼(CON-11).
- 좁은 폭에서 잘리는 탭(SCR-22, SES-10), dark의 Tabs 트랙과 상태 배지(SCR-19), 고정폭 글꼴(SCR-20).
- 토큰 정리: 쓰지 않는 토큰 7개, 호환 별칭(`border-line` 등), 문서에 없는 값, 대화 폭의 문서·CSS 불일치, scrim 토큰 우회(TOK-09~14).

## 결정을 기다리는 것

- 예약이 저장한 팀을 실행하게 할지, 대상 대화를 미리 채울지(TEAM-03).
- 대기 카드의 제거에 되돌리기를 둘지(CON-02). 실행 중 "지금 시작"을 숨길지 이유를 달지(CON-05).
- 사이드바 검색 칸이 전체 팔레트를 열지(NAV-04).
- 모델을 부를 수 없는 서버에서 Models 화면과 AI 팀 채팅이 무엇을 보일지(SET-02, TEAM-04).
- 준비 명령의 상태를 Changes 밖에서도 보일지(WB-07), Paddock 없는 Changes의 하위 탭(WB-10), 리뷰 결정 버튼 다섯 개(WB-12).
- 사람이 확인한 중지가 "3 failed"로 끝나는 것(SES-02): 실제 모델에서 같은지 먼저 확인한다.

## 확인하지 못하는 것

- 승인·질문·중단점처럼 모델이 있어야 생기는 상태는 모델 없는 서버에서 걸을 수 없다. 이 항목들은 컴포넌트 테스트로만 확인한다.
- 연결 추가 대화상자에는 실제 키를 넣지 않는다. 입력 보존은 테스트 값으로 단위 테스트에서 확인한다.
