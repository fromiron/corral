# 공통 Outrider와 팀 편집기 사용성 개선 계획

**대표 과제. “기획자와 작성자가 필요할 때 같은 조언자에게 물어볼 수 있게 하고, 작성자가 원고를 리뷰받아 직접 고쳐 제출하게 하세요.”** 사용자는 팀에 Outrider를 한 번 추가한다. 기획과 작성이 각각 진행되는 중에 자문할 수 있고, 질문이 없으면 평소대로 작업한다. 교정 의견을 받아 작성자가 V2를 제출하면 최종본의 생산자는 작성자다.

## 사용자가 설정하는 것

| 팀 설정 | 권장 기본값 | 작업 중 일어나는 일 |
| --- | --- | --- |
| 공통 Outrider 추가 | 팀에 추가한 뒤 요청형 자문 켜짐 | 적격 작업자 누구나 자기 판단으로 질문한다. 답은 그 질문을 한 작업자에게 돌아간다. |
| 대상 | 팀 전체. 필요하면 직접 선택 | 팀 전체이면 이후 추가한 작업자도 포함한다. 대상 요약을 열어 실제 명단을 확인한다. |
| 산출물 리뷰 | 끔. 켜면 ‘요청할 때’ | 작업자가 검토할 버전을 지정한다. Outrider가 수정할 곳과 이유를 답하고 작업자가 반영·재제출한다. |
| 진행 중 자동 관찰 | 끔 | 선택한 작업 기록을 주기적으로 읽고, 필요한 경우 Outrider가 먼저 의견을 보낸다. |
| 검토 통과 후 제출 | 사용자가 해당 결과에 명시적으로 선택 | 지정한 버전의 통과가 최종 제출 조건이 된다. 실패·한도 소진 때도 미통과 버전은 최종 확정되지 않는다. |

편집기 구조 목록의 팀 수준에 `공통 Outrider 추가`를 두고, 추가 후에는 `Outrider · 팀 전체`에서 모델·검토 원칙·대상·옵션을 수정한다. 캔버스의 순차 작업 열은 기획자 → 작성자 → 출력으로 읽힌다. Outrider를 선택하면 질문할 수 있는 작업자와 관찰 대상을 확인하고, 개별 작업자를 선택하면 그 작업자가 누구에게 질문할 수 있는지 본다. 실행 중인 작업자가 질문하므로 사람에게 매번 자문 버튼을 누르거나 연결선을 그리라고 요구하지 않는다. 시험 기록에는 **실제 질문자, 질문한 이유, 받은 답, 검토한 버전, 실제 제출자**가 해당하는 경우에만 나타난다.

## PR 1. 모든 작업자가 요청할 수 있는 공통 Outrider

**기존 기반.** 현재 Outrider 노드(`observer`)는 관찰 대상에게 먼저 조언한다. 질문을 받는 경로는 작업자 → `question` → `callable`이며, 질문마다 별도의 응답 작업을 만들고 `reply`로 호출자에게 돌려준다. 새로운 제품 동작은 이 두 역할을 팀 공통 설정 한 곳에서 관리하는 것이다. 기존 관찰 노드와 대화 설정에는 지금의 동작을 유지한다. [Outrider](../specs/features/advisor.md) · [협업 메시지](../specs/product-contract.md) · [그래프 규칙](../specs/features/team-graph.md)

**저장과 실행.** 팀 정의에 선택적인 공통 Outrider 설정을 두는 방안을 구현 기준으로 삼는다. 모델·원칙·대상 선택 방식과 켠 옵션을 저장하고, 기존 팀은 필드가 없으면 지금처럼 읽는다. 편집기 미리보기와 서버가 같은 규칙으로 요청 역할·질문 연결·권한을 계산한다. 역할 이름이나 선 모양으로 기존 사용자 노드를 공통 조언자로 추정하지 않는다. 저장·다시 열기·복제·JSON 왕복에도 ‘전체’와 ‘직접 선택’ 의도가 유지돼야 한다. 적용·해제는 각각 Undo 한 단계이며 해제할 때는 사용자가 별도로 만든 질문 링크·권한을 보존한다. 실행 중인 Run은 시작 당시 설정을 따른다. [정의 계약](../../packages/contracts/src/definition.ts) · [기존 질문 연결](../../packages/react/src/editor/model.ts) · [컴파일러](../../packages/core/src/compiler/index.ts)

**누가 질문하는가.** 팀 전체의 기준은 이번 팀 실행에서 일을 하는 `scheduled`·`callable` 에이전트다. Loop·하위 팀의 작업자와 호출로 시작한 작업자도 실행 순서의 위치에 관계없이 포함한다. 참조 팀은 고정 revision으로 펼친 실행 사본에서 실제 작업자와 권한을 판정하고 원본을 수정하지 않는다. 공통 조언자 자신·다른 관찰자·판정·합류·출력은 질문자에서 제외한다. 기존 한도나 권한 때문에 자문할 수 없는 대상은 대상 목록에서 원인을 알려준다. 작업자에게는 조언자에게 묻는 권한을, 응답 역할에는 `reply`와 허용된 읽기만 준다. 쓰기·셸 실행·승인·재위임 권한을 추가하지 않는다. [참조 팀 전개](../../packages/core/src/expand-teams.ts) · [도구 허용 검사](../../packages/core/src/admission/index.ts) · [에이전트 도구 노출](../../packages/adapter-pi/src/adapter.ts)

**질문 수명과 시험.** 기존 Coordinator의 질문 ID, 요청 실행·시도, 대기·취소·타임아웃, 사용량과 깊이·질문·동시성 한도를 따른다. 같은 Outrider 모델·원칙을 쓰되 각 요청은 자기 질문과 허용된 자료만 받는다. 한 질문의 지연이나 실패는 그 호출자에게 사유로 돌아가고 일반 작업의 다음 행동을 선택할 수 있다. 작업자에게 모델·도구 호출을 추가로 허용하는 범위는 확인한 대상과 자문에 한정한다. 답변 내역은 요청자별로 구분하고 호출·사용량은 실제 응답 실행에 귀속한다. 자문 설정 자체가 모델을 호출하지 않는다. 기록에서는 ‘질문 가능’, ‘답변 대기’, ‘답변 받음’을 구분한다. [질문·응답 실행](../../packages/core/src/coordinator.ts) · [협업 테스트](../../packages/core/test/collaboration.test.ts)

**인수 검증.** 한 팀에서 기획자와 작성자가 같은 조언자에게 서로 다른 질문을 보내 각각 맞는 답을 받아 계속 작업한다. 동시에 보낸 두 질문 중 하나만 취소하거나 시간을 넘겨도 다른 질문은 정상 완료되고, 늦은 답은 닫힌 질문을 다시 열지 않는다. 한 번도 묻지 않은 모의 실행에서는 조언자 호출 0회, 기존 최종 출처와 실행 순서를 확인한다. 전체 선택 후 작업자 추가, 직접 선택에서 제외, 참조 팀 내부 작업자, 기존 관찰 전용 팀을 각각 검증한다.

## PR 2A. 산출물 교정 지시를 받고 원래 작성자가 제출하기

`산출물 리뷰 → 요청할 때`를 켠 팀에서 작성자는 “원고 V1에서 근거가 빠진 문장을 찾아줘”처럼 질문할 수 있다. 읽을 수 있는 명시적 버전을 기존 질문의 `artifactRefs`로 보내고, 받은 의견은 질문 ID와 그 버전에 묶는다. 구조화된 리뷰 표시가 필요하면 발동 종류와 대상 버전을 판별할 최소 정보만 기존 협업 계약에 보완한다. 일반 질문에 첨부한 파일과 정식 리뷰 요청의 차이를 문구로 추측하지 않는다. 옵션을 꺼도 일반 자문은 사용할 수 있다. [질문 계약](../specs/product-contract.md) · [질문 도구](../../packages/core/src/coordinator.ts) · [읽기 범위 검사](../../packages/core/src/admission/index.ts)

작업 과정에는 `작성자 → Outrider · 원고 V1 리뷰 요청`과 답을 연결한다. 작성자가 V2를 만들어 제출한 경우에만 `제출된 결과 · 작성자 · V2`를 표시한다. 의견 전달만으로 ‘수정 완료’나 ‘리뷰 통과’를 표기하지 않는다. 의견을 채택하지 않고 V1을 제출해도 요청형 리뷰는 정상적인 결과다. 시험 패널에서 확정된 버전을 직접 열며, 여러 건이면 각각의 실제 생산자·버전을 확인한다. [실행 결과](../../packages/react/src/components/RunView.tsx) · [시험 패널](../../apps/studio/src/pages/EditorPage.tsx)

**첫 사용 가능 범위의 인수 검증.** 모의 실행에서 기획자와 작성자의 자문을 확인하고, 작성자의 V1 요청 → V1에 대한 조언 → 작성자가 수정한 V2 → `output.finalized`의 V2 → 사용자가 연 V2 내용까지 대조한다. 리뷰를 켜고도 요청하지 않은 실행, V1 검토 도중 V2가 생긴 경우, 접근할 수 없는 버전 요청, V1 그대로 제출도 검증한다. 자동 관찰과 필수 검토는 이 과제의 전제 조건이 아니다.

## PR 2B. 두 생산자가 있을 때 최종본 출처 선택

이 단계의 ‘편집자’은 직접 수정본을 생산하는 일반 작업 에이전트다. 작성자가 Outrider 의견을 받아 직접 수정한 경우에는 작성자의 결과를 계속 받는다.

**캔버스에서는 받을 결과를, 시험 패널에서는 실제 제출된 결과를 보여준다.** 구조 목록은 단계 탐색에, 설정 시트는 선택한 관계와 속성 편집에 쓴다. 출력 카드 전체가 선택 버튼이므로 기본 카드에는 출처 한 줄을 둔다. 기존 점선은 위임·질문을 표현하는 데 사용한다.

| 사용자가 한 일 | 출력 카드와 다음 행동 |
| --- | --- |
| 작성자 → 출력인 팀을 연다. | 카드에 `받을 결과 · 작성자`가 보인다. 카드를 선택하면 설정에서 `받을 결과 변경`을 찾을 수 있다. |
| 작성자와 출력 사이에 편집자를 넣는다. | 실행 순서는 작성자 → 편집자 → 출력으로 바뀌고 카드의 출처는 작성자다. 삽입한 자리 옆에 `편집자 결과 사용`을 한 번 제공한다. 안내를 닫은 뒤에도 출력 카드에서 변경할 수 있다. |
| 편집자의 결과를 고른다. | 카드가 `받을 결과 · 편집자`로 바뀐다. Undo 한 번이면 작성자 출처로, 한 번 더 하면 삽입 전 그래프로 돌아간다. |
| 시험을 마친다. | 시험 패널에 `제출된 결과 · 편집자`와 실제 산출물 이름·버전을 표시한다. 선택하면 그 버전의 내용을 연다. 실행 후 초안에서 역할 이름이나 출처를 바꿔도 이전 실행의 결과는 해당 실행 기록을 기준으로 표시한다. |

**편집 명령.** 출처 교체는 선택한 출력의 `task_output` 입력 한 항목에서 `sourceNodeId`만 바꾸는 순수 명령으로 구현한다. 입력 이름·순서·나머지 입력과 실행선을 보존한다. 기존 `withSuggestedBinding()`은 새 연결에 입력을 제안할 때 쓴다. 교체 후보는 같은 정의에서 출력을 선행하는 실행 에이전트나 허용된 참조 팀으로 한정한다. 후보가 무효이면 이유를 표시하고, 취소·거절·동일 출처 재선택은 Undo 기록을 만들지 않는다. ## PR 3. 편집기와 시험 패널의 판정 일치

## PR 4. 새 팀 생성과 목표 기반 Outrider 제안

- 라이브러리의 **새 Corral**에서 `목표로 초안 만들기`, `템플릿에서 시작`, `빈 팀 직접 구성`을 함께 제공한다. 목표와 템플릿은 기존 경로를 재사용하고 선택한 프로젝트를 유지한다. 시작 방법을 둘러보거나 취소한 시점에는 팀을 생성하지 않는다.
- 직접 구성에서는 기본 이름을 제공하고 **할 일과 완료 기준 한 가지**를 입력받아 팀을 만든다. 저장용 초안에도 두 필드가 필요하다. 예문은 입력 전 안내로만 보여준다. 템플릿 목록의 ‘빈 캔버스’도 이 경로를 사용한다. 이미 저장된 문장은 예문과 같아도 사용자 데이터로 취급한다.
- 빈 화면의 문맥 동작은 `첫 에이전트 추가`다. 실행 에이전트 하나를 넣은 뒤에는 `이 결과를 최종본으로 받기`로 출력 단계·입력·실행선을 한 번에 만들 수 있다. 숙련자는 같은 자리에서 전체 단계 메뉴를 연다. 초기의 중복 진단은 다음 행동 하나로 요약하고, 상세 문제는 화면 언어로 읽고 고칠 곳으로 이동하게 한다.
- 팀 이름·요청·기준은 `팀 설정`에 둔다. 시험 준비 첫 줄의 요청을 읽고 `요청 수정`을 선택하면 같은 작업 사본을 편집한다. 저장 상태와 데모·서버의 실행 방식을 그대로 따른다.

**목표에서 초안 만들기.** “모두가 필요할 때 전문가에게 물어보게 해줘”는 기존 팀 패턴에 공통 Outrider의 자문 설정을 더한다. “작성자가 원고 리뷰를 요청할 수 있게”는 요청형 산출물 리뷰를 제안한다. “리뷰 후 제출”처럼 의견인지 필수 통과인지가 모호하면 “수정 의견만 받으면 되나요, 통과해야 제출하나요?” 한 가지만 확인한다. 쓰기·검토 권한과 실행 경로에 영향을 주는 변경은 저장 전 미리보기에서 확인한다. 자동 관찰과 필수 검토는 해당 PR이 검증된 뒤 선택지를 연결한다. 로컬 추천과 모델 제안은 같은 형식·검사·미리보기를 사용한다. [초안 계약](../../packages/contracts/src/team-plan.ts) · [로컬 팀 제안](../../packages/core/src/team-draft.ts) · [모델 제안](../../apps/server/src/models/team-draft.ts)

**인수 검증.** “작업자가 직접 고쳐 제출”, “요청할 때 자문”, “매 제출 전 반드시 통과”가 각각 의도한 역할·정책으로 보이고, 자문 요청만으로 순차 검토 단계가 생기지 않는지 확인한다. 빈 프로젝트에서 세 경로를 찾고, 직접 적은 요청과 기준이 저장본과 시험 입력에 전달되는지 확인한다. 만들기 취소, 필수값 누락, 저장 실패 후 입력 보존, 기존 팀과 템플릿 원본 보존을 확인한다. ## PR 5. 자동 관찰을 선택적으로 켜기

팀 설정에서 `진행 중 자동 관찰`을 켜면 관찰 대상, 사용할 모델, 검토 간격과 호출이 발생하는 시점을 볼 수 있다. 기존 `observer → advise` 경로를 사용한다. 참고·우려·중단 권고의 전달, 마지막 검토와 종료된 대상 처리, 사용량 표시와 Run 중지 동작은 [Outrider 명세](../specs/features/advisor.md)와 [Reins 명세](../specs/features/reins.md)를 따른다. 작업 과정에는 작업자가 요청해 받은 답과 Outrider가 관찰 중 보낸 의견을 구별해 표시한다. 모델에 전달된 의견을 반영 완료로 표시하지 않는다.

**인수 검증.** 요청형만 켠 팀에서 질문이 없으면 Outrider 호출은 0회다. 관찰을 켜면 선택된 대상에서만 검토가 시작된다. 다음 실행에서 관찰을 끈 뒤에도 작업자가 질문하면 답을 받는다. 기존 관찰 전용 팀과 대화 설정의 Outrider는 이전과 같은 시점에 동작해야 한다. ## PR 6. 명시적으로 선택한 제출 전 필수 검토

사용자가 특정 최종 산출물에 `검토 통과 후 제출`을 선택하면 대상과 되돌릴 작업자를 보여준다. 공통 Outrider의 검토 원칙·모델을 이용하는 검토 역할과 기존 Reviewer·Decision·Loop를 사용해 흐름을 구성한다. 검토 통과는 **검토받은 후보 버전**에 귀속된다. 수정 필요이면 원래 생산자가 새 버전을 만들고 다시 검토받는다. 사람의 최종 승인 설정은 별개의 동작이다.

기존 Loop 감싸기는 소진 출구가 다음 단계로 이어질 수 있다. 필수 검토를 생성할 때는 소진·검토 실패·취소에서 미통과 후보가 Output에 도달하는 경로를 차단한다. 상한에 닿으면 이유와 부분 결과를 남긴다. 그래프 편집으로 검토를 우회하는 경로가 생기면 해당 선을 진단하고, 경로를 고치거나 사용자가 필수 정책을 명시적으로 해제할 때까지 시험과 서버 실행을 차단한다. 미완성 초안은 기존 저장 규칙을 따른다. [Loop 소진 규칙](../specs/features/team-graph.md) · [기존 검토 패턴](../../packages/react/src/team-editor/commands.ts) · [검토 레시피](../specs/harness-contract.md)

**인수 검증.** V1 수정 권고 → 생산자의 V2 → V2 통과 → V2 최종 확정까지 추적한다. V1만 통과한 뒤 내용이 바뀐 경우, 계속 수정 판정을 받아 한도가 소진된 경우, 검토가 실패하거나 중지된 경우에는 미검토 버전의 최종 확정 이벤트가 없어야 한다. 요청형 리뷰만 켠 팀은 조언을 채택하지 않아도 기존 방식대로 제출한다.

## PR 7B. 연결을 편집하고 같은 카드로 돌아오기

- **연결 시작.** 카드의 `다음 단계 연결`이나 출력 포트 클릭으로 연결을 시작한다. 연결할 수 있는 대상과 입력 포트를 표시한다. 카드 선택·키보드 선택·기존 포트 드래그가 같은 연결 명령을 사용한다. 잘못 고르면 그 위치에서 이유를 읽고 다시 선택하며 Esc로 취소할 수 있다. 포트를 끌어 놓은 직후 클릭 연결이 다시 시작되지 않아야 한다.
- **연결 변경.** 기존 선을 선택하면 양 끝 이름과 `다음 실행`, `위임`, `질문`, `관찰` 중 해당 관계를 표시한다. 실행선의 `대상 변경`, `연결 해제`, 같은 포트에 `병렬 단계 추가`를 구별한다. 대상 교체가 실패하면 원래 선을 보존한다. 포트 규칙에 맞아도 전체 그래프에 합류가 필요하면 문제와 고칠 곳을 보여준다. Router 경로와 판정의 통과·실패는 해당 선에서 읽을 수 있게 한다.
- **설정 찾기.** 선택한 단계의 다음 실행과 받는 입력을 설정 시트 상단에 둔다. 위임·질문·관찰은 해당 역할에서, 모델·권한 등 세부 필드는 이어지는 설정에서 제공한다. 검토·승인·규칙을 새로 만들면 고른 종류와 화면 언어에 맞는 이름을 붙인다. 기존 사용자 지정 이름은 유지한다.
- **좁은 화면.** 카드 선택은 캔버스 위치를 유지하고, 카드 가까이의 `편집자 설정 열기`를 누르면 설정 필드로 이동한다. 닫으면 같은 카드로 포커스를 돌린다. 구조 목록·문제 목록에서 설정을 연 사용자는 해당 대상까지 이동할 수 있어야 한다.

**인수 검증.** 같은 합법 연결을 포트 드래그, 클릭, 키보드로 만들고 대상 교체·병렬 추가·거절 후 재선택·취소를 확인한다. 390×844와 좁은 세션 패널에서 역할을 편집하고 선택 카드로 복귀한다. 패닝·팔레트 및 구조 목록 D&D, 읽을 수 있는 관계 이름, 키보드 포커스와 동작 줄이기를 확인한다. **사용성 확인.** 대표 과제는 기획자·작성자·출력만 있는 팀에서 시작한다. 조작법을 알려주지 않고 “둘 다 필요할 때 같은 전문가에게 물을 수 있게 하세요. 작성자는 초안 의견을 받아 직접 고쳐 제출해야 합니다”라고 요청한다. 동일한 모의 작업으로 아래를 관찰한다.

1. 개별 연결을 그리지 않고 팀 전체 자문과 요청형 리뷰를 설정하고 저장·재열기 할 수 있는가. 실행 전에 누가 질문하고 누가 최종본을 낼지 설명할 수 있는가.
2. 시험 기록에서 각 질문의 답을 찾고, 리뷰받은 V1과 작성자가 제출한 V2를 각각 열 수 있는가. 완료 시간은 과제 제시부터 **기대한 생산자의 최종 산출물을 열어 확인한 순간**까지 잰다.
3. 관찰만 끄고 일반 질문을 유지할 수 있는가. “의견만 받기”와 “통과해야 제출”의 차이를 실제 통과·소진 사례의 결과로 예측할 수 있는가. 해당 옵션 구현 뒤 별도로 검증한다.
4. 별도 생산자 과제에서는 편집자도 계속 실행하되 원본을 제출하도록 설정한다. 좁은 화면에서는 같은 카드에서 설정을 고치고 돌아온다. 새 팀 만들기는 빈 라이브러리에서 시작한다.

도움 없이 완료했는지, 예상한 수신자·생산자가 맞았는지, 잘못 바꾼 관계, 도움을 요청한 지점, 스스로 복구했는지를 기록한다. 실제 참여자 성공률·개선 폭은 아직 미측정이다.

**진행 상태.** PR 1에서 공통 요청형 설정과 실행 경로를 구현했다. 서로 다른 요청의 답·취소·시간 초과, 조언자 호출 0회, 저장·복제·가져오기와 기존 관찰 전용 팀을 모의 실행으로 검증했다. 실제 Studio 서버와 Chromium에서 설정 저장·재열기·제거 후 한 단계 Undo를 확인했다. 선택한 작업자의 삭제 뒤 ID가 재사용돼도 새 작업자가 자문 권한을 상속하지 않는다. 실제 DeepSeek 작업자 두 명이 GLM Outrider에게 각자 질문해 답을 받고 작성자가 최종 제출했다(모델 요청 9회, 보고된 출력 토큰 1,153개). 실제 초보 사용자의 과제 성공률은 미측정이다.

PR 2A의 첫 사용 가능 범위는 실제 서버 UI와 유료 모델에서 확인했다. Chromium의 편집기에서 요청형 리뷰를 켜고 저장·재열기한 뒤 V1 의견과 작성자의 V2 원문을 열었다. DeepSeek 기획자·작성자, GLM 조언자로 실행한 성공 사례는 두 질문의 답과 작성자가 최종 V2에 반영한 조언의 고유 문구까지 확인했다(모델 요청 10회, 보고된 출력 토큰 1,894개). 별도 실험에서는 조언자의 응답 기한 초과 후 작성자가 제출한 경우와 작업자가 자문을 생략한 경우도 관찰했다. 다음은 두 일반 작업자의 출력 출처 선택이다.
