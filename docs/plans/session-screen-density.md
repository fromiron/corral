# 세션 화면 밀도 개선: 작업 계획

세션(대화) 화면을 1280×800에서 걸어 보고 잰 결과, 핵심 작업은 한두 번의 클릭으로 닿는다. 복잡하게 느껴지는 까닭은 깊이가 아니라 한 화면에 함께 놓이는 양과, 같은 일을 하는 길이 여럿인 데 있다. 이 계획은 그중 방향이 정해진 것을 고치고, 큰 항목은 시안으로 방향을 정한 뒤 고친다.

명세: [Workbench](../specs/workbench.md), [채팅 위젯](../specs/chat-widgets-contract.md), [컴포저 흐름](../specs/features/composer-flow.md), [실행 모니터](../specs/features/execution-monitor.md), [모델·추론·리소스](../specs/models-and-resources.md).

브랜치는 `develop`에서 분기한 `fix/session-screen-density` 하나다. 단계마다 커밋하고, 동작이 바뀌는 단계는 명세 → 실패하는 테스트 → 구현 순서로 한다. 단계마다 `pnpm lint`, `pnpm typecheck`, 관련 테스트를 돌리고 실제 화면에서 확인한다. E2E 흐름 묶음은 끝에 한 번 돌린다.

잰 값과 걷기 기록은 저장소에 싣지 않는 `ux-flows/`에 있다(지도 `session-tasks.flow.json`, 기록 `runs/`, 정리 `notes/session-screen.md`). 고친 뒤 같은 여정을 다시 걸어 새 기록으로 남기고 비교한다.

| 단계 | 내용 | 상태 |
|---|---|---|
| S0 | 설정의 작업 폴더 줄: 긴 경로가 입력과 버튼을 줄 밖으로 밀어냄 | 완료 |
| S1 | 폴더가 없는 대화의 안내: 문구가 가리키는 곳과 버튼이 여는 곳이 다름 | 완료 |
| S2 | 도구 줄의 모델 칩: 긴 이름이 두세 줄이 되어 컴포저가 자람 | 완료. 긴 팀 이름은 이어서 |
| S3 | 라이브러리 리소스 행의 "관리"가 그 항목을 연다 | 명세 반영, 구현 다음 |
| S4 | 경로의 제목 메뉴는 대화 고르기만 한다 | 명세 반영, 구현 다음 |
| S5 | 대화의 표시는 주소의 실행 선택을 따르지 않는다 | 확인 중 |
| S6 | 큰 항목 셋의 시안과 결정 | S3–S5 다음 |
| S7 | 작업 영역의 최소 폭: 파일 뷰어는 자리가 남을 때만 옆에 붙는다 | 명세 반영, 구현 다음 |

## S2. 모델 칩

[컴포저 흐름](../specs/features/composer-flow.md)은 도구 줄이 늘 한 줄 높이라고 하는데, 그보다 먼저 정한 킷의 칩은 긴 이름을 여러 줄로 보였다. 컴포저의 도구 줄은 640px 폭부터 한 줄 모드(`toolbar="single"`)이고 왼쪽 묶음이 자리를 내주므로, 1280 폭에서도 36자 이름이 두 줄, 파일 뷰어를 열면 세 줄이 됐다.

한 것: 한 줄 도구 줄에서는 칩도 한 줄이고 이름이 말줄임으로 준다. 전체 이름은 툴팁으로 읽는다. 아이콘 버튼은 줄지 않고, 보이지 못하는 보내기 키 안내는 자리를 차지하지 않는다. 도구 줄이 여러 줄로 접히는 640px 미만과 칩 혼자 쓰일 때는 그대로 줄을 바꾼다([Workbench](../specs/workbench.md)의 390px 검증 문장은 그대로다).

같은 대화, 같은 설정에서 고치기 전과 후를 쟀다(파일 뷰어를 연 창 폭 1024~1280). 고친 뒤 도구 줄은 어느 폭에서나 28px이고 권한 버튼은 어느 폭에서도 전보다 덜 보이지 않는다. 고치기 전에는 대화 칸 502px 이하에서 이름이 한 글자씩 33줄로 쌓여 컴포저가 749px이 됐다.

남은 것:
- 대화 칸이 약 450px 아래면 권한 버튼이 가려진다(고치기 전에도 그랬다). S7이 그 폭을 없앤다.
- 긴 팀 이름(40자)의 Corral 칩은 줄지 않아 1280 폭에서도 모델 칩과 권한 버튼을 밀어낸다(고치기 전에도 그랬다). 이 계획에서 이어서 고친다.
- 컴포저 흐름의 "늘 한 줄 높이"에는 폭 조건이 없다. 640px 미만에서는 도구 줄이 여러 줄이 되므로 그 문장을 좁은 폭에 맞게 고칠지 정해야 한다.

## S3. 라이브러리의 "관리"

리소스 행의 "관리"는 설정의 맞는 구역을 열지만 항목을 고르지 않는다. 링크가 그 리소스의 키를 이동 상태에 싣고(주소에는 싣지 않는다), 설정이 목록을 읽은 뒤 한 번 그 항목을 고른다. 보관된 항목이면 보관한 항목 보기를 켠다. 패키지는 고르는 목록이 없어 그 줄로 가서 초점을 둔다. 명세는 [라이브러리](../specs/features/library.md)에 있다.

## S4. 제목 메뉴

경로의 대화 제목 메뉴와 상단의 더 보기 메뉴가 이름 바꾸기, 완료 기준, 고정, 보관을 함께 실었다. 제목 메뉴에는 대화 목록만 남기고 동작은 더 보기 메뉴에만 둔다. 회의 화면의 제목 메뉴도 같은 컴포넌트라 함께 바뀐다. 명령 팔레트의 명령은 그대로다. 명세는 [채팅 위젯](../specs/chat-widgets-contract.md)의 배치와 [Workbench](../specs/workbench.md)의 완료 기준 문장에 있다.

사이드바의 대화 행 메뉴와 상단의 더 보기 버튼은 같은 접근 이름("{제목} 메뉴")을 쓴다. 이 단계에서는 바꾸지 않는다.

## S5. 실행 선택

실행 기록에서 지난 실행을 본 뒤 대화 탭으로 돌아오면 주소에 선택이 남아, 컴포저에 "다른 실행을 보는 중" 경고가 뜨고 활동 바와 현황이 선택한 실행을 말한다. [채팅 위젯](../specs/chat-widgets-contract.md)은 대화의 요약·활동 표시가 진행 중인 실행, 없으면 마지막 실행을 따른다고 이미 정해 두었고, 코드만 주소의 선택을 먼저 따른다.

정한 것: 대화의 표시는 주소의 실행 선택을 따르지 않는다. 주소와 실행 기록 탭의 선택은 그대로 두어, 실행 기록 탭은 지금처럼 마지막에 본 실행을 다시 연다(이 동작을 바꿀지는 S6의 "실행 기록으로 가는 길"에서 정한다). 초안과 보낼 대상은 바뀌지 않는다.

구현 전에 확인할 것: 대화에서 지난 실행의 계획·변경·컨텍스트·사용량을 읽던 길이 실행 기록 탭에도 있는지, 지난 실행을 보는 동안 다른 실행이 진행 중임을 실행 기록 탭이 어떻게 알리는지. 갈 곳이 없는 정보가 있으면 먼저 방향을 묻는다.

## S6. 시안으로 정할 것

지금 화면과 제안을 나란히 보이고 방향을 정한 뒤 구현한다. 활동 바의 Reins 조작은 승인 없이 빼거나 미루지 않는다.

- 펼친 활동 바: 실행 중에 펼치면 컴포저가 147에서 380px로 자라고 역할 이름과 "중지"가 두 번씩 나온다.
- 파일을 보는 자리 셋: 상단 "파일" 탭, 대화 옆 "파일 뷰어", 터미널 보기 안의 "파일" 창. 파일 뷰어를 열면 "파일 뷰어 닫기"가 둘이다.
- 실행 기록으로 가는 길 넷: 응답 행의 "실행 #n", 상단 "실행 기록" 탭, "결과 화면에서 보기", 상단 경로의 실행 표지. "실행 기록" 탭은 실행 목록이 아니라 마지막에 본 보기를 다시 연다.

## S7. 작업 영역의 최소 폭

파일 뷰어는 384px 고정 폭으로 작업 영역 옆에 붙고, 창이 1024px 미만일 때만 작업 영역 전체를 썼다. 그래서 창 폭 1024~1200에서 뷰어를 열면 대화 칸이 376~552px이 되어 컴포저의 도구 줄이 한 줄에 들어가지 못했다(권한 버튼이 가려지고 모델 칩이 표지만 남는다).

정한 것: 작업 영역에 560px 이상이 남을 때만 뷰어가 옆에 붙는다. 자리가 없어지면 뷰어가 물러나고(열려 있었다는 것은 기억한다) 넓어지면 돌아온다. 자리가 없을 때 버튼을 누르면 지금의 좁은 화면 동작대로 작업 영역 전체를 쓴다. 오른쪽에 아이콘 줄을 따로 두지 않는다. 명세는 [Workbench](../specs/workbench.md)의 파일 뷰어 문단에 있다.

나중에 정할 것: 데스크톱 앱에서 자리가 없을 때 창을 뷰어 폭만큼 넓히는 동작.
