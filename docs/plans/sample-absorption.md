## 2. 지금 코드에서 확인한 것

- **실패 기록:** 모델 요청 기록 `ModelAttempt`에 `failure.code`, `status`, `retryAfterMs`가 남는다(`packages/contracts/src/model-requests.ts:80-104`). 분류는 `packages/adapter-pi/src/ported/dsh/retry.ts:59-98`이 한다.
  - `QUOTA`는 오류 글의 정규식(`insufficient_quota|quota.exceed|usage.limit|…`)으로 가른다.
  - 그 밖의 429는 `RATE_LIMIT`이다.
  - `QUOTA`는 자동 재시도하지 않는다(`retry.ts:106`).
- **실패가 오가는 길:**
  - 모델 브리지는 분류한 실패 객체를 보낸다(`packages/adapter-pi/src/model-bridge.ts:186`, `:208`).
  - 실행 단위가 끝날 때 worker는 오류를 문자열로만 넘긴다(`packages/adapter-pi/src/adapter.ts:744-763`). 이 문자열은 "the model request failed: HTTP 429 (QUOTA)" 같은 형태다.
  - `retryAfterMs`는 `RATE_LIMIT`일 때 공급자 쿨다운에만 쓰인다(`apps/server/src/models/request-runtime.ts:180-185`).
- **리셋 시각의 출처:**
  - ChatGPT 구독은 한도 오류 본문 `error.resets_at`(epoch 초)에 리셋 시각을 싣는다.
  - Corral은 Pi를 `maxRetries: 0`으로 부른다(`packages/adapter-pi/src/model-bridge.ts:144`). 그래서 Pi의 Codex 경로는 재시도 없이 바로 오류 본문을 해석한다(`@earendil-works/pi-ai/dist/api/openai-codex-responses.js:296-314`).
  - 그 오류 글은 "You have hit your ChatGPT usage limit (… plan). Try again in ~N min."이다(`:1265-1285`). 해석에 실패할 때만 `err.message`를 쓴다.
  - 따라서 이 글은 Corral 분류기의 `usage.limit`에 걸려 `QUOTA`가 될 것이다(추론, 실제 응답으로는 확인 못 함). 리셋 시각은 분 단위로만 남고, 정확한 `resets_at`은 버려진다.
  - 헤더 `retry-after`·`retry-after-ms`는 Pi와 Corral 분류기가 둘 다 읽는다.
  - Anthropic 구독과 Copilot은 모른다.
- **실패한 Run 뒤의 요청:** 다음 요청은 앞 Run의 요청과 끝 상태("실패")만 받는다([LLM 런타임](../specs/llm-runtime.md) "Continuation and accounting"). 실패한 Run이 한 도구 호출은 다음 요청의 대화에 실리지 않는다. 파일 변경은 Paddock에 남는다. 사람의 "다시 보내기"는 원문과 첨부를 새 요청으로 보낸다([Workbench](../specs/workbench.md) 246행).
- **대기 요청:** 서버가 Run이 끝날 때 맨 앞 대기 요청을 시작한다(`apps/server/src/session-queue.ts:93`).
- **예약 실행:** 발화 claim과 놓침 처리가 `apps/server/src/schedules/service.ts:199-265`, `store.ts`에 있다.
- **무진전 카운트** (`packages/core/src/limits.ts:95-170`)
  - 모델 응답마다 1씩 늘고, 새 도구 증거·산출물·제출·검토·승인 해결이 있으면 0으로 돌아간다.
  - `progressHash`는 도구 이름, 인자, 결과의 증거 필드(`path`, `sha256`, `text`, `exitCode` 등), 출력을 함께 해시한다(`packages/core/src/coordinator.ts:12062-12090`). 오류로 끝난 도구는 0으로 돌리지 않는다.
  - 그래서 같은 도구를 같은 인자로 다시 불러도 결과가 새로우면 0이 된다. 결과가 매번 다르게 나오는 반복(불안정한 테스트를 계속 다시 돌리는 경우 등)은 지금 게이트에 걸리지 않는다.
  - 결과가 같으면 6번째 응답에서 승인 게이트가 걸린다.

## 3. S0 측정과 확인

제품 코드는 바꾸지 않는다. 스크립트는 `output/sample-analysis-2026-11-25/scripts/`(추적하지 않음)에 두고 `python3 -I`나 읽기 전용 DB 연결로 돌린다. 로컬 DB는 서버가 쓰는 중이면 백업 사본을 읽는다. 결과에는 개수와 ID만 남기고 메시지 본문은 남기지 않는다. 모의 실행은 모두 뺀다.

- **S0a. 한도 실패의 빈도와 리셋 시각.**
  - `ModelAttempt` 중 `status=429`이거나 `code`가 `QUOTA`·`RATE_LIMIT`인 것을 공급자·인증 방식(구독·키)별로 센다.
  - 각 행에 `retryAfterMs`가 있는지, 값이 몇 분 단위인지 센다.
  - 그 요청이 속한 Run 중 사람이 같은 세션에서 다시 보낸 비율을 센다. M1의 목표 수치다.
- **S0b. 공급자별 출처.**
  - 설치된 Pi 1.6.0에서 ChatGPT·Anthropic·Copilot 구독 경로를 읽는다. 한도 오류가 리셋 시각을 어디에 싣는지(본문 필드, 헤더), 정상 응답이 남은 한도를 싣는지 표로 만든다.
  - 헤더로 오는 공급자는 Pi 패치가 필요 없다. 본문으로만 오는 공급자는 패치가 필요하다.
  - S1은 이 표에서 리셋 시각을 주는 공급자만 다룬다. 지금 확인된 것은 ChatGPT 하나다.
  - ChatGPT는 Pi 패치 없이 오류 글의 "~N min"만으로 갈지, 패치로 `resets_at`을 그대로 받을지 여기서 정한다. 분 단위로 반올림한 값은 몇십 초 일찍 보낼 수 있어서 제안은 패치다.
- **S0c. 말만 하고 끝난 턴의 빈도.**
  - 성공으로 끝난 대화 Run의 최종 응답 끝부분 200개를 표본으로 뽑는다.
  - 이 세션이 "할 일을 약속하고 끝났는가"를 직접 판정하고, 판정 근거를 개수로 남긴다.
  - 비율이 5% 미만이면 S4를 뺀다. 문턱은 결과를 보고 함께 정한다.
- **S0d. 같은 도구 반복의 빈도.**
  - 실행 단위마다 같은 도구·같은 인자가 연달아 3번 이상 나온 경우를 센다.
  - 그 반복이 무진전 카운트를 0으로 돌렸는지(결과가 달랐는지), 무진전 승인까지 갔는지, 그 승인에서 사람이 무엇을 골랐는지 센다.

### S0 결과 (2026-11-25)

수치와 근거는 `output/sample-analysis-2026-11-25/s0/results.md`에 있다. 로컬 DB 4개(개발 작업공간)에서 실제 모델로 돈 Run은 약 50개였다. 도구는 Corral 자체 도구뿐이었고 `run_command`나 편집은 없었다. 그래서 아래 결과를 코딩 작업에 그대로 적용할 수는 없다.

- **S0a:** 한도 실패는 0건이라 빈도는 모른다. 실패한 Run 8개는 모두 분류되지 않은 "the model worker reported a request failure"였고, 요청 기록(`model_attempts`)에 한 줄도 없었다. 실패한 worker 요청은 요청 기록에 남지 않는 것으로 보인다. 따라서 S1은 실패 분류(`code`, `resetAt`)를 실행 단위 실패까지 싣는 일부터 한다. §8의 가정은 실패한 요청에 대해서는 틀렸다.
- **S0b:**
  - ChatGPT는 한도 오류 글에 분 단위 리셋 시각을 남긴다. Pi 패치로 `resets_at`을 받는 것을 S1에 넣는다.
  - ChatGPT와 Anthropic 모두 정상 응답의 헤더를 Pi가 거르지 않고 Corral 모델 브리지에 넘긴다. 남은 한도 헤더가 실제로 있는지는 실제 응답 한 번씩을 봐야 안다(S2의 시작 조건).

## 4. S1 M1a: 한도가 풀리면 다시 보내기

동작과 계약의 정본은 [한도 뒤 다시 보내기](../specs/features/usage-limit-resend.md)다. 여기에는 만든 것의 위치와 처음 계획에서 달라진 점만 적는다.

**만든 것**

- **리셋 시각:** `packages/adapter-pi/src/ported/dsh/retry.ts`가 `QUOTA`일 때 `retry-after-ms`·`retry-after` 헤더와 ChatGPT 글의 "~N min" 가운데 늦은 쪽을 `resetAt`으로 남긴다. SDK worker의 실패에도 오류 글을 싣는다(`sdk-worker.ts`).
- **기록:** `AgentSettlement.usageLimit` → `execution.settled.usageLimit` → projection의 실행 단위로 이어지고, 모델 요청 기록 `failure.resetAt`에도 남는다.
- **판단:** `packages/core/src/usage-limit-resend.ts`. 규칙은 샘플 저장소의 `limitRecoveryCommand`에서 가져왔다.
- **대기열:** `apps/server/src/session-queue.ts`가 Run이 끝날 때 사본을 대기열 맨 앞에 두고, 시각에 시작한다. 화면이 실행 뒤에 요청을 기록해도 사본을 만들고, 다른 Run이 끝나면 지운다. 서버를 시작할 때 시계를 다시 건다.
- **화면:** 대기 카드에 "HH:MM에 다시 보냄"(오늘이 아니면 날짜도), 다시 보낸 요청의 메타 줄에 "한도가 풀려 다시 보냄".
- **테스트:**
  - `packages/adapter-pi/test/request-retry.test.ts`
  - `packages/core/test/usage-limit-resend.test.ts`
  - `apps/server/test/session-queue-unit.test.ts`
  - `apps/server/test/usage-limit-resend.test.ts`(실제 서버·저장소)
  - `apps/studio/src/workbench/session/ComposerQueue.test.tsx`

**처음 계획과 달라진 점**

1. **Pi 패치 없음.** ChatGPT의 "~N min" 글에서 읽고 1분을 더한다. 분 단위로 정확하다.
2. **실패 줄이 아니라 대기 카드.** 다시 보낼 요청을 대기 요청 하나로 두어, 지금 시작·편집·제거를 그대로 쓴다.
3. **대기열 전체가 기다린다.** 같은 연결의 대기 요청만 기다리게 하는 대신 순서를 지킨다. 뒤의 요청이 실패한 요청의 결과를 전제로 썼을 수 있기 때문이다. "지금 시작"은 언제든 된다.
4. **서버가 꺼졌던 경우.** 시각이 24시간 안에 지났으면 다시 켜진 뒤 바로 보낸다. 샘플의 규칙을 따랐다. 처음 계획은 "놓침으로 표시하고 소급하지 않음"이었다.

**확인하지 못한 것**

- 실제 ChatGPT 한도 응답은 본 적이 없다. 그 글이 `QUOTA`로 분류되는 것은 Pi 소스를 읽고 내린 추론이다.
- 브라우저 화면은 확인하지 못했다. 모델 없는 서버의 모의 에이전트는 사용 한도 실패를 낼 수 없다. 카드는 jsdom 테스트로만 봤다.
- 서버 통합 테스트와 카드 테스트는 구현한 뒤에 썼다. 분류·판단·대기열 테스트는 먼저 실패를 확인했다.
- 실패 JSON이 300자를 넘으면(아주 긴 요청 ID) worker의 `safe()`가 잘라 리셋 시각을 잃는다. 고치지 않았다.
- 리뷰: Astra가 `model_not_found`로 돌지 않아 어드바이저가 리뷰했다. Astra와 Sol의 확인은 아직이다.

**정한 것(11-25)**

  - 확인한 것: 모의 서버와 Vite에서 열기 → 목록 → 앱 안의 stage·커밋 → 부모에 합치기 → merge·계속 → 부모 사본에 파일과 두 부모 커밋까지 걸었다(en, 1280×800). 세션 행을 읽는 E2E flow 3개와 server 2개가 통과했다.
  - 보강(어드바이저 검토 뒤): 부모 실행 중 열기와 서브세션 안의 실행, 두 단계 서브세션(가운데로 합침, 팀을 이어받음)을 HTTP 테스트로 확인했다. 실패한 열기는 같은 화면에서 같은 명령 ID와 제목으로 다시 보낸다. 변경 탭 머리는 탭이 화면에 나올 때와 Git 보기의 새로 고침에도 다시 읽는다. API 계약 표에 두 라우트를 더했다.
  - 사용자에게 묻지 않고 정한 것: 버튼은 꺼진 채 두지 않고 없앤다, 가운데 세션을 지우면 그 아래는 맨 위로 간다(조부모로 옮기지 않는다), 서브세션 브랜치는 부모 제목으로 이름 짓는다(그래서 부모와 서브세션 브랜치가 끝의 6자리만 다르다), 이어받은 미커밋 변경은 합치기를 막지 않는다.
  - 확인하지 않은 것: 합치기의 충돌 길, 데스크톱 앱. 흐름 지도(`ux-flows`)가 없어 실행 기록은 지도와 대조하지 못했다. 테스트는 소유자의 미커밋 변경이 있는 작업 트리에서 돌았고, 커밋된 트리만으로는 돌리지 않았다.

**T4 PR 흐름**
- 출처는 ade 샘플이다. 상황에 따라 바뀌는 commit·push·PR 버튼과 PR 본문 생성(D5), 에이전트가 셸로 만든 PR 자동 연결(`PullRequestSyncReactor.ts`), PR 감시와 에이전트 깨우기(`pullRequestWatch.ts`, D8).
- 서브세션 브랜치에서 PR을 열 수 있게 한다. 기능 미리보기의 `pr-review`는 실제 기능으로 바꾸거나 지운다.
- 정한 것(11-25, 사용자)
  - 사람이 로그인한 `gh`를 실행만 한다. 토큰을 읽거나 저장하지 않는다. 세션의 PR은 Paddock의 지금 브랜치를 head로 한 PR이고, 에이전트가 셸로 만든 PR도 이 브랜치 조회로 찾는다(샘플의 API·토큰과 셸 출력 파서는 옮기지 않는다. 모든 Paddock이 자기 브랜치를 가지기 때문이다).
  - PR 제목과 본문은 세션의 모델이 쓰고, 모델이 없으면 커밋 목록으로 채운다. 보내기 전에 사람이 고친다.
  - 에이전트를 깨우는 것은 검사 실패와 병합 충돌뿐이다. 리뷰와 댓글은 확인 필요에만 올린다.
  - 서브세션 변경 탭은 "부모에 합치기"가 앞이고, 서브세션의 PR은 저장소의 기본 브랜치로 향한다.
  - 기능 미리보기의 `pr-review`는 리뷰 댓글을 실제로 만들 때까지 둔다.
- 단계: T4a 만들기·연결·PR 상태, T4b 감시와 깨우기. 단계마다 명세·실패 테스트·화면 걷기·커밋.
- T4a 결과(11-25)
  - 명세 [풀 리퀘스트](../specs/features/pull-requests.md). 서버는 `gh`를 데이터 폴더에서 `--repo`로만 실행하고(프롬프트·색·페이저·업데이트 알림 끔, 30초), 실패는 없음·종료 코드 4·그 밖으로만 나눈다. 저장소는 설정된 `remote.origin.url`로, 기본 브랜치는 `origin/HEAD` 뒤에 `gh repo view`로 안다.
  - 변경 탭 머리 아래 PR 줄(A안). 열린 PR이 없고 기본 브랜치에 없는 커밋이 있으면 "올리고 PR 열기"·"PR 열기"·"Git 보기에서 맞추기" 가운데 하나, 합쳐진 PR 뒤에도 새 PR을 연다. `gh` 줄은 열 것이 있을 때만.
  - 대화상자: 초안은 세션의 최근 요청 모델(팀 도우미와 같은 단발 호출과 작업 기록), 없으면 커밋 목록. 닫으면 초안 요청을 멈춘다. push는 Git 보기의 push 명령(영수증)을 먼저 보내고, PR 열기는 대화상자를 연 때의 head로 보내며 같은 브랜치에 열린 PR이 있으면 그것을 돌려준다.
  - 샘플에서 옮긴 것: PR 내용 지침과 구획 제한(`apps/server/src/pull-requests/prompt.ts`, 템플릿과 대화 맥락 없이).
  - 확인한 것: 서비스·라우트·`gh` 실행기 테스트, 변경 탭 테스트, 가짜 `gh`와 로컬 bare 저장소로 브라우저에서 줄 → 대화상자 → push → PR 열림까지 걸었다(en). push 실패 시 PR을 열지 않고 실패를 보이는 것도 화면에서 봤다. 변경 탭을 쓰는 E2E server 스펙 5개 통과.
  - 리뷰 뒤 보강: 남은 GitHub 결과가 없으면 "PR 없음"이 아니라 GitHub를 읽는다. 버려진 GitHub 읽기(StrictMode, 빠른 Git 변경)는 다시 한다. 탭이 다시 보이면 GitHub를 읽는다. 세션의 모델은 보낸 요청의 경로 기록에서 찾는다. `gh`는 데이터 폴더의 `pull-requests`에서 돈다. 대화상자와 줄의 push는 작업 ID를 결과를 읽은 뒤에만 다시 쓴다. `origin/HEAD`와 `gh`가 없으면 올리지 않은 커밋이 있을 때만 `gh` 줄을 보인다.
  - 확인한 것(추가): DeepSeek(deepseek-hive)로 초안 한 번, 1.7초에 `source: model`, Summary·Testing 형식, 로컬 경로 없음. 가짜 `gh`로 줄의 상태들(가장 긴 줄, 합쳐진 PR 뒤 새 PR, 맞추기, 로그인 안 됨, 읽기 실패, 서브세션, 한국어)을 화면에서 봤다.
  - 실제 GitHub 확인(11-25, 사용자가 스크래치로 내준 비공개 저장소): 모델 없는 서버로 Git push 명령 → 커밋 목록 초안 → PR 열기가 됐다(`gh pr create --repo --head`가 데이터 폴더에서 돈다). 커밋 상태 셋(실패·성공·진행 중)은 `StatusContext`의 `state`로 오고 줄은 1·1·1로 셌다. 리뷰 규칙이 없으면 `reviewDecision`은 빈 문자열이다. 빈 설정 폴더의 `gh`는 종료 코드 4다. 새 커밋 뒤 "올리기"가 뜨고, 다른 작업 ID로 다시 열어도 PR은 하나다.
  - 확인하지 않은 것: Actions가 만드는 `CheckRun`의 모양(저장소의 실행 시간을 쓰지 않으려고 돌리지 않았다), 데스크톱 앱. T4b 시험용으로 그 저장소의 PR #1과 브랜치를 열어 두었다.
  - 디자인으로 남은 것: 가장 긴 줄(실패한 검사·변경 요청·충돌·올리기)은 패널 폭에서 두 줄이 되고, 줄 안의 버튼이 기본 높이(36px)다. 밀도 규칙상 작은 고정 크기는 DESIGN.md의 예외 목록에 넣어야 쓸 수 있다.
- 확인한 `gh` 사실(2.105, 도움말): `gh pr list --head <브랜치> --state all --json …`, `gh pr create --repo --head --base --title --body-file`, `gh pr view <번호> --repo --json …`. JSON에 `statusCheckRollup`, `reviewDecision`, `mergeable`, `mergeStateStatus`, `comments`, `reviews`, `headRefOid`, `state`가 있다.

  - 뒤에 고친 것: 확인 필요의 PR 항목 버튼이 이름 키(`Inbox.open.changes`) 없이 나가 있었다. "PR 열기"(Open pull request)를 넣고, 보관한 세션의 감시 끝(서비스 경로까지), PR 항목의 행 문구, "PR 감시가 보냄" 메타 줄을 테스트로 묶었다. 서버·Studio 전체 스위트는 다시 돌렸다(서버의 실패 셋은 부하 때문이었고 단독으로 통과).

- T5 사라진 질문: 쓴 글만 옮기고 고른 선택지는 옮기지 않는다. 확장 요청 가운데 쓴 글은 `input` 종류뿐이다(가려진 입력 종류는 없다).

- T5 팔레트: 고정한 대화를 팔레트에서 앞세우지 않는다. 고정은 사이드바의 순서이고, 팔레트는 돌아가기 위한 목록이라 최근 사용만 본다.
- T5 사이드바(11-25 고침): 킷은 하위 행을 쉴 때 보조 글자색으로 그리므로(포인터를 올리거나 고른 행만 전경색) "보조 색으로 가라앉히기"는 화면에서 차이가 없었다. 쉬는 행은 킷 색 그대로 두고, 나머지 행의 제목을 전경색(보통 굵기)으로 밝힌다. 점이나 더 흐린 색은 쓰지 않는다. 지금 열린 대화의 행은 킷이 굵게 밝힌다.
- T5 사이드바: 지금 프로젝트의 확인 필요에 항목이 있는 대화(꺼진 자동 시작의 대기 요청, 실패한 검사, PR 항목 등)는 밝다. 결과물의 수(`unreviewed`, `lsp_proposal`)는 행을 밝히지 않는다(결과물은 숙제가 아니다). 다른 프로젝트의 항목은 사이드바가 읽지 않으므로 모른다. 회의는 본 것으로 센다: 할 것이 없으면 쉬고, 있으면 밝고, "읽지 않음"은 없다.
- T5 대화 표시: 새 내용은 행으로 센다(기하로 재지 않는다). 그려지지 않은 행은 잴 수 없고, 위의 행이 다시 재어지는 것은 새 내용이 아니다. 개수와 글자는 붙이지 않는다.
- T5 착지: 들어올 때만, 방문마다 한 번. 들어온 뒤 처음 답한 실행 목록에서 정한다(그때 돌고 있던 실행은 놓지 않는다: "따라가는 동안은 끝을 지킨다"는 71행 규칙 그대로). 이 탭에 읽던 자리가 있거나 주소가 자리를 가리키면 놓지 않는다. 답의 행이 다 그려질 때까지 기다렸다가 화면보다 커지면 놓는다(실행 기록은 행이 붙은 뒤에 읽힌다). 사람의 첫 움직임·보내기·다른 배치가 오면 그만둔다.
- T5 보이는 것만 승인: 경로를 고르는 승인과 내용을 아직 읽지 못한 도구·검사 승인은 들지 않는다. 도구 승인도 평범한 승인("한 번 허용")으로만 들고, 실행 내내 허용은 들지 않는다.
- T6 진행 방식: 항목마다 코드 전에 읽기만 하는 관문을 하나 확인하고 그 결과를 계획에 적는다. 관문을 통과하지 못하면 이유와 함께 미룬다. 뜻이 다른 작은 것을 대신 만들지 않는다. 순서는 세션 깨우기와 곁가지 질문 → adapter-pi 도구(묶음 끝에 GLM·DeepSeek 실제 실행을 지켜보며 한 번씩) → 바깥 면(가져오기, MCP).
- T6 스스로 깨우기: 관문은 ABS-08에 한 번만 도는 예약이 Coordinator를 거쳐 세션의 대기열에 들어가는 길이 있는지. 세션마다 기다리는 깨우기 하나, 사람의 요청 없이 연속 세 번까지(PR 깨우기와 같은 한도), 그 뒤는 확인 필요. 사람의 요청이 세기를 되돌리고, 보관하면 취소된다.
- T6 `/btw`: 관문은 입력창이 `/runs/explain`을 그만 쓴 까닭(Git)과 샘플의 `/btw`. 세션의 실행이 도는 동안 explain 실행을 시작해 본다. 그 실행이 세션의 가장 새 실행이 되면(사이드바 상태, 대기열 시작, PR 읽기, 본 실행 기록을 건드림) 미룬다.
- T6 큰 파일 선언: 윤곽은 본문을 읽은 것이 아니다. 반례: 윤곽만 읽은 뒤의 편집은 거절된다.
- T6 Hashline 거절: ABS-03을 먼저 읽는다. 읽은 근거가 줄 범위 단위면 보여 준 줄은 읽기 도구의 기록으로 센다. 파일 단위면 세지 않고 보여 주기만 한다.
- T6 편집 방식 기본값: 명시 설정이 이긴다. 샘플의 표를 그대로 옮기고 실제로 확인하지 않은 계열을 적는다. Corral에 편집 방식이 하나뿐이면 뺀다.
- T6 편집 방식(11-26 되돌림): "빈 값이면 모델에 따라"를 거두고, "모델에 따라"를 역할이 고르는 선택으로 했다. 빈 값을 모델에 맡기자 저장소가 세 번 밀어냈다: 자동 모드와 대화 정의를 바이트 단위로 얼린 테스트(다시 기록하지 말라고 적혀 있다), "기존 자료는 Pi 방식"이라는 ABS-03 문장, 시작 역할을 정의의 역할과 비교하는 테스트들. 대화의 기본 에이전트가 GPT에서 화면의 손잡이 없이 Hashline으로 바뀌는 것도 막는다. 새 역할의 기본을 "모델에 따라"로 바꾸는 것은 GPT로 지켜본 실행 한 번 뒤 소유자가 정한다.
- T6 의도 문장: 보여 주기만 한다. 도구 인자에 실려 오면 같은 호출 세기, 실행 내내 허용의 맞춤, 해시 전에 뗀다(그렇지 않으면 문장이 달라져 9번 멈춤과 실행 내내 허용이 깨진다). 두 반례를 먼저 쓴다.
- T6 셸 출력 줄이기: 정의 파일의 머리와 샘플의 고지를 본다. 그 파일이 분명히 기여자의 것이 아니면 뺀다.
- T6 가져오기: 사람이 파일을 고른다. 서버는 홈 폴더를 훑지 않고 본문을 기록하지 않는다. 새 대화로 들어오고, 첫 요청이 대화록을 텍스트 첨부로 싣는다(만든 실행이나 턴이 아니다). 파서만 옮긴다.
- T6 MCP: 사람이 시작하는 stdio 프로세스, 새 포트 없음. 화면이 보이는 것을 읽고, 요청은 보통 항목으로 보내 입장 검사와 승인을 그대로 받는다. 승인이나 질문에 답하지 않고, 자격 증명과 설정을 건드리지 않는다. SDK가 새것이면 `pnpm deps:record`.

  - 편집 방식 "모델에 따라": 역할이 고르는 세 번째 선택(`model`)이다. 고르면 실행 단위의 모델 계열이 정한다(샘플의 표 그대로: 기본 Hashline, Kimi·MiMo·MiniMax·DeepSeek·StepFun·Codex Spark·GLM 5.3 Flash·Qwen 3.8과 이름 없는 모델은 Pi). 고르지 않은 역할과 Corral이 만드는 정의(대화의 기본 에이전트, 자동 팀)는 T6 전처럼 Pi다. 풀린 값은 실행 단위의 시작 입력에 실려 어댑터와 입장 검사가 같은 값을 보고, 시작 입력에는 `model`이 남지 않는다. 체크포인트에서 이어 가는 비교도 같은 값으로 한다(이어 가기의 `model` 역할은 테스트하지 않았다). Hashline 계열 모델로는 아직 한 번도 돌지 않았다.
  - 의도 문장: 워커가 내놓는 Corral 도구마다 선택 필드 `i`(왜 이 호출인가, 몇 마디). 워커가 Coordinator에 허가를 묻기 전에 인자에서 떼어 따로 싣고, Coordinator는 `tool.requested`에 표시용으로만 남긴다(200자). 검사·같은 호출 세기·실행 내내 허용·해시·실행은 늘 `i` 없는 인자를 본다(반례: `i`만 다른 세 호출의 인자가 같다). 실행 기록의 도구 행 설명 줄 맨 앞에 보인다. Pi가 스스로 내놓는 Harness 도구(read·write·edit)에는 없다.
  - 고친 것(11-26, 어드바이저 검토 뒤): Hashline이 보인 줄은 거절 문장(영구 기록의 `tool.finished` 실패 문장)이 아니라 적용하지 않은 결과(`applied: false`)의 본문으로, 읽기와 같은 크기 한도로 돌려준다. `i`는 워커가 감싼 도구에서만 뗀다(MCP 도구에 진짜 `i` 인자가 있을 수 있다). 인자를 숨기는 호출(`ask_user`, `update_plan`, `advise`, Harness 호출)은 의도도 남기지 않는다. 편집 방식은 `write_file`이 있는 역할에만 채운다(읽기만 하는 역할이 `read_hashline`을 얻지 않게). 체크포인트에서 이어 갈 때는 채운 방식까지 같은 역할로 비교한다. pi-ai는 strict 전송 때 선택 속성을 "필수 + null"로 바꾸고 Corral은 strict를 보내지 않으므로 `i`가 요청을 깨지 않는다.
  - 실제 모델 확인(11-26, `tests/live/tool-intent.live.test.ts`, 지켜보며 한 번씩): DeepSeek V4.1 Flash와 GLM 5.3 Flash 모두 `i`가 붙은 도구를 그대로 불렀고 두 호출 모두 의도 문장을 채웠다("Saving the two-line note" 등). 인자에는 `i`가 없었고 두 실행 모두 성공했다. 두 모델은 표에서 Pi 쪽이라 Hashline 기본값과 Hashline 거절 줄은 실제 모델로 확인하지 않았다(파일 도구는 작업 공간이 있어야 해서 이 확인 밖이다).
  - Hashline 실제 확인(11-26, `tests/live/hashline-unseen.live.test.ts`, DeepSeek V4.1 Flash에 Hashline을 명시, 연결한 폴더, 한 번): 1–5행만 읽고 40행을 고치자 적용되지 않은 결과로 그 줄들이 왔고, 같은 태그로 다시 고쳐 40행이 바뀌었다. 실패 줄에 파일 글은 없었다. 알고 두는 것: 적용되지 않은 편집도 도구 행에는 "완료"로 보인다(실패가 아니라 결과이기 때문).
- 곁가지 질문(`/btw`) 화면(서버의 explain 경로가 있다)
- 다른 코딩 도구의 세션 가져오기(ade C13, pi 10.5)
- Corral 기능을 MCP 서버로 열기(ade A16·H6, agentes 10.3). 권한 범위를 먼저 정한다.
- 에이전트가 스스로 나중에 다시 깨어나기(agentes `follow_up`, ade PR 감시)
- 도구 호출마다 의도 문장(pi 1.2), 큰 파일은 선언만 먼저(pi 3.2), 셸 출력 줄이기(pi 4.2, 정의 파일의 출처 확인 필요)
- 모델 계열별 기본 편집 방식(pi 2.6)
- Hashline 편집 거절 때 문제 줄을 함께 보여 주기(pi 2.4). 작은 포팅이 아니다. 읽은 근거의 정의(ABS-03)가 바뀌므로 명세 결정이 먼저다.

**T7 이벤트 로그 정리**
- ade A6 방식(보관 기간, 정리 경계 표시, 재접속 replay 상한)을 참고한다. Corral은 실행 기록 재열람이 제품 약속이라, 무엇을 지워도 되는지부터 정한다.

**라이선스(정함, 11-25)**
- 사용자가 세 샘플 모두 직접 기여한 코드라며 그대로 옮겨도 된다고 했다. 옮긴 파일은 `THIRD-PARTY-NOTICES/`에 "기여자 본인의 코드"로 적고, 사용자가 저장소 이름과 커밋을 알려 주면 그것을 더한다.
- 그 전에 확인한 표기: Corral은 MIT이고, 포팅한 코드를 `THIRD-PARTY-NOTICES/llm-runtime-ports.md`에 저장소와 커밋으로 적는다.
  - ade: 패키징 메타데이터가 MIT다.
  - pi: 라이선스 표기가 없다.
  - agentes-chat: AGPL 신호가 있다(데스크톱 크레이트, `check-licenses.ts`의 NOTICE 언급).

## 8. 아직 확인하지 못한 것

- 리셋 시각을 준다고 확인한 공급자는 ChatGPT 하나다.
- 로컬 DB에는 실제 코딩 작업 기록이 거의 없다. S0의 빈도는 대표성이 없다.
- 실패한 worker 요청은 `ModelAttempt` 행으로 남지 않는다(S0a에서 8/8). 그 이유는 S1에서 코드로 확인한다.
- ChatGPT 한도 오류가 실제로 `QUOTA`로 분류되는지는 실제 응답으로 본 적이 없다.

## 9. 진행 방식

- 메인 세션이 직접 구현한다. Coordinator와 데이터 경로를 바꾸는 단계는 Astra 리뷰와 Sol 확인을 거친다. Astra가 안 될 때는 어드바이저가 리뷰한다(사용자 결정, 11-25).
- E2E는 바뀐 명세에 해당하는 것만 돌리고, 전체 E2E는 마지막에 한 번 돌린다.
- 끝난 단계는 로컬 `develop`에 합친다. push와 PR은 요청이 있을 때만 한다.
